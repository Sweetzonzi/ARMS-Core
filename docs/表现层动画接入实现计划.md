### 0.4 由基线得到的三条结论

**结论 A：表现层首版不需要角色控制器的任何状态量。** 由 §0.1 与 §0.2 两张表的对应关系：角色控制器只产出 `ON_GROUND` / `SPEED` / `VERTICAL_SPEED` / `KCC_JUMP_BOOSTING` 四项（§0.2 的「变量容器的写入来源」行）；逻辑层状态图消费其中三项（§0.2 的「逻辑层状态图读到的变量」行），产出的结论是 `POSTURE` / `GAIT` / `VERTICAL`（§0.2 的「逻辑状态快照的产出方向」行）；而这三项已经在同步字段里（§0.2 的「四项逻辑状态已在下行通道里」行）。表现层的选片只需要这三个枚举，因此与角色控制器无直接依赖。

**结论 B：驱动必须按物理子步，不能按游戏刻。** 由 §0.1 的「时间推进的单位」行与「客户端也有物理线程」行，客户端 `tps = 60` 而游戏刻是 20 Hz；`AnimInstance` 每调用一次 `physTick()` 只推进 `1/60` 秒，所以每游戏刻调用一次会让动画以 `1/3` 速度播放，同时让 `progress(dt)` 里以秒为单位的驻留时长判据差 3 倍。

**结论 C：并行动画的每个槽位必须独占一层。** 由 §0.1 的「层内多动画的混合口径」行，同一层里放两个实例时，只在其中一个出现的骨骼，其位置与缩放会按 `1/2` 被拉向 0 / 1。由 §0.3 第 3 条，`pre_parallel0` 与 `pre_parallel1` 的交集是 2 个骨骼，即同层方案会精确地让这 2 个骨骼的位置与缩放出现折半。把每个槽位放进独立层即无此问题，也与「一个槽位一个控制器」的语义一致。

## 1. 目标与非目标

**目标**

1. 素体动画在客户端按物理子步推进，姿态由一组硬编码状态机选择，且状态机的输入是服务端权威的 `POSTURE` / `GAIT` / `VERTICAL`。
2. 表现层编排归 `MechaControl`，使其在客户端也有实例——因为表现层后续会承载实际游戏性逻辑（关键帧驱动的部件刚体，§8.4），不适合挂在渲染适配器上。
3. `pre_parallel*` 以常驻循环层的形式接入。

**非目标**

1. 覆盖层与武器本地状态机（动画清单里 `use_mainhand` / `use_offhand` / `swing_hand` 一类）。
2. `parallel*` 的加性叠加层（§8.1）。
3. 内容包以 `animation_controllers` JSON 替换或接管姿态选择（§8.3）。
4. 姿态与碰撞体轮廓的联动（胶囊换形属角色控制器的范围）。

## 2. 架构决策

### D1 表现层编排归 `MechaControl`，客户端也构造它

**决策**：表现层的容器使用者、状态机集合、常驻层与就绪守卫由 `MechaControl` 持有；客户端分支同样构造 `MechaControl`，其 `body` 为 `null`。

**理由**：表现层后续要承载关键帧驱动的部件刚体（§8.4），那是编排与游戏性逻辑，不是渲染细节；把它放在 `MechaAnimatable` 里会让一个自述为「渲染适配器、装配体落地后整体删除」的类承担长期职责。而 `MechaControl` 已经具备表现层所需的全部设施：变量容器、事件 latch、以及「主线程发布 / 物理线程帧首读取」的快照模式（§0.2 的「跨线程发布快照的既有模式」行）。

**代价**：`ArmsCore` 的类 Javadoc 写有「客户端不运行控制器与状态机」，本计划落地后该表述与实际不符，需按 §5 的三条不变量改写。

### D2 客户端对角色控制器的依赖：不建刚体，预留镜像口

**决策**：客户端 `MechaControl` 的 `body` 为 `null`，不建 `MechaCharacter`；客户端不推进逻辑状态机，`POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 由下行通道写入。同时预留一个「角色控制器镜像」的写入位置，首版留空实现。

**理由**：由结论 A，首版表现层不需要角色控制器状态量，因此不建刚体的成本是零。反过来，客户端本地建刚体会**破坏权威一致性**：客户端的输入与地形权威都不存在，着地判据在台阶与边缘处与服务端不同，于是同一个 `GAIT` 会在两端算出不同值，表现层跟着播不同动画——这比一个网络往返的延迟更难排查。此外客户端物理级别的步数是自适应降步的，本地刚体的 `onGround` 与速度会抖动。

**预留口的意义**：将来表现层需要按 `VERTICAL_SPEED` 细分上升 / 下落段，或需要 `ON_GROUND` 做表现层判定时，只需追加同步字段并在该处填入镜像值。其中 `SPEED` 与 `VERTICAL_SPEED` 可由已经在同步的 `DATA_VEL` 推出，无需新增字段（§0.2 的「四项逻辑状态已在下行通道里」行）。

**遗留代价**：动画对状态变化的响应比服务端晚一个上行往返（服务端物理步 → 主线程写同步数据 → 广播 → 客户端接收）。离散状态切换上表现为延迟而非错误。

### D3 状态机载体用 `MultiAnimStateMachine`

**决策**：姿态状态机用 `MultiAnimStateMachine`，`animTargets` 传单元素列表，`animGroup` 传 `AnimGroups.LOCOMOTION`。

**理由**：装配体由多个 `SubPart` 组成，逐零件渲染落地后 `animTargets` 需要扩成多元素列表；现在就选广播式载体，届时不改图结构。附带收益是三级动画回退可用（§0.1 的「广播式状态机的行为」行）。

**代价**：`MultiAnimStateMachine` 上只有 `PlayAnimAction` 有效，`StopAnimAction` / `MoLangAction` / `SoundAction` / `ParticleAction` 在它上面会告警并跳过。本计划的图只用 `PlayAnimAction`，不受影响。

### D4 驱动点双端共用 `PhysicsLevelTickEvent.Pre`

**决策**：把服务端侧已有的物理步扇出改为双端共用：去掉 `level.isClientSide()` 提前返回，对客户端 Level 也遍历注册表调用 `ArmsCore.prePhysicsTick(dt)`。客户端的 `dt` 由同一个 `1f / tps` 公式得出（服务端 100，客户端 60）。

**理由**：只需一处改动即可满足结论 B（按物理子步驱动）。客户端物理级别已存在（§0.1 的「客户端也有物理线程」行），注册表已支持客户端 Level（§0.2 的「注册表双端可用」行），`ArmsCore.prePhysicsTick` 已对 `mechaControl == null` 提前返回。

### D5 层号：并行动画一槽位一层，层号取本项目私有的一段

**决策**：定义本项目私有的层号常量，`pre_parallel` 槽位 N 用 `PRE_PARALLEL_BASE + N`，其中 `PRE_PARALLEL_BASE = -8`，即八个槽位落在 `-8`~`-1`，全部低于 `AnimGroups.AMBIENT`（1）。姿态机器继续用 `AnimGroups.LOCOMOTION`（2）。

**理由**：由结论 C 需要一槽位一层；而 Spark-Core 的层号是 2 的幂（§0.1 的「现存层号」行），低于 `AMBIENT` 的可用整数只有 0 与负数，因此取一段负数作为槽位段。层号只是 `Int` 键，引擎不对其取值域作假设。

## 3. 分层与职责

表现层引入后，一个骨骼的最终姿态由下列层按层号升序叠加得出。表中「首版」列标出本计划填内容的层。

| 层号 | 层 | 写入者 | 混合模式 | 首版内容 |
|-----:|----|--------|----------|----------|
| `-8` ~ `-1` | `pre_parallel` 槽位 0~7 | 每槽位一个常驻 `AnimInstance` | 覆盖 | 槽位 0、1 |
| 1 | `AMBIENT` | 未使用 | 覆盖 | — |
| 2 | `LOCOMOTION` | 四台姿态状态机 | 覆盖 | STAND / AIR / WATER / CROUCH |
| 4 | `POSTURE` | 覆盖层（持物、瞄准、骑乘） | 覆盖 | 非目标 |
| 8 | `ACTION` | 覆盖层（挥动、使用、开火） | 覆盖 | 非目标 |
| 16 | `OVERRIDE` | 强制覆盖（死亡、布娃娃） | 覆盖 | 非目标 |
| 32 | `PARALLEL` | 槽位 0~7 各一层 | 加性 | §8.1 |

层的覆盖是**按骨骼**生效的：某一层若没有任何实例驱动某骨骼，该骨骼在本层取不到值，于是低层的值保留。这解释了为什么 `pre_parallel0` 的那 55 个独占骨骼会显现（§0.3 第 2 条），也解释了为什么姿态机器必须真的播一个动画，而不能"不播以保留底层"。

## 4. 详细设计

### 4.1 `MechaControl` 双端化

三处改动。

**4.1.1 构造与权威分支**

构造参数中 `body` 改为可空。新增一个判定方法（如 `hasBody()`）作为权威分支的开关，取值为 `body != null`。`ArmsCore` 的构造分支由「客户端不建 `MechaControl`」改为「客户端建 `MechaControl(this, null)`」，服务端分支不变（仍在 `authoritative` 为真时读物理空间建刚体）。

**4.1.2 物理步分段**

`onPhysicsStep(dt)` 按顺序分三段，前两段的两个权威调用用 `hasBody()` 包住：

```
onPhysicsStep(dt):
    if (hasBody()) frameLogic(dt)             // 汇入快照与刚体状态 → 推进逻辑树 → 产出回写 → 转发输入
    presentation().progress(dt)               // 表现层：状态机推进 + 动画时间推进
    if (hasBody()) { extractAnimRootDelta(); body.prePhysicsTick(dt) }
```

表现层推进的位置沿用 §0.2 的「物理步主流程」行给出的空档（`frameLogic` 之后、`extractAnimRootDelta` 之前），不改变既有的权威侧顺序。

**4.1.3 下行状态通道**

新增一对方法，与 `applyConditionSnapshot` / `conditionSnapshot` 同构（§0.2 的「跨线程发布快照的既有模式」行）：主线程用 `applySyncedLogicState(LogicStateSnapshot)` 发布到一个 volatile 字段，物理线程在帧首用该字段把 `POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 及其派生 one-hot 写入 `variables`。派生 one-hot 的口径与 `MechaStateVariableKeys` 中既有键的定义一致（`IS_STANDING` / `IS_AIRBORNE` / `IN_WATER_POSTURE` / `IS_CROUCHING` / `IS_PRONE` 以及 gait、vertical 各自的 one-hot 组）。

同一 record 在这条通道上两个方向的语义相反，需在 Javadoc 里写明：服务端方向是**产出**（`snapshotLogicState()` 从容器读出，供主线程写同步数据），客户端方向是**输入**（从同步数据写入容器）。

### 4.2 客户端主线程投影

客户端的 `LevelTickEvent.Post` 分支（由 §4.4 的接线决定它落在哪个订阅者里）做三件事：从同步数据读 `DATA_POSTURE` / `DATA_GAIT` / `DATA_VERTICAL` / `DATA_ENERGY`；用新增的 `fromMolangName(String)` 把三个字符串翻成枚举（§0.2 的「三个枚举只有单向换算」行指出目前只有单向换算）；组装 `LogicStateSnapshot` 后调用 `applySyncedLogicState`。record 的 `equals` 可用于抑制同值发布。

### 4.3 客户端物理线程驱动

由 D4，客户端侧不需要新增订阅者。`ArmsCore.prePhysicsTick` 增加一个客户端分支：**跳过逻辑状态快照的发布**（客户端不从容器反推状态，它的状态来自 §4.2 的投影），其余步骤共用。表现层的推进由 `MechaControl.onPhysicsStep` 内部完成（§4.1.2），因此这一层不需要额外接线。

### 4.4 表现层编排

新增 `common/control/presentation/` 包，内容如下。

| 文件 | 职责 |
|------|------|
| `MechaAnimPresenter` | 编排。持有 `MechaAnimatable`、四台姿态状态机、常驻层实例表、就绪守卫与拆除逻辑 |
| `MechaPresentationGraphs` | 四张姿态图的纯数据常量（`StateMachineGraph`） |
| `MechaAnimPreset` | 动画名常量与「姿态状态 → 动画名」的映射表（把映射集中一处，便于将来由内容包替换，§8.3） |
| `MechaAnimGroups` | 本项目私有的层号常量（§D5） |

`MechaAnimatable` 由 `client` 包移入本包。判据是它没有引用任何客户端专属类型（其 import 只有 Spark-Core 的动画类与 `Level` / `Vec3` / `JOML` / `Lombok`），因此放在 `common` 下不会在专用服务端触发类加载失败；渲染侧的 `MechaPlayerRenderer` 从 presenter 取动画体供绘制，其静态映射表随之移入 presenter。

### 4.5 就绪守卫与重启

三个就绪条件相互独立、到达顺序不保证：客户端实例出现、内容包读取完成（`OModel.ORIGINS` 与 `OAnimationSet.ORIGINS` 有内容）、客户端物理级别建立。守卫写成幂等入口，`MechaControl.onPhysicsStep` 每步调用一次：

```
presentation().progress(dt):
    if (!ready()) return
    ensureStarted()                       // 幂等：建常驻层、启动四台机器
    machines.forEach { it.progress(dt) }
    animatable.animController.physTick()  // 推进时间与权重
```

三个判据：

1. **模型就绪** —— 当前 `ModelInstance` 非空且骨骼姿态非空。这一条与 `MechaAnimatable` 既有的模型补齐逻辑同源。
2. **物理级别就绪** —— 取值前必须能判定，因为 `getPhysicsLevel()` 在字段为空时抛异常（§0.1 的「物理级别未就绪时的行为」行）。首版用捕获异常的方式判断，并向上游提出一个可空或可查询的入口以便去掉异常控制流。
3. **动画集未失效** —— 常驻实例持有的动画对象必须仍属于当前动画集。判据是 `OAnimationSet.ORIGINS` 中该模型索引对应的集合对象引用与上一次记录的不同（§0.1 的「内容包重载会清空动画集」行说明重载会清空并重填）。命中即整体重建：清空所有层 → 重建 `ModelInstance` → 重新起常驻层与状态机。

### 4.6 姿态状态机

四台机器，每台一图，共用同一种骨架：一个 `inactive` 初态 + 若干活跃态。所有转移都是 `event == null` 的每步自动求值（§0.1 的「图的两种转移」行），条件用 `CheckVariableCondition` 读共享的 `variables`（§0.1 的「硬编码条件的载体」行）。四台机器每步都被推进，靠各自 `inactive` 实现互斥。

**节点命名口径**：节点名取自它要播的动画语义，而非 gait 名——因为动画数量少于 gait 数量，两者不是一一对应。

**STAND**（四个活跃态）：

| 节点 | 进入条件 | 该态动画 |
|------|----------|----------|
| `inactive` | `!IS_STANDING` | — |
| `idle` | `IS_STANDING && (IS_IDLE \|\| IS_DRIFTING)` | `idle` |
| `move` | `IS_STANDING && (IS_CREEPING \|\| IS_JOGGING)` | `walk` |
| `sprint` | `IS_STANDING && IS_SPRINTING_G` | `run` |
| `hit` | `IS_STANDING && IS_STUNNED` | `attacked` |

`IS_DODGING` 与 `IS_HARD_LANDING` **不设节点**：这两个 gait 在资源里没有对应动画，若为它们设节点，`PlayAnimAction` 会因找不到动画而跳过（§0.1 的「广播式状态机的行为」行），结果是状态切过去但画面停在上一段动画的中途，反而不如让机器停在前一个节点继续播。取舍是这两个 gait 期间沿用进入前的动画。`IS_DODGING` 的时长由既有逻辑层的 `DODGE_DURATION` 界定，表现层不重复计时。

**AIR**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IS_AIRBORNE` | — |
| `fall` | `IS_FALLING \|\| IS_JUMP_BOOSTING` | `jump` |
| `glide` | `IS_GLIDING` | `elytra_fly` |
| `fly` | `IS_HOVERING \|\| IS_FLYING` | `fly` |

`IS_JUMP_BOOSTING` 与 `IS_FALLING` 合并到一个节点：资源里只有一个 `jump` 动画，没有上升 / 下落两套，因此细分段留到 §D2 预留口接线之后再做。

**WATER**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IN_WATER_POSTURE` | — |
| `float` | `IN_WATER_POSTURE && IS_IDLE` | `swim_stand` |
| `swim` | `IN_WATER_POSTURE && !IS_IDLE` | `swim` |

**CROUCH**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IS_CROUCHING` | — |
| `idle` | `IS_CROUCHING && IS_IDLE` | `sneaking` |
| `move` | `IS_CROUCHING && !IS_IDLE` | `sneak` |

四台机器都带一条共同的保底转移：**当所在姿态失配而当前节点不是 `inactive` 时，先回 `inactive`，再由 `inactive` 重新进入匹配节点**。这样姿态切换时不会残留上一个姿态的动画实例。

`inactive` 节点的进入动作是「停止本机追踪的动画实例」。`MultiAnimStateMachine.onExit` 负责退出当前节点的实例，因此这一步由引擎完成，不需要额外动作。

**不做的姿态**：`PRONE`（资源里没有卧倒动画，机器只会常驻 `inactive`）、`RIDING`（骑乘的输入抑制与上下载具尚在验收阶段）、`RAGDOLL`（物理接管，无动画输出）。

### 4.7 动画名映射与缺失回退

映射表集中在 `MechaAnimPreset`，形态是「姿态状态 → 动画名」。当前映射即 §4.6 各表的第三列，全部命中 §0.3 的清单。

资源侧缺失的动画有三处：`IS_DODGING` / `IS_HARD_LANDING`（STAND 的取舍见 §4.6）、`PRONE` 整台机器。三处的处理都是「不播」，不需要写回退逻辑：`PlayAnimAction` 在找不到动画时静默跳过（§0.1 的「广播式状态机的行为」行），三级回退的第二、三级（素体与内置动画集）在首版都传 `null`。

### 4.8 常驻并行动画层

每个槽位一个独立层（D5）。启动方式：在 `ensureStarted()` 里对每个**存在**的槽位动画名调用一次播放，实例参数为「本层号、权重 1、进出场过渡时长 0」；启动一次即完成，不需要每步干预——动画自身的循环设置让它持续播放，永不结束。

两个实现细节：

1. **槽位缺失要静默跳过**。查找动画用返回可空值的辅助函数，不要用找不到即抛异常的构造器（§0.1 无对应行，见 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/anim/AnimInstance.kt#AnimInstance` 的两个构造）。由 §0.3 清单，`pre_parallel2`~`pre_parallel7` 在资源里是空占位，将来替换资源包时也可能整体缺席。
2. **实例表要参与 §4.5 的重启**。它们与姿态机器的实例同寿命，动画集失效时一并清空重建。

首版接入槽位 0 与 1（`pre_parallel0`、`pre_parallel1`），层号 `-8` 与 `-7`。

### 4.9 拆除

拆除路径有三条：装配体注销（注册表淘汰）、退出世界、内容包重载（§4.5 第 3 条判据）。三条都必须**先清空所有层再丢弃引用**：`AnimInstance` 在层里持有动画对象，直接丢引用会让它成为孤儿（§0.1 的「内容包重载会清空动画集」行）。清空用 `AnimController` 的停止全部动画入口，随后释放 presenter。

客户端实例的持有者由 `MechaPlayerRenderer` 的静态表迁移到 presenter 内部（§4.4），因此淘汰判据沿用该表既有的「注册表里查不到即丢弃」。

## 5. 不变量

以下三条要写进 `MechaControl` 与 `ArmsCore` 的 Javadoc，作为后续改动的边界。

1. **客户端实例没有身体、没有权威。** 客户端的 `MechaControl.body` 恒为 `null`，不推进逻辑状态机、不施力、不写刚体、不产生任何上行状态。
2. **客户端的逻辑四项只能来自下行通道。** `variables` 里的 `POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 及其 one-hot 派生由 §4.1.3 的通道写入，不得由客户端本地的任何状态机推导。
3. **表现层是单向消费者。** 它只读 `variables`、只驱动动画与表现层自身的物理对象（§8.4），不写任何会被回传服务端的量。

## 8. 已知缺口与后续

### 8.1 `parallel*` 的加性叠加层

引擎的加性模式没有调用者（§0.1 的「加性模式未被使用」行），因此这条路径未经实战验证。语义上还有一处与资源来源的差异需要验证：加性模式对位置做加法、对缩放做插值式混合，而资源里的 `parallel0` 只驱动缩放、`parallel2` 与 `parallel3` 只驱动旋转（§0.3 清单），三者都不驱动位置，因此按现有资源不会踩到位置通道的语义差异；若将来内容包提供驱动位置的并行动画，需要单独确认。

层号取 32（高于 `OVERRIDE` 的 16），一槽位一层，每层显式设为加性模式（§0.1 的「加性模式未被使用」行指出该属性当前全仓库无人赋值）。

### 8.2 `parallel1_1` 与 `parallel1_2` 的物理模拟链路

`parallel1_1` 没有任何骨骼，只有 timeline，作用是逐步写入物理模拟所需的变量；`parallel1_2` 是把模拟结果烘焙成的姿态。这条链路依赖资源来源方特有的数学函数命名空间，而引擎侧的变量桥只有 `variable.*` / `v.*` 与 `query.*` / `q.*`（§0.1 的「MoLang 变量桥的命名空间范围」行），没有该命名空间。接入的前提是先在引擎侧提供对应的函数绑定，否则播出来的是静止姿态。

### 8.3 内容包的 JSON 入口

本计划的映射表集中在 `MechaAnimPreset`（§4.4），就是为了让「内容包提供 `animation_controllers` 以替换姿态选择」这一步只需换掉图的来源，不动状态机与层结构。姿态机器的载体已经选了广播式（D3），届时不改图结构。

### 8.4 关键帧驱动的部件刚体

表现层归 `MechaControl` 的动因之一（D1）。所需的前置是客户端侧的表现层物理对象与 §D2 预留口的镜像值；本计划不设计这一部分的具体形态，只保证其落点存在。

## 9. 未决问题

1. **物理级别就绪的判据。** 首版用捕获异常规避 `getPhysicsLevel()` 的抛异常行为（§0.1 的「物理级别未就绪时的行为」行），属于用异常控制流。是否请上游提供一个可空或可查询的入口，需要决定。
2. **`pre_parallel` 槽位段的层号取值。** 本计划取 `-8`~`-1`（D5）。负数层号在引擎里合法（层号只是排序键），但可读性不如正数；替代方案是向上游提请在 `AnimGroups` 里开一段低位区间。
3. **姿态切换时的混合时长。** 四台机器的 `PlayAnimAction` 需要一个进出场过渡时长参数，本计划未定值；它决定姿态切换是硬切还是渐变，需要在实机上定。
4. **`IS_JUMP_BOOSTING` 与 `IS_FALLING` 是否长期合并。** 合并的理由是资源只有一个 `jump` 动画（§4.6）。若后续资源提供上升 / 下落两套，拆分需要 `VERTICAL_SPEED`，即 D2 预留口。
5. **`inactive` 是否要停动画。** §4.6 依赖引擎在节点退出时退出实例。若实机观察到姿态失配后仍有残留骨骼停在中途，需要在 `inactive` 的进入动作里补一次显式停止——但 `MultiAnimStateMachine` 只支持 `PlayAnimAction`（D3），届时的做法需要另行设计。
