### 0.4 由基线得到的三条结论

**结论 A：表现层首版不需要角色控制器的任何状态量。** 由 §0.1 与 §0.2 两张表的对应关系：角色控制器只产出 `ON_GROUND` / `SPEED` / `VERTICAL_SPEED` / `KCC_JUMP_BOOSTING` 四项（§0.2 的「变量容器的写入来源」行）；逻辑层状态图消费其中三项（§0.2 的「逻辑层状态图读到的变量」行），产出的结论是 `POSTURE` / `GAIT` / `VERTICAL`（§0.2 的「逻辑状态快照的产出方向」行）；而这三项已经在同步字段里（§0.2 的「四项逻辑状态已在下行通道里」行）。表现层的选片只需要这三个枚举，因此与角色控制器无直接依赖。

**结论 B：驱动必须按物理子步，不能按游戏刻。** 由 §0.1 的「时间推进的单位」行与「客户端也有物理线程」行，客户端 `tps = 60` 而游戏刻是 20 Hz；`AnimInstance` 每调用一次 `physTick()` 只推进 `1/60` 秒，所以每游戏刻调用一次会让动画以 `1/3` 速度播放，同时让 `progress(dt)` 里以秒为单位的驻留时长判据差 3 倍。注意「按物理子步驱动」不等于「按 60 Hz 恒定推进」：§0.1 的「物理步数会自适应降频」行说明每 tick 的步数在客户端会降到 1，此时动画的实时播放速度随之变慢，这是引擎的既有性质，不在本计划的范围。

**结论 C：并行动画取「一槽位一层」，理由是按层操作的语义，不是数值上的必要。** 由 §0.1 的「层内多动画的混合口径」行，阶段 0 的 B 项已把层内分母收口为「含该骨骼的参与实例权重和」并与层权重同源，因此同一层里放两个实例时，只在其中一个出现的骨骼**不再**被缩小——`pre_parallel0` 与 `pre_parallel1` 交集的 2 个骨骼（§0.3 第 2 条）也就不再折半，同层与分层在数值上等价。本计划仍取「一槽位一层」：槽位与层一一对应之后，按层操作（§4.9 的 `stopAnimation` / `stopAllAnimation`）才有确定的语义。姿态机四台共用一层（D3）同理。

## 1. 目标与非目标

**目标**

1. 素体动画在客户端按物理子步推进，姿态由一组硬编码状态机选择，且状态机的输入是服务端权威的 `POSTURE` / `GAIT` / `VERTICAL`。
2. 表现层编排归 `MechaControl`，使其在客户端也有实例——因为表现层后续会承载实际游戏性逻辑（关键帧驱动的部件刚体，§8.4），不适合挂在渲染适配器上。
3. `pre_parallel*` 以常驻循环层的形式接入。

**非目标**

1. 覆盖层与武器本地状态机（动画清单里 `use_mainhand` / `use_offhand` / `swing_hand` 一类）。
2. `parallel*` 的加性叠加层（§8.1）。
3. 内容包以 `animation_controllers` JSON 替换或接管姿态选择（§8.3）。
4. 姿态与碰撞体轮廓的联动（胶囊换形属角色控制器的范围）。

## 2. 架构决策

### D1 表现层编排归 `MechaControl`，客户端也构造它

**决策**：表现层的容器使用者、状态机集合、常驻层与就绪守卫由 `MechaControl` 持有；客户端分支同样构造 `MechaControl`，其 `body` 为 `null`。

**理由**：表现层后续要承载关键帧驱动的部件刚体（§8.4），那是编排与游戏性逻辑，不是渲染细节；把它放在 `MechaAnimatable` 里会让一个自述为「渲染适配器、装配体落地后整体删除」的类承担长期职责。而 `MechaControl` 已经具备表现层所需的全部设施：变量容器、事件 latch、以及「主线程发布 / 物理线程帧首读取」的快照模式（§0.2 的「跨线程发布快照的既有模式」行）。

**代价**：`ArmsCore` 的类 Javadoc 写有「客户端不运行控制器与状态机」，本计划落地后该表述与实际不符，需按 §5 的三条不变量改写。

### D2 客户端对角色控制器的依赖：不建刚体，预留镜像口

**决策**：客户端 `MechaControl` 的 `body` 为 `null`，不建 `MechaCharacter`；客户端不推进逻辑状态机，`POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 由下行通道写入。同时预留一个「角色控制器镜像」的写入位置，首版留空实现。

**理由**：由结论 A，首版表现层不需要角色控制器状态量，因此不建刚体的成本是零。反过来，客户端本地建刚体会**破坏权威一致性**：客户端的输入与地形权威都不存在，着地判据在台阶与边缘处与服务端不同，于是同一个 `GAIT` 会在两端算出不同值，表现层跟着播不同动画——这比一个网络往返的延迟更难排查。此外客户端物理级别按 §0.1 的「物理步数会自适应降频」行会降步，本地刚体的 `onGround` 与速度会抖动。

**预留口的意义**：将来表现层需要按 `VERTICAL_SPEED` 细分上升 / 下落段，或需要 `ON_GROUND` 做表现层判定时，只需追加同步字段并在该处填入镜像值。其中 `SPEED` 与 `VERTICAL_SPEED` 可由已经在同步的 `DATA_VEL` 推出，无需新增字段（§0.2 的「四项逻辑状态已在下行通道里」行）。

**遗留代价**：动画对状态变化的响应比服务端晚一个上行往返（服务端物理步 → 主线程写同步数据 → 广播 → 客户端接收）。离散状态切换上表现为延迟而非错误。

### D3 状态机载体用 `MultiAnimStateMachine`

**决策**：姿态状态机用 `MultiAnimStateMachine`，`animTargets` 传单元素列表，`animGroup` 传 `AnimGroups.LOCOMOTION`，`variables` / `tags` 传 `MechaControl` 的那一对。

**理由**：装配体由多个 `SubPart` 组成，逐零件渲染落地后 `animTargets` 需要扩成多元素列表；现在就选广播式载体，届时不改图结构。附带收益是三级动画回退可用（§0.1 的「广播式状态机的行为」行）。传共享容器是硬要求：§0.1 的「共享变量容器决定 `reset` 是否清空」行说明传 `null` 会自建空容器，条件便读不到逻辑层写入的值。

**代价**：`MultiAnimStateMachine` 上只有 `PlayAnimAction` 有效，`StopAnimAction` / `MoLangAction` / `SoundAction` / `ParticleAction` 在它上面会告警并跳过（§0.1 的「状态机退出节点回收实例」行末段给出原因）。本计划的图只用 `PlayAnimAction`，不受影响；需要「停某个层」时改用自定义的 `StateAction`（`StateAction` 是接口，实现它并返回 `MapCodec.unit(this)` 即可）。

### D4 驱动点双端共用 `PhysicsLevelTickEvent.Pre`

**决策**：把服务端侧已有的物理步扇出改为双端共用：去掉 `level.isClientSide()` 提前返回，对客户端 Level 也遍历注册表调用 `ArmsCore.prePhysicsTick(dt)`。客户端的 `dt` 由同一个 `1f / tps` 公式得出（服务端 100，客户端 60）。

**理由**：只需一处改动即可满足结论 B（按物理子步驱动）。客户端物理级别已存在（§0.1 的「客户端也有物理线程」行），注册表已支持客户端 Level（§0.2 的「注册表双端可用」行），`ArmsCore.prePhysicsTick` 已对 `mechaControl == null` 提前返回。

**代价**：承载它的 `ArmsCoreServerEvents` 类名与类注释都只描述服务端，落地时需一并改名或改写其 Javadoc（§6 阶段 5）。

### D5 层号：并行动画一槽位一层，层号取本项目私有的一段

**决策**：`pre_parallel` 槽位 N 直接用 `AnimGroups.persistent(N)`，即八个槽位落在 `-8`~`-1`，全部低于 `AnimGroups.AMBIENT`（1）；槽位越界时该函数直接抛 `IllegalArgumentException`，越界因此在构造期就暴露，不需要本项目自己再夹一次范围。姿态机器继续用 `AnimGroups.LOCOMOTION`（2）。

**理由**：由结论 C 需要一槽位一层；而 Spark-Core 的层号是 2 的幂（§0.1 的「现存层号」行），低于 `AMBIENT` 的可用整数只有 0 与负数，因此取一段负数作为槽位段。层号只是 `Int` 键，引擎不对其取值域作假设。

### D6 两处引擎缺陷已在 Spark-Core 侧修掉，不在本项目侧绕

**状态：已落地**（`../Spark-Core` 提交 `0e42ec5c`，2026-10-14）。本计划依赖的两条修正与两项设施都已就位，D6 保留在本文是为了记录「为什么这几条不能在本项目侧绕」——后续若有人想把它们改成下游补偿，这里是反对理由。

**决策**：本计划依赖的 Spark-Core 修正，作为阶段 0 先行：

1. **状态机退出节点时回收动画实例。** 由 §0.1 的「状态机退出节点回收实例」行与「实例离开层的唯一路径」行，`PlayAnimAction` 放进层的**循环**动画在节点被离开之后本会永久留在层里，而姿态机播的动画全是循环的（§0.3 表里 `idle` / `walk` / `run` / `sneak` / `sneaking` / `jump` / `fly` / `elytra_fly` / `swim` / `swim_stand` 十者皆为循环）。不修它，四台机器共用 `LOCOMOTION` 层时每切一次节点该层的实例数就 +1，同层混合口径随之把折半系数变成 1/3、1/4，模型会逐次塌缩。**阶段 4 的实机验收里「`LOCOMOTION` 层实例数恒为 1」这一条（§6）就是它的回归判据，请保留。**
2. **`AnimLayer.blendBone` 的位置 / 缩放按参与实例归一。** 同上第一条的「层内多动画的混合口径」行，交叉淡化的过渡期内新旧实例同层共存，两个动画的独占骨骼本会被压一次（过渡时长由 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/anim/AnimInstance.kt#inTransitionTime` 与 `#outTransitionTime` 决定，默认 0.15 s）。

**理由**：这两条在本项目侧都没有可用的绕法。第一条：`StopAnimAction` 在 `MultiAnimStateMachine` 上不可用（§0.1 的「状态机退出节点回收实例」行），而 `stopAnimation(group)` 会连别的机器刚起的实例一起停掉（四台机器共用 `LOCOMOTION`）。第二条：只要层内可能同时存在两个实例就会发生，而交叉淡化本身就会产生这种状态。此外两条都不是本项目特有的口味——它们影响 Spark-Core 自己的两个内置预设（`PlayerBaseAnimStateMachine#playRelativeAnim` 与 `EntityBaseUseAnimStateMachine#onStateEntry` 都在手动补偿第一条，上游文档 §1.6 说明这两处不在修正覆盖范围内、补偿必须保留）、影响 `../Machine-Max` 直接持有 `AnimInstance` 的两处（`FabricatorBlockEntity#updateState` 只调 `enter()` 从不调 `exit()`，且它的 `workAnim` / `idleAnim` 都没赋值 `group`，因此同层共存、第二条直接生效），也影响任何内容包的 `animation_controllers`。在本项目侧绕开等于把引擎缺陷固化到下游。

**代价**：阶段 0 曾落在 `../Spark-Core`，与 `../Machine-Max` / `../BallisticsFramework` 共用复合构建，改动前后要跑 `Spark-Core` 自己的测试与 `../Machine-Max` 的构建——这一步已经做完。剩下的是复合构建的常规风险：上游再动这几处时，本项目要跟着复测。

**改动清单与验收用例的坐标**：`../Spark-Core/docs/anim_layer_blend_and_state_exit_plan.md` 的 §1（缺陷 A）、§2（缺陷 B）、§3（顺带项 C、D）与 §4（验证）。本文只依赖 §0.1 列出的那几条事实，不依赖那份文档的其它结论。

## 3. 分层与职责

表现层引入后，一个骨骼的最终姿态由下列层按层号升序叠加得出。表中「首版」列标出本计划填内容的层。

| 层号 | 层 | 写入者 | 混合模式 | 首版内容 |
|-----:|----|--------|----------|----------|
| `-8` ~ `-1` | `pre_parallel` 槽位 0~7 | 每槽位一个常驻 `AnimInstance` | 覆盖 | 槽位 0、1 |
| 1 | `AMBIENT` | 未使用 | 覆盖 | — |
| 2 | `LOCOMOTION` | 四台姿态状态机 | 覆盖 | STAND / AIR / WATER / CROUCH |
| 4 | `POSTURE` | 覆盖层（持物、瞄准、骑乘） | 覆盖 | 非目标 |
| 8 | `ACTION` | 覆盖层（挥动、使用、开火） | 覆盖 | 非目标 |
| 16 | `OVERRIDE` | 强制覆盖（死亡、布娃娃） | 覆盖 | 非目标 |
| 32 | `PARALLEL` | 槽位 0~7 各一层 | 加性 | §8.1 |

层的覆盖是**按骨骼**生效的：某一层若没有任何实例驱动某骨骼，该骨骼在本层取不到值，于是低层的值保留。这解释了为什么 `pre_parallel0` 的那 52 个模型内独占骨骼会显现（§0.3 第 1 条），也解释了为什么姿态机器必须真的播一个动画，而不能"不播以保留底层"。

同一条按骨骼的规则还有第二个后果，需要在验收时区分：**一个动画在整段播放期间只驱动它自己的那批骨骼**，其余骨骼在本层取不到值，于是落回绑定姿态。§0.3 的表里各动画的「模型内」骨骼数差得很大（`elytra_fly` 20、`jump` 20、`sneak` 19、`idle` 15、`fly` 13），所以姿态切换时被覆盖的骨骼集合会跟着变，表现上是一部分骨骼回到绑定姿态。这是资源的骨骼覆盖范围决定的，也受 §0.3 第 3 条（动画文件按更完整的模型导出）影响；要消除它得让同一姿态级的动画驱动同一批骨骼，属内容侧的事。

## 4. 详细设计

### 4.1 `MechaControl` 双端化

三处改动。

**4.1.1 构造与权威分支**

构造参数中 `body` 改为可空。新增一个判定方法（如 `hasBody()`）作为权威分支的开关，取值为 `body != null`。`ArmsCore` 的构造分支由「客户端不建 `MechaControl`」改为「客户端建 `MechaControl(this, null)`」，服务端分支不变（仍在 `authoritative` 为真时读物理空间建刚体）。

客户端构造 `MechaControl` 时还有一处必须处理：由 §0.2 的「构造即启动逻辑状态树」行，构造器末段的 `logicStateMachine.reset()` 会把 `POSTURE` 与 posture 的 one-hot 写进 `variables`，且发生在构造线程（客户端即主线程）。这违反 §5 的不变量 2，也与「`variables` 由物理线程独占」的既有约定冲突。两条可选处理，实施时二选一并在代码注释里写明选择：

- 客户端分支不构造、不启动逻辑状态树（`logicStateMachine` 置 `null`，`snapshotLogicState` 一类方法在客户端不可用）；
- 或保留构造但把启动推后到首次物理步，让写入与后续的物理线程写读同属一个线程。

首版取前一条：客户端不推进逻辑状态机（D2），因此它不需要这棵树。

**4.1.2 物理步分段**

`onPhysicsStep(dt)` 按顺序分四段，权威调用用 `hasBody()` 包住，**下行状态写入放在 `hasBody()` 之外**：

```
onPhysicsStep(dt):
    applySyncedLogicState()                   // 下行通道：从 volatile 字段把四项及 one-hot 写进 variables
    if (hasBody()) frameLogic(dt)             // 汇入快照与刚体状态 → 推进逻辑树 → 产出回写 → 转发输入
    presentation().progress(dt)               // 表现层：状态机推进 + 动画时间推进
    if (hasBody()) { extractAnimRootDelta(); body.prePhysicsTick(dt) }
```

第一行必须在这两个位置之外，否则客户端的 `variables` 里永远是 `StateVariableKey` 的默认值（`IS_STANDING` 与 `IS_IDLE` 的默认都是 `true`），四台机器会全部停在 STAND.idle 而不报任何错。表现层推进的位置沿用 §0.2 的「物理步主流程」行给出的空档（`frameLogic` 之后、`extractAnimRootDelta` 之前），不改变既有的权威侧顺序。

**4.1.3 下行状态通道**

新增一对方法，与 `applyConditionSnapshot` / `conditionSnapshot` 同构（§0.2 的「跨线程发布快照的既有模式」行）：主线程用 `applySyncedLogicState(LogicStateSnapshot)` 发布到一个 volatile 字段，物理线程在帧首用该字段把 `POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 写进 `variables`。

one-hot 的派生不要另写一份逻辑：§0.2 的「枚举 → one-hot 的写入动作已存在」行给出的 `MechaStateActions.postureFlags` / `gaitWithModifier` / `verticalFlags` 就是「枚举 → 枚举 + 全部 one-hot」的现成实现，它们只依赖 `controller.getVariables()`，客户端按同一个口径填入即可。`gaitPreservingModifier` 不写 `MOVE_SPEED_MODIFIER` 的口径也一并沿用（客户端不用这个倍率）。

同一 record 在这条通道上两个方向的语义相反，需在 Javadoc 里写明：服务端方向是**产出**（`snapshotLogicState()` 从容器读出，供主线程写同步数据），客户端方向是**输入**（从同步数据写入容器）。

### 4.2 客户端主线程投影

客户端的 `LevelTickEvent.Post` 分支（由 D4 的接线决定它落在哪个订阅者里——`ArmsCoreServerEvents` 未标注 `Dist`，因此双端都注册，`common/ArmsCoreServerEvents.java#onPostTick`）做三件事：从同步数据读 `DATA_POSTURE` / `DATA_GAIT` / `DATA_VERTICAL` / `DATA_ENERGY`；用新增的 `fromMolangName(String)` 把三个字符串翻成枚举（§0.2 的「三个枚举只有单向换算」行指出目前只有单向换算）；组装 `LogicStateSnapshot` 后调用 `applySyncedLogicState`。record 的 `equals` 可用于抑制同值发布。

### 4.3 客户端物理线程驱动

由 D4，客户端侧不需要新增订阅者。`ArmsCore.prePhysicsTick` 增加一个客户端分支：**跳过逻辑状态快照的发布**（客户端不从容器反推状态，它的状态来自 §4.2 的投影），其余步骤共用。表现层的推进由 `MechaControl.onPhysicsStep` 内部完成（§4.1.2），因此这一层不需要额外接线。

### 4.4 表现层编排

新增 `common/control/presentation/` 包，内容如下。

| 文件 | 职责 |
|------|------|
| `MechaAnimPresenter` | 编排。持有**注入进来的** `List<IAnimatable<?>>`、四台姿态状态机、常驻层实例表、就绪守卫与拆除逻辑 |
| `MechaPresentationGraphs` | 四张姿态图的纯数据常量（`StateMachineGraph`） |
| `MechaAnimPreset` | 动画名常量与「姿态状态 → 动画名」的映射表（把映射集中一处，便于将来由内容包替换，§8.3） |
| `MechaAnimGroups` | 本项目私有的层号常量（D5；`pre_parallel` 段直接复用 `AnimGroups.persistent`，本类只放姿态机那一条的语义别名） |

**`MechaAnimatable` 留在 `client` 包（与 `ClientMechaAnchor` 一起）；presenter 只认 `IAnimatable<?>`。**

presenter 持有的不是 `MechaAnimatable` 而是 `List<IAnimatable<?>>`，由外部注入。选这个类型的理由是它正是 `MultiAnimStateMachine.animTargets` 的类型（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/state/MultiAnimStateMachine.kt#animTargets`），而 `IAnimatable` 与 `Part` **都在 common 包**：

- `IAnimatable` 在 `cn.solarmoon.spark_core.animation`（Spark-Core 的公共包，非 Dist 专属）；
- `Part implements IAnimatable<Part>`，位于 `../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/Part.java#Part`——common 包。

因此 `MechaControl`（common）持有 `List<IAnimatable<?>>` 不需要引用任何客户端类型，D1「把表现层编排收进 `MechaControl`」这一步不受阻碍：`MechaAnimatable` 与 `ClientMechaAnchor` 留在 `client` 包即可，presenter 不引用它们。

一处订正备用：`SubPart extends DestroyableRigidObject implements ISubsystemHost`（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#SubPart`），**不是** `IAnimatable`。`MechaControl` 里那批 TODO 注释写的是「挂在各 SubPart 的 AnimController 上」，将来别照抄——动画目标是 `Part`。

**注入点的两套来源，切换时不改 presenter：**

| 期 | 注入者 | 注入内容 |
|----|--------|----------|
| 首版（Part 未接入） | 客户端主线程（`MechaPlayerRenderer.onClientTick`，§0.2 的「客户端动画体的持有与驱动」行） | 单元素列表 `[mechaAnimatable]` |
| Part 装配落地后 | 装配体（`ArmsCore`，按 `IPartAssembly` 追溯 partNet） | 全体 `Part` 的动画体列表 |

注入做成幂等的 `attach(List<IAnimatable<?>>)`：客户端 tick 第一次遍历到该装配体时注入一次，之后不变。`ensureStarted()` 在物理线程、可能早于注入发生，因此 §4.5 的守卫要显式判「至少一个目标」。

**`MechaAnimatable` 是首版唯一的验收载体，不能因为它是占位就跳过接线。** `ArmsCore` 的 `IPartAssembly` 实现目前全是空壳（`getRootSubPart()` 返回 `null`，`addPart` 空实现），因此现在没有任何 `Part` 可注入；而阶段 1~4 的验收（下行通道、常驻层、姿态机选片）全部要在实机上看到画面才算数。它自述为「装配体落地后整体删除」，但删除的时机是 Part 接入，不是现在。

`MechaPlayerRenderer` 的 `clientTick` 保留主线程那三件事（§0.2 的「主线程 `clientTick` 做三件事」行）——同步位姿采样、模型补齐、`AnimController.tick()`；物理线程那一半（时间与权重推进）由 presenter 的 `progress()` 承担。这是 Spark-Core 自身的分工（`physTick` 在物理线程、`tick` 在主线程，§0.1 的「实例的生命周期」行），不是本项目的取舍。渲染侧的静态映射表 `ANIMATABLES` 也留在 `MechaPlayerRenderer`，不随 presenter 搬家（§4.9 的拆除清单因此少一条）。

### 4.5 就绪守卫与重启

三个就绪条件相互独立、到达顺序不保证（§0.1 的「客户端拿到动画集的时点由网络决定」行说明动画集可能晚于装配体创建包到达）：客户端实例出现、内容包读取完成（`OModel.ORIGINS` 与 `OAnimationSet.ORIGINS` 有内容）、客户端物理级别建立。守卫写成幂等入口，`MechaControl.onPhysicsStep` 每步调用一次：

```
presentation().progress(dt):
    if (!ready()) return
    ensureStarted()                                    // 幂等：建常驻层、启动四台机器
    machines.forEach { it.progress(dt) }
    targets.forEach { it.animController.physTick() }   // 推进时间与权重，按目标逐个推进
```

最后一行是**按目标遍历**而不是推进单个动画体：`MultiAnimStateMachine` 只负责在各目标上起实例，不负责推进各目标的控制器（§0.1 的「广播式状态机的行为」行），因此 presenter 必须自己走一遍 `targets`。首版 `targets` 是单元素（§4.4），写成遍历是为了让 Part 装配落地后不用改这里。

三个判据：

1. **目标已注入且模型就绪** —— `targets` 非空，且每个目标的 `ModelInstance` 非空、骨骼姿态非空。这一条与 `MechaAnimatable` 既有的模型补齐逻辑同源（§0.2 的「主线程 `clientTick` 做三件事」行）。判据**落在目标粒度**：某个目标没好不该拖累其余目标，因此实现上按目标过滤而不是整体 `return`。
2. **物理级别就绪** —— 用 `LevelPatch.getPhysicsLevelOrNull()` 判空（§0.1 的「物理级别未就绪时的行为」行），不要捕获 `getPhysicsLevel()` 的异常：后者在字段为空时抛 `IllegalStateException`，用它做流程控制既慢又会把真正的初始化错误吞掉。
3. **资源对象未失效** —— 常驻实例持有的动画对象、以及 `ModelInstance.pose` 里的骨骼对象，都必须仍属于当前资源集。判据取「`OAnimationSet.ORIGINS` 与 `OModel.ORIGINS` 中该模型索引对应的对象引用与上一次记录的不同」：§0.1 的「内容包按类型 + 目录名归并」行说明重载会先 `clear()` 再重填，因此重载后取到的是新对象。**两个 ORIGINS 都要判**——只判动画集的话，模型文件被替换而动画文件没变时，姿态里留着的仍是旧骨骼。命中即整体重建：清空所有层 → 重建 `ModelInstance` → 重新起常驻层与状态机。

模型的重建只有这一条路：既有的 `refreshModelIfNeeded` 的判据是「当前姿态没有骨骼而模型表里有本模型」，而重载后旧姿态仍然有骨骼，因此它不会触发（§0.2 的「主线程 `clientTick` 做三件事」行）。实施时把重建的触发点收敛到这一处，避免主线程与物理线程各有一套。

### 4.6 姿态状态机

四台机器，每台一图，共用同一种骨架：一个 `inactive` 初态 + 若干活跃态。所有转移都是 `event == null` 的每步自动求值（§0.1 的「图的两种转移」行），条件用 `CheckVariableCondition` 读共享的 `variables`（§0.1 的「硬编码条件的载体」行）。四台机器每步都被推进，靠各自 `inactive` 实现互斥。

**节点命名口径**：节点名取自它要播的动画语义，而非 gait 名——因为动画数量少于 gait 数量，两者不是一一对应。

**条件的互斥性**：除 STAND 的 `inactive → idle` 兜底条之外，各表的条件两两互斥（都源自同一步写入的枚举 one-hot 组合），因此 `autoTransitions` 的排列顺序不影响结果。兜底条与同表的其它出边**不互斥**，靠排在最后来保证只在没有更具体的分支成立时才命中（见 STAND 的边表）。

**条件是按边给的，不是按节点给的。** `StateTransition(target, condition)` 的粒度是边（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/state_machine/graph/StateTransition.kt#StateTransition`），同一个目标节点从不同来源可以挂不同条件。下面四台的表格一律按「源节点 → 出边列表」给出；同一源节点的多条出边按表格顺序排列，`node.autoTransitions.firstOrNull` 取第一条成立的（§0.1 的「图的两种转移」行）。各条条件两两互斥（都源自同一步写入的枚举 one-hot），因此顺序只在不互斥的那几处有意义，届时单独点明。

**STAND**（三个活跃态，`inactive` → `idle` / `move` / `sprint`）：

| 源节点 | 出边（按求值顺序） | 该节点动画 |
|--------|------------------|------------|
| `inactive` | `→ sprint`（`IS_SPRINTING_G`）、`→ move`（`IS_CREEPING \|\| IS_JOGGING`）、`→ idle`（`IS_STANDING`，兜底） | — |
| `idle` | `→ sprint`（`IS_SPRINTING_G`）、`→ move`（`IS_CREEPING \|\| IS_JOGGING`）、`→ inactive`（`!IS_STANDING`） | `idle` |
| `move` | `→ sprint`（`IS_SPRINTING_G`）、`→ idle`（`IS_IDLE`）、`→ inactive`（`!IS_STANDING`） | `walk` |
| `sprint` | `→ move`（`IS_CREEPING \|\| IS_JOGGING`）、`→ idle`（`IS_IDLE`）、`→ inactive`（`!IS_STANDING`） | `run` |

两条设计意图靠这张边表钉住，后续改图时不要顺手改回去：

- **`inactive → idle` 是兜底，条件是裸的 `IS_STANDING`，且必须排在最后。** 它保证「姿态刚变到 STAND、而 gait 恰好是某个未映射值」时机器也能落到有动画的节点，而不是停在 `inactive`（无动画 → 绑定姿态）。典型场景是空中落地：那一刻 `posture` 已成 STAND，而 gait 常是 `DRIFT`。排在最后是因为它与前面两条不互斥。
- **`move` / `sprint` → `idle` 的条件是不含 `IS_DRIFTING` 的裸 `IS_IDLE`。** 于是 DRIFT 期间这两条边不成立，机器留在原节点继续播。`run_idle` 想做的减速收尾因此不需要专门动画：由 gait 子机的滞回自动完成——`DRIFT` 在水平速度降到 `STOP_SPEED_THRESHOLD = 0.05 m/s` 以下时转回 `IDLE`（`common/control/state/preset/GaitSubGraphs.java#STOP_SPEED_THRESHOLD`、`#COND_STOPPED`），进入阈值是更高的 `0.15 m/s`（`#DRIFT_ENTRY_SPEED_THRESHOLD`），两者构成滞回以避免边界抖动。**把 `|| IS_DRIFTING` 加回这两条边会立刻破坏它**，表现为冲刺松手时硬切回站立动画。

**未映射的 gait 一律沿用上一节点的动画，且不需要为它们写任何东西。** `IS_DODGING` / `IS_HARD_LANDING` / `IS_STUNNED` 都不设节点、也不设出边：它们期间 gait 的其余 one-hot 全为假，上表没有任何一条边成立，机器因此停在进入前的那个节点、循环动画继续播。这不是兜底逻辑，而是「没有任何出边」的自然结果，§4.6 各表条件的互斥性保证了这一点。三者的时长都由逻辑层的常量界定（`GaitSubGraphs.java#STUN_DURATION` = 0.8 s、`#DODGE_DURATION` = 0.4 s、`#HARD_LAND_DURATION` = 1.0 s），表现层不重复计时。

**`IS_STUNNED` 曾有 `hit` 节点（播 `attacked`），本计划删掉它**，三条理由：

1. `attacked` 是 `Loop.ONCE`（§0.3 表），0.4583 s；而 stun 的驻留时长是 0.8 s。两者一个由美术资源定、一个由逻辑常量定，没有任何东西保证相等。把 `hit` 留在图里，动画播完到 stun 结束之间的 0.34 s 要么回绑定姿态、要么需要一条基于 `ALL_ANIMATIONS_FINISHED` 的出口（该信号见 §0.1 的「动画完成状态的现成信号」行）。
2. 而那条出口做不出来：stun 期间 `IS_STANDING && IS_STUNNED` 恒为真，`hit` 一旦离开就会在下一步被同一条边拉回来重播 `attacked`，形成自激振荡，一直持续到 `STUN_DURATION` 走完。
3. 受击表现的正确归属是覆盖层（`ACTION` / `OVERRIDE`，§3 的层表），不是姿态层——它是一个动作覆盖，应当压在 `LOCOMOTION` 之上。

`attacked` 资源保留在内容包里，首版不引用（§4.7）。

下面三台仍用「节点 → 进入条件」的紧凑写法：它们的条件已经覆盖所在姿态下的全部取值，且两两互斥，因此按节点与按边等价，不需要 STAND 那套边表。**一个口径差异不是疏漏**：WATER 与 CROUCH 的第二条分支都是裸的 `!IS_IDLE`，它把 `DRIFT` / `DODGE` / `STUN` 一并吃下（水中与蹲下时继续播移动动画），而 STAND 按上面的边表让这三个 gait 沿用上一节点。STAND 之所以要区分，是因为它有三个备选动画可以沿用，而那两台各只有两个、且 `!IS_IDLE` 的那一支本就覆盖「还在动」。

**AIR**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IS_AIRBORNE` | — |
| `fall` | `IS_FALLING \|\| IS_JUMP_BOOSTING` | `jump` |
| `glide` | `IS_GLIDING` | `elytra_fly` |
| `fly` | `IS_HOVERING \|\| IS_FLYING` | `fly` |

`IS_JUMP_BOOSTING` 与 `IS_FALLING` 合并到一个节点：资源里只有一个 `jump` 动画，没有上升 / 下落两套，因此细分段留到 D2 预留口接线之后再做。

**WATER**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IN_WATER_POSTURE` | — |
| `float` | `IN_WATER_POSTURE && IS_IDLE` | `swim_stand` |
| `swim` | `IN_WATER_POSTURE && !IS_IDLE` | `swim` |

**CROUCH**：

| 节点 | 进入条件 | 动画 |
|------|----------|------|
| `inactive` | `!IS_CROUCHING` | — |
| `idle` | `IS_CROUCHING && IS_IDLE` | `sneaking` |
| `move` | `IS_CROUCHING && !IS_IDLE` | `sneak` |

四台机器都带一条共同的保底转移：**当所在姿态失配而当前节点不是 `inactive` 时，先回 `inactive`，再由 `inactive` 重新进入匹配节点**。姿态切换时的实例清理由引擎在节点退出时完成：阶段 0 的缺陷 A 修正已落地，`onExit` 会对已追踪的实例调 `exit()`（§0.1 的「状态机退出节点回收实例」行），出场过渡照常走完，因此 `inactive` 节点的进入动作不需要再做任何事。

**不做的姿态**：`PRONE`（资源里没有卧倒动画，机器只会常驻 `inactive`）、`RIDING`（骑乘的输入抑制与上下载具尚在验收阶段）、`RAGDOLL`（物理接管，无动画输出）。

### 4.7 动画名映射与缺失回退

映射表集中在 `MechaAnimPreset`，形态是「姿态状态 → 动画名」。当前映射即 §4.6 各表的第三列，全部命中 §0.3 的清单。

资源侧缺失动画的情形共四处：`IS_DODGING` / `IS_HARD_LANDING` / `IS_STUNNED`（STAND 的取舍见 §4.6）、`PRONE` 整台机器。四处的处理都是「不播」，不需要写回退逻辑：`PlayAnimAction` 在找不到动画时静默跳过（§0.1 的「广播式状态机的行为」行），三级回退的第二、三级（素体与内置动画集）在首版都传 `null`。

清单里现成但本计划不用的条目，取舍一并写在这里，避免实施时误以为漏了：

| 条目 | 取舍 |
|------|------|
| `run_idle` | DRIFT 期间沿用 `run`（§4.6 的 STAND 边表让 `sprint` 在 DRIFT 时无出边），减速收尾由 gait 子机的滞回自动结束，因此首版不需要它 |
| `run_jump_left` / `run_jump_right` | 冲刺起跳的左右分侧版本，需要区分起跳脚，而刚体侧的起跳不分侧 |
| `death` / `sleep` / `sit` / `boat` / `ride` / `ride_pig` / `climb` / `climbing` / `riptide` | 对应的姿态或状态不在首版范围内（§4.6 的「不做的姿态」与 §1 的非目标） |

### 4.8 常驻并行动画层

每个槽位一个独立层（D5）。启动方式：在 `ensureStarted()` 里对每个**存在**的槽位动画名调用一次播放，实例参数为「本层号、权重 1、进出场过渡时长 0」；启动一次即完成，不需要每步干预——动画自身的循环设置让它持续播放，永不结束。

两个实现细节：

1. **槽位缺失要静默跳过**。查找动画用返回可空值的辅助函数，不要用找不到即抛异常的构造器（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/anim/AnimInstance.kt#AnimInstance` 的两个构造：主构造收已解析的 `OAnimation`，次构造收 `AnimIndex` 并在查不到时抛 `IllegalArgumentException`）。由 §0.3 清单，`pre_parallel2`~`pre_parallel7` 在资源里是空占位，将来替换资源包时也可能整体缺席。
2. **实例表要参与 §4.5 的重启**。它们与姿态机器的实例同寿命，资源对象失效时一并清空重建。

首版接入槽位 0 与 1（`pre_parallel0`、`pre_parallel1`），层号 `-8` 与 `-7`。

`enter()` 是经 `submitImmediateTask` 投到物理线程的（§0.1 的「实例的生命周期」行），而该任务的回执时点在 `PhysicsLevelTickEvent.Pre` 之后（§0.2 的「`submitImmediateTask` 的回执时点」行）。因此在物理步内启动的槽位，其第一个 `physTick()` 发生在下一个物理步，属预期。

### 4.9 拆除

拆除路径有两条：退出世界、资源对象失效（§4.5 第 3 条判据）。两条都必须**先清空所有层再丢弃引用**：`AnimInstance` 在层里持有动画对象，直接丢引用会让它成为孤儿（§0.1 的「内容包按类型 + 目录名归并」行末段说明重载会清空动画集而实例持有的对象不随之更新）。清空用 `AnimController` 的 `stopAllAnimation()`（它与 `stopAnimation(group)` 一样逐个 `exit()`），随后释放 presenter。

**第三条路径（装配体注销）不属于 presenter。** `MechaAnimatable` 的持有者仍是 `MechaPlayerRenderer` 的静态表（`ANIMATABLES`，§4.4），淘汰判据沿用该表既有的「注册表里查不到即丢弃」（`client/MechaPlayerRenderer.java#ANIMATABLES`）。presenter 自己不持有目标的所有权和寿命：它持有的是注入进来的引用，随 `MechaControl` → `ArmsCore` 一起被 GC。淘汰判据需要有人按注册表周期性扫描，而 presenter 没有自己的 tick 入口（它的 `progress` 由物理步驱动，装配体注销后就不再被调用），因此这条扫描落在有客户端 tick 的那一侧。

退出世界那条路径还要覆盖 `MechaCoreRegistry` 的客户端清表（§0.2 的「注册表双端可用」行所在的类里，`onLevelUnload` 已按 Level 清表）。

## 5. 不变量

以下三条要写进 `MechaControl` 与 `ArmsCore` 的 Javadoc，作为后续改动的边界。

1. **客户端实例没有身体、没有权威。** 客户端的 `MechaControl.body` 恒为 `null`，不推进逻辑状态机、不施力、不写刚体、不产生任何上行状态。
2. **客户端的逻辑四项只能来自下行通道。** `variables` 里的 `POSTURE` / `GAIT` / `VERTICAL` / `ENERGY` 及其 one-hot 派生由 §4.1.3 的通道写入，不得由客户端本地的任何状态机推导。落地这一条要把构造期的那次写入一并处置（§4.1.1 末段）。
3. **表现层是单向消费者。** 它只读 `variables`、只驱动动画与表现层自身的物理对象（§8.4），不写任何会被回传服务端的量。

## 7. 验证方式

| 车道 | 能覆盖 | 覆盖不了 |
|------|--------|----------|
| 单元测试 | 下行通道的两个方向互为逆运算；`fromMolangName` 对全部枚举值的往返；四张图的转移在给定变量组合下是否走向预期节点 | 动画是否真的画出来 |
| 实机（`runClient`） | 动画选片、常驻层是否生效、姿态切换是否残留、资源包重载后的重建 | 双端一致性只能靠与服务端同步值比对 |
| 服务端实测 | 权威侧行为未回归 | 客户端表现 |

四张图的用例可以完全脱离物理与资源：用 `StateGraphController` 直接驱动，给 `MultiAnimStateMachine` 传 `animTargets = emptyList()`——`PlayAnimAction.execute` 在 Multi 分支对 `animTargets` 逐元素操作，空列表即零次迭代，天然是 no-op，不会碰到 `AnimInstance.enter()` 里的物理级别投递。**空列表不是可选写法**：`PlayAnimAction` 的 Multi 分支确实会调 `instance.enter()`，而它在持有者没有物理级别时才退化为调用线程（§0.1 的「实例的生命周期」行），带真实目标的图在 JUnit 里会真的去建实例、需要真实资源。

动画的推进是否按 60 Hz 而不是 20 Hz，有一个直接判据：`pre_parallel1` 的动画长度是 5 秒，观察它回到起点的周期。若为 15 秒则说明 `physTick()` 被按游戏刻驱动。周期取值的解释要带上 §0.1 的「物理步数会自适应降频」行——客户端每 tick 的步数会在 1 到 3 之间调整，因此周期会随之在 5 秒到 15 秒之间浮动；要判定驱动频率本身，比较 `PhysicsLevelTickEvent` 的计数与 tick 数的比值更可靠。

## 8. 已知缺口与后续

### 8.1 `parallel*` 的加性叠加层

引擎的加性模式没有调用者（§0.1 的「加性模式未被使用」行），因此这条路径未经实战验证。语义上还有一处与资源来源的差异需要验证：加性模式对位置做加法、对缩放做插值式混合，而资源里的 `parallel0` 只驱动缩放、`parallel2` 与 `parallel3` 只驱动旋转（§0.3 清单），三者都不驱动位置，因此按现有资源不会踩到位置通道的语义差异；若将来内容包提供驱动位置的并行动画，需要单独确认。

层号取 32（高于 `OVERRIDE` 的 16），一槽位一层，每层显式设为加性模式（§0.1 的「加性模式未被使用」行指出该属性当前全仓库无人赋值）。

### 8.2 `parallel1_1` 与 `parallel1_2` 的物理模拟链路

`parallel1_1` 没有任何骨骼，只有 timeline，作用是逐步写入物理模拟所需的变量；`parallel1_2` 是把模拟结果烘焙成的姿态。这条链路依赖资源来源方特有的数学函数命名空间，而引擎侧的变量桥只有 `variable.*` / `v.*` 与 `query.*` / `q.*`（§0.1 的「MoLang 变量桥的命名空间范围」行），没有该命名空间。接入的前提是先在引擎侧提供对应的函数绑定，否则播出来的是静止姿态。

### 8.3 内容包的 JSON 入口

本计划的映射表集中在 `MechaAnimPreset`（§4.4），就是为了让「内容包提供 `animation_controllers` 以替换姿态选择」这一步只需换掉图的来源，不动状态机与层结构。姿态机器的载体已经选了广播式（D3），届时不改图结构。

### 8.4 关键帧驱动的部件刚体 —— 本计划不做，且不会随 Part 接入自动出现

表现层归 `MechaControl` 的动因之一（D1）。**本计划不设计这一部分，也不预留它的落点之外的任何东西。**

要说清一条容易误判的事：`AnimController.physTick()`（§4.5 伪码最后一行）的职责只有**骨骼姿态混合**——它把各层混合结果写进 `bonePose`（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/anim/AnimController.kt#physTick`），**没有任何**把骨骼姿态转成关节约束目标的代码。所以「Part 接入之后，各部件的关节就会被动画驱动」是不成立的：那是一条独立的、尚未设计的链路（骨骼姿态 → 关节目标角度 → `New6Dof` 马达），它需要单独的设计与验收，与本计划的分层结构无关。本计划保证的只是它的落点存在（表现层编排在 `MechaControl` 里，将来能拿到物理目标与变量）。

### 8.5 动画目标换成 `Part`（1:N 广播）

§4.4 的注入点从「单元素 `[mechaAnimatable]`」换成「全体 `Part`」时，剩下三件事已在本文范围内有了结论，记在这里避免到时候重新论证：

1. **动画集不用拆。** `findAnimation` 是三级回退（目标自身 → 素体 → 内置），而 `blendBone` 是「按模型骨骼逐根去动画里查，查不到就跳过」（§0.1 的「层内多动画的混合口径」行、§0.3 第 3 条）。因此把**整具**动画集放进 `builtinAnimations` 即可，每个 `Part` 只吃自己骨骼的那部分——`bmpt_main` 的 343 个骨骼名只有 195 个在当前模型里就是同一个机制在起作用。不需要先按零件拆资源。
2. **常驻层不用拆。** 广播时每个目标各起一个实例，写在**各自的** `AnimController.layers` 里（不同控制器，互不相干），因此每个 Part 的常驻槽位天然一层、天然隔离。`pre_parallel0` 的 57 根骨骼跨多个 Part 也不成问题。
3. **成本按目标数线性增长。** `physTick()` 要按目标遍历（§4.5），每个目标一次 LOD 计算与一次骨骼混合。LOD 降频表（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/anim/AnimController.kt#lodSkipIntervals`）能兜住一部分；`CameraHelper.getLodLevel` 对非客户端 `Level` 直接返回 0，服务端安全。剩下的（动画名在每个 Part 的动画集里的覆盖情况）属内容侧。

## 9. 未决问题

1. **姿态切换时的混合时长。** 四台机器的 `PlayAnimAction` 需要一个进出场过渡时长参数（构造签名里的 `blendTime`，默认 0.15 s），本计划未定值；它决定姿态切换是硬切还是渐变，需要在实机上定。
2. **`IS_JUMP_BOOSTING` 与 `IS_FALLING` 是否长期合并。** 合并的理由是资源只有一个 `jump` 动画（§4.6）。若后续资源提供上升 / 下落两套，拆分需要 `VERTICAL_SPEED`，即 D2 预留口。
3. **presenter 是否在服务端也推进。** §4.1.2 的伪码里 `presentation().progress(dt)` 没有被 `hasBody()` 包住，而 §1 的目标只提到客户端。若服务端也跑，则服务端也要注入动画目标（§4.4）；首版的目标只有 `MechaAnimatable` 一种，它是客户端对象，因此**首版服务端不注入、presenter 在服务端空转**。二选一需要在阶段 3 之前定：要么服务端跳过（首版取这一条），要么服务端也建 presenter 并为将来的服务端权威动画判定留路。
4. **动画整段只驱动自己那批骨骼带来的姿态跳变。** §3 末段指出各动画的模型内骨骼数差得多，切换时未被覆盖的骨骼会回落到绑定姿态。要消除它得让同一姿态级的动画驱动同一批骨骼，属内容侧；本计划不处理，但验收时要能区分「层结构错」与「资源骨骼覆盖范围不同」。
