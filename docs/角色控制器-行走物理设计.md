# 角色控制器 — 行走物理设计

> **状态**: 设计草案  ·  **关联文档**: [机娘模组企划](./总体设计文档.md) 2.4 节角色运动系统

本文档细化角色控制器的运动学设计。全文采用国际单位制。

***

## 1. 设计思想

### 1.1 问题本质：角色运动的双重性

考虑动作游戏中角色的一帧位移。它从哪来？

```
角色本帧位移 = intent（主动意图） + response（被动响应）
```

**主动意图**：玩家的 WASD、攻击动画的前冲、翻滚的 root motion——角色"想"往哪去。
**被动响应**：被炮击炸飞、站坡上往下滑、被友军碰撞挤开——物理世界"推"了角色多少。

这两者的力学需求截然不同：

| 需求 | 主动意图 | 被动响应 |
|------|----------|----------|
| 理想力学模型 | 运动学——清晰、可控、无超调 | 动力学——真实惯性、碰撞反弹、关节约束 |
| 不应受什么影响 | 外部冲击。玩家按前进时，爆炸不应把控制器炸飞 | 不应被抹除。被击中就该后仰，站在坡上就该下滑 |

用一个动力学刚体承载两者 → 爆炸把控制器炸飞（意图被污染），或滑坡被力模型抵消（物理被压制）。用一个纯运动学幽灵体 → 没有惯性，也没有真实碰撞反馈。

**所以我们用两个体，一个约束。**

### 1.2 解决方案：控制器牵引，躯干跟随

```
                    ┌──────────────────────┐
  主动意图 ──────→ │ MechaCharacter (KCC) │ ← 运动学幽灵体
  (玩家/动画)      │ 纯位移生成，不受外力    │
                    └──────────┬───────────┘
                               │ New6Dof 世界锚点约束
                               │ (每步 pivotInA = 控制器位置)
                               ▼
                    ┌──────────────────────┐
  被动响应 ──────→ │ 躯干刚体 + 四肢       │ ← 动力学刚体
  (爆炸/碰撞/斜坡)  │ 惯性、关节、冲击全保留  │
                    └──────────────────────┘
```

- **控制器**：运动学幽灵体（KCC）。只接收意图输入（玩家方向、动画根骨骼位移、参数调制），产生位移。不参与碰撞响应——爆炸力不作用于控制器。
- **躯干**：动力学刚体。承载全部物理反馈——被打会飞、站坡会滑、有惯性。关节约束、空气动力学照常运作。
- **约束**：世界锚点（`New6Dof`，bodyA=null）。每步将锚点更新到控制器位置，躯干被"牵引"跟随。但牵引不是刚性的——被击中时躯干拖后产生分离距离，分离超过阈值则触发 RAGDOLL。

**一句话**：控制器提供意图的纯粹性，躯干保留物理的真实性，约束是两者之间的弹性纽带。

### 1.3 多通道合成：为什么不"切模式"

意图本身有多个来源——玩家按键、动画 root motion、甚至环境脚本。传统做法是"切模式"：

```
if (放技能动画中)
    位移 = rootMotion
else
    位移 = 玩家输入
```

这有三个问题：
1. **边界硬切换**：攻击动画结束时 root motion 戛然而止，下一帧切回玩家输入——没有过渡
2. **同时性需求**：角色可以一边放前冲斩（动画根运动）一边被玩家 WASD 微调方向，两个来源应该共存
3. **参数泄漏**："当前什么模式"的判断渗入控制器内部，控制器开始需要知道动画状态

**叠加代替切换**：

```
每物理步:
  通道 A：玩家物理输入（方向 × 力模型 × inputScale）
  通道 B：动画根骨骼位移（帧间世界坐标差）
  通道 C：参数调制（gravityScale、inputScale ← MoLang ctrl.*）

  位移 = 通道A + 通道B  （三轴向量加法）
  重力 = G × gravityScale（§1.5）
```

每个通道有自己的调制系数。`inputScale = 0` 关掉玩家但仍然叠加动画。`gravityScale = 0` 关掉重力但不影响 XZ。不存在 `if (inAnimation)` 分支——位移始终是向量和，每一帧。

**这就是多通道合成的核心价值**：不是"切换行为"，而是"叠加来源"。边界问题消失，组合爆炸由参数自然约束。

### 1.4 控制与反馈的分离

控制器不判断"当前在放什么动画"或"处于什么战斗状态"。行为差异通过**外部改参数**体现，不通过内部改代码路径：

| 你想让角色…… | 怎么做 | 谁做 |
|-------------|--------|------|
| 浮空（放技能时悬空） | `gravityScale = 0` | MoLang，动画关键帧脚本 |
| 锁操作（处决/受击僵硬） | `inputScale = 0` | MoLang |
| 前冲（攻击的强制位移） | `animDelta = rootBone位移` | MechaControl，读动画骨骼 |
| 正常走路 | 所有参数默认值 | 什么都不做 |

三种行为由三种不同的外部系统发起，控制器只是变换函数。

**分层**：

| 层 | 是什么 | 做什么 |
|----|--------|--------|
| MechaControl | 编排者 | 管理状态机、每步读 AnimController 根骨骼差 → `setAnimRootDelta`；转发玩家输入 |
| MoLang（`ctrl.*`） | 调制者 | 动画关键帧脚本改写 `gravityScale`、`inputScale` |
| MechaCharacter | 变换器 | 力模型积分 + animDelta 叠加 → `setLinearVelocity`；`setGravity` |
| Bullet KCC | 执行器 | sweep、滑墙、爬坡、着地检测 |

### 1.5 其他核心概念

**分离距离保护**：躯干被击退而与控制器拉开距离时，行走力随距离折减（`行走力 × max(0, 1 - sep/sep_max)`，默认 sep_max=2m）。控制器被"拖住"减速，拉开超过阈值 → RAGDOLL。

**质量**：m 仅用于手动积分 a=F/m，不参与 Bullet 刚体。控制器质量 = 机体总质量，质量越大手感越厚重。

**KCC 单位**（详见 §11）：`getLinearVelocity()` 的 XZ 是位移（m/tick），Y 是速度（m/s），读写时需分别换算。**原因**：KCC 内部的 `m_walkDirection` 在 `stepForwardAndStrafe` 中直接用作位置偏移，而 `m_verticalVelocity` 在 `playerStep` 中做 `× dt` 积分。这是 Bullet 的设计惯性，调用方适应即可。

## 2. 状态机

玩家通过**离散按键**或**程序逻辑**(如布娃娃，浸入水中)在各状态间切换。状态决定 worldAnchor 的定位策略和约束行为。

```
                         ┌─────────────┐
                  toggle  │    WALK     │  toggle
              ┌───────────│ 控制器主导   │───────────┐
              │           └──────┬──────┘           │
              │                  │                  │
              │            death/硬直               │
              ▼                  ▼                  │
       ┌─────────────┐   ┌─────────────┐            │
       │    DRIVE     │   │   RAGDOLL   │            │
       │ XZ放开 Y锁   │   │  全部解锁    │            │
       └──────┬──────┘   └─────────────┘            │
              │                                      │
              └──────────── death ───────────────────┘
                        (ragdoll 也能死亡)

       ┌─────────────┐
       │    SWIM     │ ◄── 进入水体
       │   (未来)    │
       └─────────────┘
```

### 2.1 状态行为

| 状态          | 锚点世界位置.XZ (pivotInWorld) | 锚点世界位置.Y (pivotInWorld) | 约束旋转     | 说明             |
| ----------- | ------------------------ | ----------------------- | -------- | -------------- |
| **WALK**    | controller.pos           | controller.pos          | 全锁       | 控制器主导位置，身体追随   |
| **DRIVE**   | body.COM（每帧追）            | controller.pos（单向弹簧）    | 全锁（弹簧阻尼） | XZ 自由推进，Y 兜底支撑 |
| **RAGDOLL** | body.COM（0.3s过渡）         | body.COM（0.3s过渡）        | 逐渐解锁     | 完全布娃娃          |
| **SWIM**    | —                        | —                       | —        | 未来设计           |

### 2.2 WALK — 行走/站立

默认状态。约束锚点（pivotInWorld）全等于 controller.pos。施加到控制器的行走力通过单端世界约束单向传递给身体。

站立时行走力为零，控制器胶囊与身体紧耦合——自然提供抗扰动稳定性。

### 2.3 DRIVE — 高速移动

玩家按键切换。此状态下轮子（MotorSubsystem）和推进器（ThrusterSubsystem）对自身刚体施加驱动力，不再经控制器中转。

**XZ 平移**：解锁。锚点 XZ 每帧追踪 body.COM（每步调 `setPivotInA()` 更新），躯体不受控制器拖累。

**Y 轴**：单向弹簧约束。仅当身体 Y 低于锚点 Y（即低于控制器所在高度）时施加回拉力——控制器兜底支撑。控制器胶囊被斜坡/台阶碰撞抬升时锚点 Y 自然上移，无阻力。身体越障弹起时无向下拽力。

**Y 轴跳跃行为**：玩家在 DRIVE 下按跳跃键时，Y 轴临时切换为双向传力（持续 \~0.5s），跳跃完成后恢复单向弹簧。

**旋转轴**：全锁，弹簧阻尼（ERP=0.8, CFM=1e-5）。维持直立但允许 ±2° 微倾吸收颠簸。机体自然跟随控制器的面朝方向，无需复杂的车控逻辑。

### 2.4 RAGDOLL — 布娃娃

死亡/腿部全毁时进入。锚点渐变（0.3s）从控制器位置过渡到 body.COM，之后平移和旋转约束全部解除，身体自然 ragdoll。

### 2.5 状态切换渐变

```
WALK → DRIVE:
  锚点 XZ: controller.pos → body.COM.pos（0.5s lerp）
  锚点 Y:  controller.pos（不变）

DRIVE → WALK:
  锚点 XZ: body.COM.pos → controller.pos（0.5s lerp）
  锚点 Y:  controller.pos（不变）
```

进入 DRIVE 时约束平移刚度同步从正常值下降到零（XZ 解锁），退出时反向。渐变时长硬编码 0.5s。

## 3. 行走驱动力模型

### 3.1 概念综述

行走驱动由多个**动力源**组成：控制器本体（素体"肌肉"）加上各腿部助力子系统（LocomotionLimbSubsystem）。每个源独立基于功率-速度关系出力和自限速，最终合力经地面摩擦钳制后施加到控制器胶囊。

### 3.2 动力源参数

每个动力源拥有三个核心参数：

| 参数   | 符号       | 单位  | 含义                      |
| ---- | -------- | --- | ----------------------- |
| 功率   | P        | W   | 持续机械输出功率                |
| 额定速度 | v\_rated | m/s | 有效工作速度上限，超速则出力衰减        |
| 最大出力 | F\_max   | N   | 低速区间（v→0）的力上限，同时约束极限加速度 |

### 3.3 力-速曲线（每物理步计算）

水平对地速率 v = |velocity\_horizontal|

**第一步：功率限力**

```
F_power = P / v   （v > ε）
F_power = F_max   （v ≈ 0，用 F_max 兜底避免除零奇异）
```

**第二步：力上限钳制**

```
F_raw = min(F_power, F_max)
```

起步时 v→0 导致 F\_power→∞，F\_max 钳制防止无限大力和加速度发散。

**第三步：超速衰减**

```
当 v ≤ v_rated：F = F_raw
当 v > v_rated：F = F_raw × exp(-(v - v_rated) / λ)
```

λ（衰减陡度）可配，默认合理值。超过额定速度后该源快速退场。让"高扭低速"源在起步区主导，"高速"源在极速区接棒。

### 3.4 多源叠加

物理步进时，收集所有活跃源：

```
F_drive_total = Σ F_i    （i = 控制器本体 + 所有 LocomotionLimbSubsystem）
```

各源依自身 P / v\_rated / F\_max 独立计算 F\_i，各对速度区间形成自然分工——无需手动权重分配。

**控制器本体**的 P\_base / v\_rated / F\_max 定义于 `mech_chassis.json`。助力子系统各自定义于腿部 Part JSON。

### 3.5 地面抓地力限制

所有驱动合力最终都通过脚-地面接触传递。因此总驱动力受静摩擦约束：

```
F_drive_effective = min(F_drive_total, μ × N)
N = m × g × cos(θ_slope)
```

μ 取所有活跃 LocomotionLimbSubsystem 中 `μ_foot` 的**最大值**。多足时取最好那只脚的抓地力。若未安装任何助力腿，退化到素体裸足摩擦系数 `μ_naked`（定义于 mech\_chassis.json）。

**摩擦系数来源**：仅来自助力子系统属性，与 Machine-Max 碰撞箱 friction 不混用。μ\_foot 代表脚底最大静摩擦，语义独立。

> **与 KCC 内建碰撞的关系**：§3.5 的抓地力限制 `min(F_drive_total, μ × N)` 是应用层钳制——确保驱动力不超物理极限。KCC 自身的 `setMaxSlope` 和碰撞响应提供额外的运动学保障。有输入时 `setMaxSlope = atan(μ_effective)`（每步动态更新），过量坡度下 KCC 拒斥法向运动。

### 3.6 内阻与净力

```
F_resist = c₀ × m × g
F_net = F_drive_effective - F_resist - m × g × sin(θ_slope)
```

**内阻系数 c₀**（无量纲）：由设计参数自动导出，不手工配置。

```
c₀ = P_base / (v_ref × m_naked × g)
```

其中 P\_base 为控制器本体基准功率，v\_ref 为期望裸机行走速度，m\_naked 为裸机质量。c₀ 在素体加载时计算一次，之后作为该素体的"生物力学效率常数"保持不变。

加装零件使总质量 m 增大 → 内阻力 c₀ × m × g 增大 → 同功率下匀速更低，实现"越重越慢"。助力子系统增加功率 → 驱动力增大，平衡更高速度。

**粘滞阻尼**：一阶速度相关项 `c₁ × v` 不在此处计算，而是通过 `physicsCharacter.setLinearDamping(c₁)` 映射为 KCC 内建线性阻尼，在运动学步进阶段自动消耗速度。阻尼是纯阻力——它只消耗速度，不像摩擦力（μ × N）能提供反力——因此不应出现在牵引力竞争链路中。

> F\_resist 仅在**有行走输入时**施加（此时 `v_horizontal > 0` 且 `a > 0`）。无输入时仅 KCC 线性阻尼和碰撞摩擦制动（§3.9）。

### 3.7 空中行为

离地时（N=0，无地面接触）：

```
F_drive_effective = F_drive_total × 0.05
```

控制力衰减至 5%，允许空中姿态微调但不可加速。硬编码系数。

### 3.8 位移生成与施加

行走力最终以 `setLinearVelocity` 写入 KCC，同时叠加动画根骨骼位移。每物理步：

```
// 读取 KCC 当前速度（XZ 为位移/m/tick，需 /dt 转回 m/s，详见 §11）
v_horizontal = |physicsCharacter.getLinearVelocity()|_horizontal / dt

有输入时：
  a = F_net / m                               // 水平加速度（§3.6）
  v_horizontal += a × dt                      // 速度积分（m/s）
  // KCC 线性阻尼（c₁）在此处消耗速度——physicsCharacter.setLinearDamping(c₁) 内部处理

  // animDelta_xz 来自动画根骨骼帧间差（m/tick），由 MechaControl 每步写入
  physicsCharacter.setLinearVelocity(
      v_horizontal × dt × input_dir.x + animDelta_x,  // X: 物理位移 + 动画位移
      animDelta_y / dt,                                 // Y: 动画位移→速度
      v_horizontal × dt × input_dir.z + animDelta_z   // Z: 同上
  )

无输入时（§3.9）：
  刹车逻辑同下，最终以 setLinearVelocity 写入，动画位移在同一次调用中叠加。

当 animDelta == (0,0,0) 时（大部分行走/站立情况）：
  Y 分量 = 0，KCC 内部重力正常接管垂直运动。此时等价于原 setWalkDirection 行为。
```

> **单位转换**（详见 §11）：KCC 的 `getLinearVelocity()` 返回的 XZ 分量是位移量（m/tick），Y 分量是速度（m/s）。因此读 XZ 需 `÷ dt`，写 XZ 需 `× dt`（将 m/s 转回 m/tick），写 Y 直接用速度。`setWalkDirection` 仍可用于 "无动画叠加且仅需水平位移" 的路径——Y 分量被 KCC 强制归零，垂直由内部重力接管。

### 3.9 无输入制动

无行走输入时（input\_direction ≈ 0），不施加驱动力，依靠**主动摩擦刹车**配合 KCC 阻尼减速。摩擦刹车模拟角色"主动停步"——脚底施加最大静摩擦以尽快站住，不同地面表现不一：

```
若无输入：
  F_drive_total = 0
  F_net = 0
  a = 0
  a_brake = μ_effective × g × cos(θ_slope)        // 摩擦刹车减速度，与质量无关
  v_horizontal -= a_brake × dt                     // 每步减速
  if (v_horizontal < 0) v_horizontal = 0
  // KCC 线性阻尼（c₁）叠加提供一阶速度衰减

  physicsCharacter.setLinearVelocity(
      v_horizontal × dt × dir.x + animDelta_x,    // 刹车后速度 × dt + 动画位移
      animDelta_y / dt,
      v_horizontal × dt × dir.z + animDelta_z
  )
```

> 无输入时动画位移依然叠加——如受击后仰动画驱动的位移，角色不按键也会被"推"。若需完全锁定（如处决动画），动画侧应将 `inputScale` 设为 0 且确保 `animDelta` 完全由动画师 K 帧控制。
>
> **两条减速线分工**：
>
> | 机制   | 来源                                    | 触发条件 | 效果               |
> | ---- | ------------------------------------- | ---- | ---------------- |
> | 摩擦刹车 | μ\_effective × g × cosθ               | 无输入时 | μ=1 急停，μ=0.05 长滑 |
> | 粘滞阻尼 | physicsCharacter.setLinearDamping(c₁) | 始终生效 | 空气阻力级持续衰减        |
>
> 摩擦刹车减速度 `μ × g` 与质量无关（`a = (μ × m × g) / m = μ × g`），刹车手感仅由地面 μ 决定，不受机体重量影响。
>
> 注意：即使无输入，滑坡（θ\_slope > 0）时重力分量 `m × g × sin(θ_slope)` 未在水平力模型中扣除？已在 §3.6 中扣除。但 KCC 内部重力仍会使胶囊沿坡下滑——`setMaxSlope` 限制了"可站住"的最大坡度（= atan(μ\_effective)，§8.1）。

> ## 4. 跳跃模型

### 4.1 概念

跳跃是瞬时过程，以冲量建模。每条助力腿提供自身的 I\_min / I\_max / v\_extend。素体裸身跳跃参数由 mech\_chassis.json 兜底。

### 4.2 参数

| 参数     | 符号        | 单位  | 位置    | 含义            |
| ------ | --------- | --- | ----- | ------------- |
| 轻拍冲量   | I\_min    | N·s | 腿部子系统 | 轻按跳跃键的冲量      |
| 满蓄冲量   | I\_max    | N·s | 腿部子系统 | 蓄满后施放的冲量      |
| 最大伸展速度 | v\_extend | m/s | 腿部子系统 | 单腿可贡献的起跳速度硬上限 |
| 满蓄时间   | t\_charge | s   | 控制器   | 从轻拍到满蓄所需的按住时长 |

### 4.3 蓄力机制

线性蓄力曲线：

```
ratio = min(t_hold / t_charge, 1.0)
I_per_leg = I_min + (I_max - I_min) × ratio
```

按住跳跃键累积 t\_hold。松开即施放当前 ratio 对应的冲量。

### 4.4 蓄力期间的行为

| 行为        | 处理                                                     |
| --------- | ------------------------------------------------------ |
| 移动输入      | 行走速度随 ratio 折减：`v_walk_multiplier = 1.0 - ratio × 0.5` |
| 转向        | 不受影响                                                   |
| 松开跳跃键     | 立即按当前 ratio 施放冲量                                       |
| 受击/硬直/中断  | 蓄力取消归零，不触发跳跃                                           |
| 离地（脚脱离地面） | 蓄力取消                                                   |

### 4.5 多腿叠加与起跳速度硬上限

```
I_vertical = Σ I_per_leg_i      （各腿冲量叠加）
v_raw = I_vertical / m           （理论垂直离地速度）
v_takeoff = min(v_raw, max(v_extend_i))
```

取最快那条腿的 v\_extend 作为硬上限——最快腿伸直时身体已离地，慢腿来不及继续发力。

### 4.6 方向冲量与抓地力

方向跳（前跃/侧跳）有水平分量。水平冲量受抓地力约束：

```
I_horizontal_effective = min(I_intended_horizontal, μ_effective × I_vertical)
```

垂直跳时无水平分力，不受摩擦限制。前跃在冰面（μ≈0.05）被压至几乎纯垂直跳；粗糙地面可做出远距跳跃。

### 4.7 施加

KCC 内置跳跃机制可直接复用——设置起跳速度后调用 `jump()`，水平速度自动保留：

```
physicsCharacter.setJumpSpeed(v_takeoff)
physicsCharacter.jump()
```

> KCC 的 `jump()` 内部将垂直速度覆写为 `m_jumpSpeed` 同时保留水平分量，无需手工构造 `setLinearVelocity` 向量。方向跳（前跃/侧跳）的水平冲量可通过 `jump(Vector3f direction)` 传入。

## 8. 地形交互

### 8.1 爬坡角度限制

最大可攀爬坡度由物理导出，无需额外配置参数：

```
θ_max = atan(μ_effective)
```

其中 μ\_effective 取所有活跃 LocomotionLimbSubsystem 中 μ\_foot 的最大值（同 §3.5）。此限制由现有驱动力模型自然实现：

- §3.5 抓地力限制：F\_drive\_effective ≤ μ × N = μ × m × g × cos(θ\_slope)
- §3.6 重力分量：F\_net 中扣除 m × g × sin(θ\_slope)

当 θ\_slope → θ\_max 时，抓地力上限趋近于重力下滑分量，净驱动力趋零。超过 θ\_max 后抓地力不足以对抗重力，控制器沿坡面下滑。μ\_foot 越高 → 爬坡能力越强，纯物理自洽。

### 8.2 自动越障（Auto-Step）

小型垂直障碍（半砖、台阶边缘、地毯）不应卡住角色。每物理步执行越障检测：

```
1. 水平 sweep：沿 input_direction 向前 sweep 一个步长
2. 若命中垂直面（法线接近水平）：
   a. 在命中点上方 step_height_effective 处再次水平 sweep
   b. 若上方通道畅通且落脚面深度 ≥ step_depth_min：
      → 控制器胶囊瞬移抬高，继续水平移动
   c. 若上方也堵塞 → 正常碰撞停止
3. 若未命中垂直面 → 不触发越障
```

**生效步高**：

```
step_height_effective = step_height_base + max(各腿部子系统的 step_height_bonus)
```

默认 0.6m（能上半砖/地毯，上不了完整方块），腿部升级后可提高。取所有腿中最大加成——用最好的那条腿跨障碍。

### 8.3 参数

| 参数               | 默认值  | 来源                 | 说明                    |
| ---------------- | ---- | ------------------ | --------------------- |
| `step_height`    | 0.6m | mech\_chassis.json | 素体裸足越障高度              |
| `step_height`    | 0m   | 腿部 Part JSON       | 单腿越障加成                |
| `step_depth_min` | 0.2m | 硬编码                | 障碍顶面最小可站立深度，防止跨步后卡进墙内 |

> θ\_max 由 μ\_foot / μ\_naked 导出，不暴露为独立配置项。

## 11. KCC 的 `getLinearVelocity` / `setLinearVelocity` 单位语义

> **发现时间**：2026-06。从 Bullet C++ 源码（`btKinematicCharacterController`）追踪确认。

### 11.1 结论

`getLinearVelocity()` 和 `setLinearVelocity()` 的 **XZ 分量与 Y 分量单位不一致**。

| 轴 | 存储位置                 | KCC 内部单位        | `setLinearVelocity` 预期 | `getLinearVelocity` 返回 |
| - | -------------------- | --------------- | ---------------------- | ---------------------- |
| X | `m_walkDirection.x`  | **位移** (m/tick) | 位移                     | 位移                     |
| Y | `m_verticalVelocity` | **速度** (m/s)    | 速度                     | 速度                     |
| Z | `m_walkDirection.z`  | **位移** (m/tick) | 位移                     | 位移                     |

### 11.2 源码证据

**`playerStep(dt)`**（btKinematicCharacterController.cpp:711）：

```cpp
// 垂直：velocity × dt → 位移
m_verticalVelocity -= m_gravity * dt;    // 速度 × dt（加速度积分）
m_verticalOffset = m_verticalVelocity * dt;  // 再 × dt → 位移

// 水平：m_walkDirection 直接用作位移
stepForwardAndStrafe(collisionWorld, m_walkDirection);  // 不做 × dt
```

**`stepForwardAndStrafe(walkMove)`**（line 392）：

```cpp
m_targetPosition = m_currentPosition + walkMove;  // walkMove 即偏移量
```

**`getLinearVelocity()`**（line 671）：

```cpp
return m_walkDirection + (m_verticalVelocity * m_up);
// X = m_walkDirection.x  (位移)
// Y = m_verticalVelocity  (速度)
// Z = m_walkDirection.z  (位移)
```

**`setLinearVelocity(v)`**（line 644）：

```cpp
m_walkDirection = velocity;  // 整向量存入，但后续分解出 Y
if (m_walkDirection.length2() > 0) {
    btVector3 upComponent = /* 从 velocity 分解出 up 分量 */;
    m_walkDirection -= upComponent;      // XZ 保留在 m_walkDirection（位移语义）
    m_verticalVelocity = upComponent.length();  // Y 存入 m_verticalVelocity（速度语义）
}
```

### 11.3 对调用方的影响

| 操作                        | XZ              | Y           |
| ------------------------- | --------------- | ----------- |
| 读：`getLinearVelocity().x` | 需 `÷ dt` 得到 m/s | 已是 m/s，无需转换 |
| 写：`setLinearVelocity(v)`  | 应传入 m/tick 位移   | 应传入 m/s 速度  |
| `setWalkDirection(d)`     | 传入 m/tick 位移    | **Y 被强制归零** |

**调用方转换规则**（在 MechaCharacter 中）：

```
物理速度 v_xz (m/s) → setLinearVelocity XZ = v_xz × dt
动画位移 Δ_anim (m/tick) → setLinearVelocity XZ = Δ_anim（无需转换）
动画位移 Δ_anim.y (m/tick) → setLinearVelocity Y = Δ_anim.y / dt
```

`setWalkDirection` 在 Y 轴上强制归零——因此在无动画 Y 位移的正常行走/站立场景中，可继续用 `setWalkDirection` 走原有的水平位移路径，垂直由 KCC 重力自动驾驶。
