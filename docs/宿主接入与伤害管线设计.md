## 一、宿主形态

**玩家宿主只有一个实体：玩家自己的实体。** `ArmsCore` 不是实体，它是一份挂在玩家身上的数据；玩家"是不是机娘"取决于这份数据是否存在。

由此推出三条贯穿全文的结论：

1. **不存在"玩家实体"与"机体实体"的区分**，因此不存在两者之间的位置同步、伤害仲裁、拾取归属问题。
2. **相机、交互、背包、快捷栏、区块加载全部沿用原版**：相机跟随的就是玩家实体，`Minecraft.player` 就是它，服务端认定玩家位置用的也是它。
3. **切换素体、退出机械化、更换机体，都是替换玩家身上那条数据**，而不是换实体。玩家实体在所有这些操作中是同一个对象。

## 二、状态分层

| 层 | 载体 | 说明 |
| --- | --- | --- |
| 实体 | 玩家实体（原版 `Player`） | 原版机制的唯一承载者：相机、交互、背包、无敌帧、护甲、附魔、事件 |
| 数据 | `ArmsCore`（`common/ArmsCore.java`） | 装配体级对象：`UUID assemblyId`、`Level`、服务端权威的 `MechaControl`、`SynchedEntityData` |
| 绑定 | 装配体 UUID → 宿主实体（玩家） | 一个玩家实体至多绑定一个 `ArmsCore`；未绑定即人类形态 |

判据集中为一条：**玩家实体上是否存在一个有效的 `ArmsCore` 绑定。** 这条判据在整个代码库中应当只有一处实现（一个查询方法），其余路径（输入、伤害、运动、渲染、命令）都调用它，避免"是否机械化"的判断散落。

**绑定字段是这条判据的唯一权威。** 玩家实体上以一个由 Mixin 注入的字段承载它当前控制的 `ArmsCore`（见 §3.1），查询方法直接读该字段。不另设"装配体 → 控制者"的表：正反两个方向都能由该字段导出，而两张表并存必然产生两者不一致的时刻。

控制权校验曾经由一张「装配体 UUID → 控制者玩家 UUID」的内存表承担，方向与本表相反：那张表由装配体查控制者，而绑定字段由宿主实体查装配体。把「谁在控制谁」存成两份必然产生两者不一致的时刻，因此该表已删除，三处用途全部改读绑定字段——控制权校验 `common/MechaInputHandler.java#isController`（发起者实体的绑定字段是不是这个装配体）、取控制者实体查环境字段 `common/MechaInputHandler.java#merge`（按发起者 UUID 解析服务端玩家实体，环境值仍由服务端查询）、断线换维度时释放控制权（`common/ArmsCoreServerEvents.java#releaseCoresControlledBy` 直接读该实体自己的绑定字段，不再遍历注册表）。

## 三、接入方式：Mixin 与事件

`ARMS-Core` 的 `src/main/resources/arms_core.mixins.json` 已经把 `PlayerHostMixin` 登记在 `mixins` 数组里（§九 第 1 步已落地），`client` 数组仍为空。本文需要新增的接入点如下分级列出。

### 3.1 必需（不做则功能不成立）

| 目标 | 目的 |
| --- | --- |
| `net.minecraft.world.entity.player.Player` 实现 `BallisticsFramework` 的 `BFHitResolver` | 让以玩家实体为命中对象的攻击解析到零件（见 §四）。实现该接口也是协议拦截器识别"这是一个代理对象"的唯一依据 |
| `Player` 上注入绑定字段（当前控制的 `ArmsCore`）与其读写方法 | 承载 §二 的那条唯一判据；输入控制权校验、环境字段来源、伤害汇总、位置回写、命令与渲染全部经它查询 |
| `Player` 实现本仓库的 `IArmsHost`（宿主接口，`io.github.sweetzonzi.arms_core.common.IArmsHost`） | 让宿主形态可替换：位置回写走宿主接口而不是写死"玩家实体"，Doll / AI 敌人等宿主按同一契约实现（`docs/总体设计文档.md` §2.1 的 `IArmsHost` 设定） |

三件事由同一个 Mixin 承担：`@Mixin(Player.class)` 的声明上写 `implements BFHitResolver, IArmsHost`，各接口方法体与绑定字段的读写方法体都放在该 Mixin 类内。`common/IArmsHost.java` 与 `mixin/PlayerHostMixin.java` 已落地（当前只实现 `IArmsHost`），`BFHitResolver` 的声明与两个方法体属 §九 第 3 步。

**不注入 `hurt`。** 玩家受击的守卫与转发由协议框架既有的注入点承担，本仓库只提供 `resolveHit` 的实现，理由见 §3.4。

绑定字段的类型是 `ArmsCore`（可空，`null` 表示人类形态）。服务端玩家持有服务端实例；客户端玩家的字段由创建包解析 `hostEntityId` 后填入客户端实例（`network/payload/ArmsCoreCreatePayload.java#handle` 一侧），两端各自的实例由 `common/MechaCoreRegistry.java` 按端分表持有。

**填入前必须比对 `hostEntityId`。** 创建包经 `net.neoforged.neoforge.network.PacketDistributor#sendToPlayersInDimension` 发给维度内全部玩家，因此同一个 `hostEntityId` 会被维度里每个客户端收到；客户端只在 `payload.hostEntityId() == context.player().getId()` 时写自己的字段，否则只建立实例、不绑定。漏掉这一条会让维度内每个玩家都把自己绑定到同一个 `ArmsCore`。

**字段只在主线程读写。** 写入点是绑定建立与解除（`PlayerEvent` 一侧），读取点是伤害解析（§4.7）、位姿回写（§5.1）、输入校验（`common/MechaInputHandler.java#isController`）与命令，全部在主线程相位；物理线程不读它。声明为 `volatile` 是为了让渲染路径能读到一个完整引用，不是为跨线程写。

#### 3.1.1 宿主接口的落地形态

`docs/总体设计文档.md` §2.1 给出的 `IArmsHost` 是伪代码，其中若干方法与 `net.minecraft.world.entity.Entity` 的既有成员冲突（`setPos(Vec3)` 与 `getPosition(float)` 都是 `final`，Mixin 无法实现同签名方法）。本阶段新建该接口，只声明真正需要的方法：绑定字段的读写、`getHostEntity`、位姿与速度的落地入口——位姿入口按 `apply*` 前缀命名（`applyPose` / `applyVelocity`），避免与实体自身的位置方法撞名，也避免"宿主自己有位置状态"的误读。

**接口定义、逐条不纳入的伪代码成员及其理由、命名约束与实施顺序见 `docs/IArmsHost宿主接口设计.md`**（该文档自包含，包含完整的接口签名、参数基准与单位、调用约束、玩家宿主的 Mixin 实现形态）。

#### 3.1.2 `ArmsCore` 侧的宿主引用

`IArmsHost` 提供 `getControlledArmsCore()`（宿主 → 装配体），`ArmsCore` 侧则持有宿主的**直接引用** —— 这正是 `docs/总体设计文档.md` §2.1 与 `docs/ArmsCore双端权威与网络同步实现计划.md` 阶段 4.2 所述的形态。

**直接引用成立的根据是两者的生命周期已经绑在一起。** 装配体在每一个宿主实体对象被替换或退场的时刻都被处理掉（§3.1.3 的规则表），因此不存在"装配体活着而它持有的宿主实体已经作废"的常态。位姿回写由 `common/ArmsCoreServerEvents.java#syncToClients` 从注册表逐个 `ArmsCore` 发起，那里拿不到宿主实体（§5.1），这条引用正是它的来源；伤害解析（§4.7）与它共用同一个字段。读写入口是 `common/ArmsCore.java#getHost` 与 `common/ArmsCore.java#setHost`，后者只由 `IArmsHost#setControlledArmsCore` 的实现调用。

| 项 | 取值 |
| --- | --- |
| 类型 | `IArmsHost`（可空，`null` 表示未绑定），不是 `UUID` 或 `Entity` |
| 为什么不是 `UUID` | 装配体不跨宿主实体存活，唯一的重设点是跨维度重生以外的那一格（§3.1.3），零点维护与一次查表之间的差别可以忽略 |
| 为什么是 `IArmsHost` 而不是 `Player` | 与 §3.1 的宿主形态可替换一致；`applyPose` / `applyVelocity` 直接经接口调用，不需要 `ArmsCore` 里写宿主类型分支 |
| 写入点 | 绑定建立时运行时注入，以及同维度重生的重设（§3.1.3）。注入不在构造器里做：`common/ArmsCore.java` 的构造签名是 `ArmsCore(Level, UUID)`，宿主是构造之后才出现的信息 |
| 线程 | 只在主线程读写（§3.1 的字段契约同样适用） |

**绑定只有一个人口：`IArmsHost#setControlledArmsCore`。** `ArmsCore#setHost` 是它的下游，单独调用会让宿主一侧仍指着旧装配体。该入口负责三条换绑路径——解除本宿主此前承载的装配体、解除新装配体在旧宿主上的绑定、同一装配体的重复绑定直接返回——因此"一个宿主实体至多绑定一个装配体"与"一个装配体至多出现在一个宿主上"都由它维持。绑定确实变化时顺带重置输入状态（`common/MechaInputHandler.java#resetInput`），否则状态机会卡在上一帧；重复绑定不重置，以免抹掉正在进行的跳跃蓄力。

**调用点必须写成经接口的形态。** Mixin 的注入成员在编译期不存在于目标类上，`player.setControlledArmsCore(...)` 这类直接调用编译不过，必须写 `((IArmsHost) player).setControlledArmsCore(...)` 或 `player instanceof IArmsHost host` 后经 `host` 调用；`common/ArmsCore.java#bindHostOf` 是这一形态的便捷封装。

**绑定建立时授予飞行许可，解除时收回**，并调用 `net.minecraft.server.level.ServerPlayer#onUpdateAbilities` 同步给客户端。这是 §5.2 末段"飞行过久"检测的规避手段：该检测在 `noPhysics` 为真时不再有脚下碰撞支撑，悬停与滑翔会被踢。许可的写入方式是 `NeoForgeMod#CREATIVE_FLIGHT` 属性上的一个修饰符，不是直写 `net.minecraft.world.entity.player.Abilities#mayfly`（该字段已被 NeoForge 标记为 `@Deprecated` 并明确劝阻直写）；判据是 `IPlayerExtension#mayFly`，细节与理由见 `docs/IArmsHost宿主接口设计.md` §5.2。

**字段可空，因此每次使用前必须检查。** 装配体在"已注册、尚未绑定宿主"这段时间里是合法存在的——调试命令的创建路径就经过这一段，客户端实例则永远没有宿主——所以引用为 `null` 是常态而不是错误状态。三条使用路径各自规定如下，实现时逐条落地：

| 使用点 | 宿主为 `null` 时的行为 |
| --- | --- |
| 位姿回写 `common/ArmsCoreServerEvents.java#syncToClients` | 只跳过 `applyPose` / `applyVelocity` 两步，写包照常执行。客户端可视锚点依赖 `DATA_POS`，若连写包一起跳过，未绑定宿主的装配体在客户端会停在上一次采样上 |
| 伤害解析 §4.7 | 返回 `null`。这与"线段与宿主包围盒无交点"是同一个出口，§4.3 第二、三行已规定该出口的去向是交回原版流程：虚空、饥饿、`/kill` 这类伤害仍能作用于玩家 |
| 环境字段 §4.6、控制权校验 `common/MechaInputHandler.java#isController` | 这两条路径的调用方本身就是玩家实体，判据是"该实体的绑定字段是不是这个装配体"，因此拿到的宿主必为非 `null`；不需要额外的空值分支 |

**不做兜底猜测。** 引用为 `null` 时不得回退去查询"哪个玩家在控制这个装配体"——那个方向的信息由 §二 所述的临时表承担，而它由绑定字段取代（§九 第 1 步），重新引入会让"装配体属于谁"有两个来源。

`docs/IArmsHost宿主接口设计.md` §六记录了这条关系为什么不能靠"实体被销毁就自毁"来维护。

#### 3.1.3 装配体的生命周期规则

| 事件 | 条件 | 机体去向 |
| --- | --- | --- |
| 登录 | — | 无机体。本次落地不做正反序列化，因此重启与重连后玩家都是人类形态 |
| 断线 | — | 注销装配体并解绑。不做序列化，也不在离线期间保留活体对象 |
| 死亡 + 掉落物品 | `isWasDeath() && !RULE_KEEPINVENTORY && !isSpectator()` | **产生残骸** |
| 死亡 + 不掉落，且重生维度等于死亡维度 | `isWasDeath() && (RULE_KEEPINVENTORY \|\| isSpectator)` | 保留机体：把宿主引用改指新实体，并把 KCC warp 到重生点 |
| 死亡 + 不掉落，但跨维度重生 | 同上，且重生维度不同于原维度 | **重建**：注销旧维度的，在新维度新建。本次落地无序列化，因此重建出来的机体状态复位 |
| 末地通关重生 | `!isWasDeath()` | 按维度分流。该路径的终点是主世界，因此实际总是走到"重建"一行 |
| 换维度（非重生） | `PlayerEvent#PlayerChangedDimensionEvent` | **重建** |
| 同维度搬迁 | 无事件 | 不处理：`ArmsCore` 的 `Level` 未变、注册表键也未变 |

判定可以集中在 `net.neoforged.neoforge.event.entity.player.PlayerEvent#Clone` 一处：那时新实体已构造完毕、其 `Level` 已是重生维度，而旧实体的绑定字段还在手上，三个分支当场都能判完。`PlayerEvent#PlayerRespawnEvent` 在新实体登记进玩家列表之后触发，可用于校验与日志。

**重生判据与原版同源，不要自己凑。** `net.minecraft.server.level.ServerPlayer#restoreFrom` 的入参 `keepEverything` 由 `net.minecraft.server.players.PlayerList#respawn` 给出，`PlayerEvent#Clone` 的 `isWasDeath` 即它的取反（`net.minecraft.server.level.ServerPlayer#restoreFrom` 内派发事件时传入 `!keepEverything`）；"是否掉落物品"则由 `net.minecraft.world.entity.player.Player#dropEquipment` 的 `!RULE_KEEPINVENTORY` 与 `net.minecraft.server.level.ServerPlayer#die` 的 `!isSpectator()` 两条守卫共同决定，而 `restoreFrom` 的保留分支正是 `keepEverything || RULE_KEEPINVENTORY || isSpectator`。三者同源，因此上表的条件不会与游戏自身的判定漂移。

**为什么"重建"与"保留"要分开。** `common/ArmsCore.java#level` 是构造时注入的 `final` 字段，而 KCC 的物理空间也是构造时从该 `Level` 取得的（见该类的构造前置注释），因此装配体无法跨维度沿用；玩家实体则在跨维度时**不换对象**（`net.minecraft.server.level.ServerPlayer#changeDimension` 的跨维度分支返回 `this`），所以绑定字段与宿主引用都还指着同一个玩家，变的只有"装配体该属于哪个维度"。

### 3.4 为什么不注入 `hurt`：拦截由协议侧承担

`BallisticsFramework` 已经把玩家受击路径覆盖了。它的 `ballistics_framework.mixins.json` 注册了三个 Mixin，其中两个注入 `hurt`：

| Mixin | 注入目标 | 作用 |
| --- | --- | --- |
| `mixin/EntityHurtMixin.java` | `Entity#hurt(DamageSource, float)` 的 HEAD | 覆盖非 `LivingEntity` 的协议感知实体 |
| `mixin/LivingEntityHurtMixin.java` | `LivingEntity#hurt(DamageSource, float)` 的 HEAD | 覆盖 `LivingEntity` 子类；玩家走这一条 |
| `mixin/ProjectileHitResolverMixin.java` | 投射物命中路径 | 在 `onHit` 阶段缓存解析结果 |

两者都把调用转给 `internal/BFHurtInterceptor.java#intercept`，后者的判定顺序中**情况 3** 的判据是 `self instanceof BFHitResolver`：命中后调用 `resolveHit` 解析实际目标，再把伤害转发给该目标并 `cir.setReturnValue(dealt > 0f)` 取消原版流程。因此只要 `Player` 实现了 `BFHitResolver`，服务端玩家受击就会被自动解析并转发到零件——这正是本仓库要的行为。

子类覆写 `hurt` 不会被注入，但玩家体系的每一层都以 `super.hurt` 向上传递，函数分派最终落到 `LivingEntity#hurt` 这个被注入的声明上。调用链中各层的形态：

| 类 | 自身 `hurt` 的形态 |
| --- | --- |
| `net.minecraft.server.level.ServerPlayer` | 检查 `isInvulnerableTo`、`spawnInvulnerableTime`、`canHarmPlayer` 后 `return super.hurt(...)`；没有别的分支能直接造成伤害 |
| `net.minecraft.client.player.LocalPlayer` | `return false`，不向上传递 |
| `net.minecraft.client.player.RemotePlayer` | `return true`，不向上传递 |
| `net.minecraft.world.entity.player.Player` | 检查 `isInvulnerableTo`、创造模式无敌、死亡后按难度缩放伤害，`return p_36155_ == 0.0F ? false : super.hurt(...)` |

由此得到的两条性质：

1. **被游戏本身拒绝的伤害不会进入机甲管线。** `ServerPlayer#hurt` 在被拒绝时直接 `return false`，不调用 `super.hurt`，`LivingEntity#hurt` 的注入点因此不会执行。破坏性检查与 PvP 许可判断在前、机甲装甲在后。
2. **协议侧无需为本模组补任何注入。** 玩家受击的守卫与转发全部由 `BFHurtInterceptor` 的情况 3 完成；本仓库只实现 `resolveHit`，不重复建立守卫。

**为什么自己再加一个 `hurt` 钩子有害。** 投递侧（§4.4）依赖协议的重入守卫来放行原版流程，而该守卫的判据是**栈顶等于调用者自身**：`BallisticsFramework` 的 `internal/BFContextStack.java#hasContextFor` 的实现是 `deque.peek().target() == target`，只比较栈顶元素，既不搜索整个栈、也不回答"这次伤害是否已经投递过"。协议在 `LivingEntity#hurt` 的 HEAD 已经用这个判据放行了，再造一个钩子只是把同一条件实现两遍，并多出一个写错的入口——写成"栈中存在任意目标即放行"就会让落在发起方帧内的投递被静默吞掉。

## 四、伤害管线

### 4.1 两个对象、两种职责

| 对象 | 实现的协议接口 | 回答的问题 | 时机 |
| --- | --- | --- | --- |
| 玩家实体 | `BFHitResolver` | "这一下实际打到了哪个零件" | 管线之外（命中解析阶段） |
| 零件（装配接入后）或 §4.8 的临时区域（装配接入前） | `BFHurtTarget` | "作为协议伤害目标，我能吸收多少" | 管线之内（`BFDamageApi.hurt` 的分支 1） |
| `ArmsCore` | 不实现任何协议接口 | —— | 它是伤害的**汇总者**，不是伤害对象 |

`ArmsCore` 不实现 `BFHurtTarget` 是硬约束：一旦它成为伤害目标，协议框架要靠 `BFHurtTarget#getBFEntity` 的返回值决定"承载实体是谁"，而该方法返回 `null` 会让协议的重入守卫失效（`BallisticsFramework` 的 `api/BFHurtTarget.java#getBFEntity` 的 Javadoc 明确要求实现者返回非 null 的实体引用）。

### 4.2 玩家实体不实现协议伤害目标接口

`BallisticsFramework` 的 `BFHurtTarget` 回答的是"作为协议伤害目标，我能吸收多少"，其接口方法（`getArmorLevel` / `getRHA` / `resolvePenetration` / `calculateFinalDamage` / `hurt`）全部服务于穿甲判定。玩家实体**不需要**实现它，理由有三条：

1. **装甲层由零件承担。** 命中判定与穿深计算发生在零件上（`SubPart` 已实现 `BFHurtTarget`），玩家侧的装甲语义没有位置。
2. **原版语义不经过协议接口。** 最终扣血走 `player.hurt` 之后，原版自己的护甲、附魔、荆棘、事件全部照常生效，这些都不需要 `BFHurtTarget`。
3. **实现了反而有害。** 协议在 `api/BFDamageApi.java#hurt` 内对"既是 `LivingEntity` + `BFHurtTarget`、又穿有协议护甲"的目标会走一条前置的护甲分支，玩家一旦声明自己是伤害目标，就会多出一条与零件装甲重叠的判定路径。此外拦截器按固定顺序判定：`self instanceof BFHurtTarget` 是**情况 2**，位置在 `self instanceof BFHitResolver` 的**情况 3** 之前，因此玩家会被情况 2 接管、由它自己的 `hurt` 承受伤害并让 `getContextFor` 返回它自己；`resolveHit` 只在 `createContextFromVanilla` 返回 null（即目标对这类伤害弃权）时才会执行。声明 `BFHurtTarget` 等于放弃"解析到零件"这条链路。

因此玩家在协议里的身份只有**解析者**：它回答"打中了哪个零件"，不回答"我能吸收多少"。解析方法的契约见 §4.7。

### 4.3 有几何的伤害与无几何的伤害

玩家实体只实现 `BFHitResolver` 之后，进入玩家实体的伤害按"能否构造出命中几何"分成两类，分流点是协议拦截器的解析步骤（`BallisticsFramework` 的 `internal/BFHurtInterceptor.java#intercept`）：

| 伤害 | 解析结果 | 去向 |
| --- | --- | --- |
| 投射物、近战、爆炸等有来源位置的伤害 | 解析到某个零件 | 零件装甲判定 → 汇总 → 投递回玩家实体 |
| 虚空、饥饿、`/kill` 等没有可复检几何的伤害 | 返回 `null` | 交回原版流程，直接作用于玩家实体 |
| 有几何但几何未命中任何零件（假阳性） | 返回 `null` | 交回原版流程，直接作用于玩家实体 |

第二、三行的去向是设计意图而非缺陷：**虚空与饥饿不应被装甲挡住**，而"几何未命中"意味着这一下本来就没打在机体上。

需要留意第一行的反例：原版爆炸会对范围内每个实体各调用一次 `hurt`，玩家实体身上的那次会经解析落到某一个零件（协议按径向几何解析，命中最近/最厚的部位），因此爆炸对玩家的效果由零件装甲决定，而不再由玩家的原版护甲决定。这是"玩家实体就是机体"这一形态的必然结果。

### 4.4 玩家实体作为伤害终点

伤害的最终落地**必须**走原版 `hurt`，因为原版的护甲与附魔减免发生在 `net.minecraft.world.entity.LivingEntity#actuallyHurt` 内部（`getDamageAfterArmorAbsorb` 与 `getDamageAfterMagicAbsorb`），无敌帧、荆棘反伤与 `LivingEntityHurtEvent` / `PlayerHurtEvent` 也在这一层。直接把结算值写进生命值会绕过上述全部语义。

因此玩家实体的 `hurt` 不在本仓库的管辖范围内：协议侧 `LivingEntityHurtMixin` 在 `LivingEntity#hurt` 的 HEAD 完成分流（判据与顺序见 §3.4 与 §4.3），投递侧 `BFDamageApi.deliverTo` 把承载实体压为上下文栈顶，使这次调用命中拦截器的**情况 1**（`BFDamageApi.hasContextFor(self)` 为真）直接放行原版流程，无敌帧、护甲、附魔、事件全部照常生效。本仓库不维护额外状态位，也不实现自己的守卫。

`deliverTo` 已在 `BallisticsFramework` 落地，两个重载的签名是 `deliverTo(Entity carrier, BFDamageContext ctx)` 与 `deliverTo(Entity carrier, BFDamageContext ctx, boolean ignoreBFArmor)`（`api/BFDamageApi.java`）。它不做穿甲判定、不修正数值，只做三件事：压栈 → 承载者穿戴 `BFArmorMaterial` 护甲且 `ignoreBFArmor` 为 false 时过一遍该护甲层 → 交给承载者的原版 `hurt`。因此 `ctx` 的构造是调用方（本仓库）的义务：`baseDamage` 取第一趟结算后的伤害量、`penetration` 取到达玩家的残余穿深。

由此得到投递的完整闭环：

```text
玩家被命中
  → LivingEntity#hurt          ← 协议注入点（情况 3：玩家是 BFHitResolver）
      → resolveHit 解析到零件
      → BFDamageApi.hurt(零件, ctx)            第一趟：零件装甲判定 → 入队
  …tick 末尾统一结算…
  → ArmsCore 汇总 → BFDamageApi.deliverTo(玩家, ctx修正后)   第二趟
      → 压栈：栈顶 = 玩家
      → 玩家.hurt（原版：无敌帧 / 护甲 / 附魔 / 事件）
          → 拦截器情况 1 命中 → 放行原版
```

### 4.5 一条需要写进代码注释的语义约定

**`BFHurtTarget#hurt` 返回 `true` 只表示"这次命中已被处理"，不表示玩家扣了血。** 零件承受了命中即返回 `true`，而零件耐久可能把伤害完全吃掉，装配体汇总后向玩家投递的量为 0。武器模组据此判断"打中了"是安全的，据此刻画"造成了多少伤害"则不成立。

### 4.6 需要迁移的字段

`common/MechaInputHandler.java#merge` 从控制者玩家实体上读取环境字段（`isInWater` / `isInLava` / `isDead` / `isSleeping` / `isFallFlying` / `isInWall` / `isOnFire`）并填入 `common/control/MechaConditionSnapshot.java`。该 record 共 15 个字段，按来源分三类：

| 类 | 字段 |
| --- | --- |
| 输入（来自上行载荷） | `inputForward`、`inputStrafe`、`jumpPressed`、`sprintPressed`、`walkKeyPressed`、`sneaking` |
| 视角（来自上行载荷） | `viewYaw`、`viewPitch` |
| 环境（服务端本地查询） | `inWater`、`inLava`、`isDead`、`isSleeping`、`isFallFlying`、`isInWall`、`isOnFire` |

三类字段的来源规则如下：

- **输入与视角**由客户端上行，服务端不采信客户端上报的环境状态，否则客户端可以伪造环境绕过状态机门控。
- **环境字段**由服务端查询宿主实体得出。上行包的处理器手上就有发送者实体（`network/payload/MechaInputPayload.java#handle` 的 `context.player()`），而按 §二 的判据，这个实体上的绑定字段就是"它是不是机娘"的唯一权威，因此环境字段直接查这个实体本身，不另按控制者 UUID 反查玩家。
- **过渡时刻**（绑定建立 / 解除的那一 tick、传送、死亡重生）是环境字段唯一需要额外规则的地方：这些时刻玩家实体的位置与 KCC 不一致，从实体读到的 `isInWall`、`isFallFlying` 等会描述一个错误的位置。规则见 §八 第 8 项。

### 4.7 伤害路由：`resolveHit` 的契约

玩家实体在协议里的全部职责就是这一个方法：把"玩家被命中"翻译成"哪个零件被命中"。

```java
@Nullable
BFHitResolveResult resolveHit(Vec3 hitPoint, Vec3 delta);
```

**它是完全自由的解析器，不是取"根零件"的 getter。** 一个装配体可以有多个 `Part`，每个 `Part` 有多个 `SubPart`，每个 `SubPart` 有多个 `HitBox`。`MechaControlHolder#getRootSubPart` 回答的是另一个问题——动画根骨骼与 KCC 耦合的宿主是谁（`MechaControl#extractAnimRootDelta` 的读取对象）——装配体只有一个"根"，而命中点可以落在任何一个零件上，因此路由不能建立在它之上。`resolveHit` 拿到的是命中点世界坐标与搜索矢量（其模为搜索距离上限，单位 m，方向为命中方向），返回"实际目标 + 修正后的命中几何 + 扩展数据"，**选哪个 `BFHurtTarget`、修正成什么几何、写入什么扩展，全部由实现决定**。

**实现放在 `ArmsCore` 上。** Mixin 侧只做两件事：取玩家实体的绑定字段、把调用转给 `ArmsCore`，形如 `ArmsCore#resolveHitFor(Vec3 hitPoint, Vec3 delta)`，Mixin 体内写 `((IArmsHost) this).getControlledArmsCore().resolveHitFor(hitPoint, delta)`。这样射线与选箱逻辑与装配体数据同处一地、可单测，Mixin 类保持为纯粹的接线。

**宿主实体取自 `ArmsCore` 自身持有的引用（§3.1.2），不作为参数传入。** 分档与射线都需要宿主的包围盒（§4.8.2）。把宿主同时当参数传进来会让"我是谁的宿主"有两条来源——一条来自调用方、一条来自字段——两者可能指向不同实体；只认字段可以让"传进来一个不属于本装配体的宿主"这类错误不可表达，而不必依赖调用方自觉。

由此 `resolveHit` 的否定路径有两条，展开见 §4.8.2：未绑定宿主（宿主引用为 `null`，其空值规则见 §3.1.2）；线段与宿主包围盒无交点。

#### 4.7.1 上游契约

四条由接口本身规定（`BallisticsFramework` 的 `api/BFHitResolver.java`）：

1. **必须是幂等且无副作用的纯查询。** 同一次命中可能被解析两次——投射物命中在 `Projectile#onHit` 阶段解析一次并缓存，但 `hurt` 阶段未必能取到那份缓存（见 §4.7.3），会按伤害来源重新解析一次。**同一组 `(hitPoint, delta)` 必须始终返回同一结果**，否则两阶段的相反结论会让投射物在"继续飞行"与"销毁"之间反复。
2. **入参 `hitPoint` 是世界坐标，`delta` 是搜索矢量，"命中点"这个名字不等于"表面上的点"。** 两者的约定是 `hitPoint.add(delta)` 给出搜索终点，因此 `hitPoint` 是**线段的起点**；它落在目标包围盒表面上，只发生在投射物经 `mixin/ProjectileHitResolverMixin.java#bf$resolveHitBeforeProcess` 调用 `resolveHit(HitResult, Vec3)` 的那一条路径上（交点是原版 `entity.getBoundingBox().inflate(pickRadius).clip(from, to)` 的结果）。其余路径的起点都在别处，展开见 §4.8.2 的路径表。
3. **返回 `null` 表示未命中**，投射物应继续飞行；对管线外伤害而言它同时意味着交回原版流程（§4.3）。
4. **返回的 `correctedHitPoint` 也是世界坐标。** 第一趟进零件时不需要任何坐标换算：兄弟仓库 `Machine-Max` 的 `common/mech/vehicle/SubPart.java#hurt` 把 `ctx.hitPoint()` 直接当世界坐标用（用 `level.playSound(null, sourcePos.x, ...)` 播世界坐标音效、用 `contactPoint.subtract(body.getPhysicsLocation(null))` 求冲量作用点）。

**唯一需要坐标换算的地方是投递期的贴身护甲。** `BFArmorMaterial#mapHitToSlot` 的默认实现按 `hitPoint.subtract(wearer.position()).y / wearer.getBbHeight()` 划分槽位（分界是 `> 0.85` 头、`> 0.55` 胸、`> 0.35` 腿、其余脚，见 `api/BFArmorMaterial.java#mapHitToSlot`），因此承载者穿戴 `BFArmorMaterial` 护甲时，投递用的 `hitPoint` 必须换算成玩家身体坐标系；沿用零件的命中点会让槽位选错。无法换算时显式传 `Vec3.ZERO`：该实现把它判为"无有效命中点"并返回 `null`，`internal/BFArmorAdapter.java` 随即转入兜底路径——按各槽位加权平均（胸 `35%`、头 `30%`、腿 `25%`、脚 `10%`）取有效 RHA，而不是跳过护甲层。

#### 4.7.2 按伤害形态分派

兄弟仓库 `Machine-Max` 的 `common/entity/MMPartEntity.java#hurt` 是同一问题的参考实现（它是单 `SubPart` 的代理实体，但选择逻辑与零件数量无关）。三种形态各有正确的路由方式：

| 伤害形态 | 判据 | 路由方式 | 命中框 |
| --- | --- | --- | --- |
| 投射物 | `source.getDirectEntity() instanceof Projectile` | 该投射物在 `onHit` 阶段已完成的解析结果（见 §4.7.3） | 随解析结果一同产出 |
| 爆炸 / 范围 | `source.is(DamageTypes.EXPLOSION)` 或 `PLAYER_EXPLOSION` | 径向几何：取各 `SubPart` 质心到来源点最近的一个 | `SubPart#findStrongestHitBox()`（爆炸没有可用的命中面） |
| 一般实体攻击 / 近战 | 其余且有 `source.getSourcePosition()` | 对物理空间做射线检测 | `SubPart#getHitBox(int)`，索引取自射线结果 |

第三种形态就是本仓库的主路径。`Machine-Max` 的 `common/attachment/LivingEntityEyesightAttachment.java` 给出了同一模式的更简洁版本：

```java
var results = physicsLevel.getWorld().getWorldSnapshot().rayTest(start, end);
for (PhysicsRayTestResult result : results) {
    if (result.getCollisionObject() instanceof PhysicsRigidBody body
            && PhysicsBodyExtensionKt.getOwner(body) instanceof SubPart subPart) {
        if (subPart.isWheelSurface(result.triangleIndex())) continue;   // 跳过轮胎球面
        HitBox hitBox = subPart.getHitBox(result.triangleIndex());
        if (hitBox != null && !hitBox.isActive()) continue;             // 跳过未激活的碰撞箱
        // → 这个 subPart + hitBox 就是路由结果
    }
}
```

射线起点与终点按形态取：活体攻击者用 `attacker.getEyePosition()` 与 `attacker.getViewVector(1).scale(5)`；其余来源用 `source.getSourcePosition()` 指向玩家位置。这与 `api/BFHitResolver.java#searchRay` 为管线外伤害构造的几何是同一套规则（该静态方法已实现爆炸优先、投射物、活体近战、其他有源位置、无源位置五级分派，可直接复用而不必自己写）。

#### 4.7.3 投射物缓存给的是精确命中判据

**这一条不是优化，它决定投射物伤害是否精确。** 原版投射物的命中判定链是：

```text
ProjectileUtil.getEntityHitResult(…)
  → AABB aabb = entity.getBoundingBox().inflate(pickRadius);   // 只对包围盒
  → Optional<Vec3> optional = aabb.clip(from, to);             // 只对包围盒求交
  → 交给 Projectile#onHit(HitResult)
```

即 `EntityHitResult` 本身**只保证射线与包围盒相交**。精确性由协议补上：`BallisticsFramework` 的 `mixin/ProjectileHitResolverMixin.java` 注入 `Projectile#onHit(HitResult)` 的 HEAD，若被命中的实体实现了 `BFHitResolver` 就调用 `BFDamageApi.resolveHitTarget`；**返回 `null` 时 `ci.cancel()` 取消原版流程，投射物继续飞行**（AABB 假阳性不销毁、不造成伤害），判定为真命中则把结果写入 `BFHitResolveCache` 缓存供 `hurt` 阶段复用。

**本仓库因此免费获得这套精确性，而 `Player` 正是判据所指的对象**——注入点的判据是 `ehr.getEntity() instanceof BFHitResolver`，与具体实现无关。玩家实现了 `BFHitResolver`，所以"擦着包围盒飞过去"的投射物会被 `resolveHit` 返回 `null` 挡下。**不需要新增实体接口**：`BFHitResolver` 就是那个抽象，协议已经把它用在源侧（投射物侧）而不只是目标侧。

缓存的写入与读取分布在两处（`internal/BFHitResolveCache.java` 定义了 `bf$cacheResolve` / `bf$takeResolve`）：

| 阶段 | 位置 | 动作 |
| --- | --- | --- |
| 写 | `mixin/ProjectileHitResolverMixin.java#bf$resolveHitBeforeProcess` | 在 `onHit` 的 HEAD 解析；`null` 则取消原版流程，否则 `bf$cacheResolve(hitEntity, resolved)` |
| 读 | `internal/BFHurtInterceptor.java#intercept` 的情况 3 | `bf$takeResolve(self)`；取到则直接用，取不到（非投射物来源、缓存被消耗、命中实体不匹配）则按 `BFHitResolver.searchRay` 的几何重新解析 |

缓存的性质：**一次性**（读取即清空）、**不跨命中事件**（穿透投射物在同一 tick 内连续多次命中，每次命中都要有自己的判定结果）、**仅在命中实体身份相等时返回**。

**一个必须知道的边界**：缓存把结果保留到 `hurt` 阶段，但 `hurt` 有可能永不被调用（原版在 `LivingEntity#hurt` 内因无敌帧、`isInvulnerableTo`、已死亡而拒绝）。这不是泄漏——缓存是投射物上的单字段，下次命中会覆写——但"缓存里有记录"与"目标确实承受了伤害"**不是一回事**。武器模组侧不要从缓存的存在推断命中已结算。

**与 `Machine-Max` 现有实现的关系**：MM 另有一套投射物缓存（`mixin_interface/IProjectileMixin.java` 的 `machine_Max$getHitSubPart` / `machine_Max$getHitPoint` / `machine_Max$getHitNormal` / `machine_Max$getHitBox`，写入方在 MM 的 `mixin/ProjectileMixin.java`），`MMPartEntity#hurt` 读的是它。那套是 MM 在 `BFHitResolveCache` 之外自建的平行机制，功能上与协议这套重叠；`MMPartEntity` 还在 `hurt` 内做了一次补写——若协议上下文里的 `HIT_BOX` 扩展为空就补上自己检测到的命中框（`common/entity/MMPartEntity.java#hurt`）。**本仓库不引入第三套**，也不需要在 `hurt` 阶段补写扩展：`resolveHit` 在构造 `BFHitResolveResult` 时就写入 `extensions`，协议在情况 3 里用它构造 context，第一趟进零件时扩展已经在位。是否让 MM 收敛到协议这套缓存，属 MM 侧的决策。

#### 4.7.4 四条否决与取舍规则

1. **必须用 `WorldSnapshot` 做射线，不能用主物理空间。** 这是硬约束：`resolveHit` 在主线程被调用（§3.4），而 `cn.solarmoon.spark_core.physics.level.WorldSnapshot` 的类注释写明其用途是"只读物理快照世界，**用于主线程进行 rayTest / sweepTest / contactTest**；不参与物理积分、不触发任何 PhysicsBodyEvent、结构稳定增量同步"。访问路径是 `SparkLevel.getPhysicsLevel(level).getWorld().getWorldSnapshot()`。直接对 `PhysicsWorld` 做射线是跨线程读主物理空间，与 §七 的线程纪律冲突。
2. **快照射线拿到的 `owner` 就是真正的 `SubPart` 实例。** `WorldSnapshot` 在创建快照刚体时直接写 `userObject`（`WorldSnapshot.kt` 内的 `snap.userObject = main.userObject`，注释即"直接写 userObject，用于查找owner"），因此 `PhysicsBodyExtensionKt.getOwner(body)` 在快照上返回主世界的那个 `SubPart`，路由结果可以直接交给 `BFDamageApi.hurt(subPart, ctx)`，不需要任何 id 翻译。
3. **`triangleIndex` 在主物理空间与快照世界之间是统一的。** 快照与主世界使用相同的碰撞形状对象，因此 `SubPart#getHitBox(int)` 可以直接接受快照射线给出的索引。该方法本身把索引解释为子碰撞形状下标（`collisionShape.listChildren()[index].getShape().nativeId()`）并自带异常捕获与回退（回退到 `hitBoxes` 的第一个）——索引失效时不会抛错，只会静默退化，因此这一条的正确性依赖"形状对象同一"这个前提，不应在别处另建索引体系。
4. **必须跳过未激活与已摧毁的零件。** 兄弟仓库 `Machine-Max` 的两处射线实现都检查 `HitBox#isActive()`；`SubPart` 另有 `isDestroyed()` 与摧毁倒计时。已摧毁的零件是被穿透到内层、还是仍可被路由，需要在实现时定一条规则并写入注释。

**`HIT_BOX` 扩展的写入是精确路由的交付物。** `common/mech/vehicle/SubPart.java#findHitBox` 优先读上下文扩展 `MMDamageExtensions.HIT_BOX`，缺失时才回退到 `common/mech/vehicle/SubPart.java#findStrongestHitBox`（装甲最厚的那个）。因此 `resolveHit` 若不写该扩展，链路仍能跑通并正确扣减耐久，但**永远打在该零件装甲最厚的命中框上，没有方向性**。要精确化，`resolveHit` 需要把选定的命中框写进 `BFHitResolveResult.extensions()`；命中点本身已是世界坐标，无需换算（见 §4.7.1）。

### 4.8 装配接入前的伤害路由（mock 目标）

§4.7 描述的路由需要"实际打到了哪个零件"，而零件装配是另一条工作线：它要接刚体、碰撞形状与子系统，不是宿主接入的前置。为了让伤害能够**先端到端跑通**，本阶段在 `ArmsCore` 内放一组临时的 `BFHurtTarget` 实现，代替真零件接收命中。

`BFHurtTarget` 不要求实现者是实体或刚体：它只强制 `getArmorLevel(BFDamageContext)` 与 `createContextFromVanilla(DamageSource, float)`，`hurt(DamageSource, float)` 是唯一必须自己写的伤害方法，其余成员都有默认实现（`BallisticsFramework` 的 `api/BFHurtTarget.java`）。因此这组对象可以完全是本仓库的普通类。

**不复用兄弟仓库 `Machine-Max` 的既有零件体系**：`common/mech/vehicle/SubPart.java` 的构造签名是 `SubPart(String name, Part part, SubPartAttr attr)`，血缘要求一个 `Part`；其基类 `common/mech/DestroyableObject.java` 是 `abstract`，有多个抽象成员待实现，且伤害结算挂在 `ObjectManager` 的每 tick 扇出上——不入注册表就永远不会结算。复用它的代价高于自己写一个。

#### 4.8.1 三个区域

| 区域 | 枚举名 | Y 比例区间（相对包围盒高度） | 装甲等级 | `medianRha()` |
| --- | --- | --- | --- | --- |
| 头 | `HEAD` | `[0.78, 1.00]` | `ArmorLevel.MEDIUM`（10–20mm） | 15f |
| 核心 | `CORE` | `[0.40, 0.78]` | `ArmorLevel.MEDIUM`（10–20mm） | 15f |
| 腿 | `LEG` | `[0.00, 0.40]` | `ArmorLevel.LIGHT_2`（5–10mm） | 7.5f |

Y 比例的定义与 `BallisticsFramework` 的 `api/BFArmorMaterial.java#mapHitToSlot` 同形：命中点在玩家包围盒内的相对高度。`ArmorLevel` 的档位取自 `api/ArmorLevel.java`，`medianRha()` 是中位值，mock 直接用默认的 `getRHA` 即可。

**区域不设耐久。** 本阶段的验收目标只有一条：伤害能被正确路由到某个区域，并被投递回玩家。耐久、摧毁、子系统事件都属于装配接入的工作。

#### 4.8.2 区域选择的实现方式

原型期不对手写的胶囊做射线求交，但**必须先与宿主包围盒求交**，再按交点的 Y 比例分档。

**求交不可省，因为 `hitPoint` 多数时候是射线起点。** 调用 `resolveHit` 的两条路径给出的几何形状不同：

| 调用路径 | `hitPoint` 的实际内容 | 是否落在包围盒上 |
| --- | --- | --- |
| 投射物在 `net.minecraft.world.entity.projectile.Projectile#onHit` 的 HEAD 处先行解析（`mixin/ProjectileHitResolverMixin.java`） | `net.minecraft.world.phys.HitResult#getLocation`，即 `net.minecraft.world.entity.projectile.ProjectileUtil#getEntityHitResult` 用 `entity.getBoundingBox().inflate(pickRadius).clip(from, to)` 求出的交点 | 是 |
| `hurt` 阶段的近战、爆炸、以及投射物缓存未命中 | `api/BFHitResolver.java#searchRay` 的 `ray[0]`：活体攻击者取 `net.minecraft.world.entity.Entity#getEyePosition`，投射物取 `net.minecraft.world.entity.Entity#position`，爆炸与其余有源位置伤害取 `net.minecraft.world.damagesource.DamageSource#getSourcePosition` | 否 |

第二分量是"方向 × 距离"的合矢量（近战固定 5 m，径向取两点距离），所以 `hitPoint.add(delta)` 才是线段终点。攻击者眼位、爆炸来源点、投射物坐标都与玩家身体位置无关：直接拿它们算 `(y − 包围盒底面y) / 包围盒高` 得到的是一个与"打在哪个部位"无关的数。

**规则**：先求线段 `[hitPoint, hitPoint.add(delta)]` 与宿主包围盒的交，取第一个交点；无交点则返回 `null`（这一下从几何上没有经过机体，交回原版流程，与 §4.3 第三行同义）。有交点时按 `(交点 y − 包围盒底面 y) / 包围盒高` 分档，并把该交点写进 `BFHitResolveResult#correctedHitPoint`。回填是必需的：拦截器随后会用 `api/BFDamageApi.java#contextForResolvedTarget` 把 `correctedHitPoint` **无条件**替换进上下文（`correctedHitNormal` 非零时一并替换），因此分档所用的点与下游读到的点必须是同一个。

**只对交点分档、不对胶囊求交，理由是两条：**

1. 本阶段没有可旋转的碰撞体可打。分区用的胶囊/包围盒是手写的常量，对它们做射线求交得到的结论与"交点在哪个 Y 区间"一致——多出来的只有代码量与出错面。
2. 三个区间的 Y 比例首尾相接覆盖 `0.00` 到 `1.00`，而求交之后交点必然落在包围盒上，比例必然落在该区间内，不存在"交点存在却无区域可归"的情形。

**返回 `null` 的路径有两条，二者的去向相同而原因不同**：未绑定宿主（宿主引用为 `null`，逐条行为见 §3.1.2 的空值规则表）与线段和包围盒无交点。两条都交回原版流程：前者没有宿主包围盒可求交，后者表示这一下从几何上没有经过机体，对应 §4.3 表格的最后两行（第二行的"无几何"与第三行的"假阳性"）。

**本阶段的命中体积取玩家原版的站立包围盒** —— `net.minecraft.world.entity.player.Player#STANDING_DIMENSIONS` 的 `0.6 × 1.8`。它与 KCC 胶囊（`common/control/attr/MechaBodyPreset.java#CAPSULE_RADIUS` 半径 `0.4`、`common/control/attr/MechaBodyPreset.java#CAPSULE_HEIGHT` 圆柱段 `1.6`，即直径 `0.8`、全高 `2.4`）不一致，后果与原版的命中求交方式直接相关：投射物的 `getBoundingBox().inflate(pickRadius).clip(...)` 与近战射线都以实体包围盒为准，所以机体高出 `1.8 m` 的那一段（`1.8` 至 `2.4`）打不到，而 §4.8.1 的三个 Y 比例区间也是按 `1.8 m` 归一化的。让命中体积跟随胶囊需要覆写 `net.minecraft.world.entity.player.Player#getDefaultDimensions`，展开与两个陷阱见 §八 第 12 项；本阶段不做。

装配接入后，区域选择改为对真零件的碰撞形状做射线检测，并写入 `HIT_BOX`（MM 侧的扩展键）供同区域内多命中框的细分——那才是 §4.7.4 第 4 条与 §4.7.2 的形态。**mock 的这处分档是临时的，但它与最终形态的接缝只有"求交对象"一处**：两者都消费"求交之后的交点"，只是求交对象从宿主包围盒换成零件碰撞形状。

#### 4.8.3 硬约束：`hurt` 内不得触碰宿主实体的 `hurt`

`BFHurtTarget` 实现每次被调用时，协议已经完成入栈（`BallisticsFramework` 的 `api/BFDamageApi.java#hurt`），而**压栈目标取决于 `getBFEntity()` 的返回值**：

```java
Object stackTarget = target;
if (target instanceof BFHurtTarget bfTarget && bfTarget.getBFEntity() != null) {
    stackTarget = bfTarget.getBFEntity();
}
BFContextStack.INSTANCE.push(stackTarget, ctx);
```

mock 不是实体，`getBFEntity()` 返回 `null`，因此**栈顶是被命中的那个区域对象，而不是玩家实体**。若 mock 的 `hurt` 里调用 `player.hurt(source, amount)`，`BFDamageApi.hasContextFor(player)` 为假，协议的 `internal/BFHurtInterceptor.java#intercept` 会把它当成管线之外的新伤害、经情况 3 重新解析回这个区域，形成无限递归。

这正是 §4.4 的分工在 mock 上的体现：**区域只记录，落地由投递完成。** `hurt` 的职责是把金额与上下文入队并返回 `true`，宿主实体的扣血在结算相位由 `BFDamageApi.deliverTo` 承担（它在自己的调用期内压栈，使 `hasContextFor(玩家)` 为真、原版流程放行）。

`getBFEntity()` 返回 `null` 与 `api/BFHurtTarget.java#getBFEntity` 的 Javadoc"必须优先返回非 null"并不矛盾：那条要求针对**委托实体 `hurt()` 的实现者**——它若返回 null 会让重入守卫失效。本组实现不委托给任何实体，返回 null 是正确形态，此点须写入代码注释，避免后来者照 Javadoc 改坏它。

#### 4.8.4 `createContextFromVanilla` 必须返回有效上下文

玩家受击的解析路径是拦截器的**情况 3**（`self instanceof BFHitResolver`）。情况 2（`self instanceof BFHurtTarget`）的判据针对的是**被直接命中的对象**，而拦截器的形参类型是 `net.minecraft.world.entity.Entity`：区域是本仓库的普通类、不是实体，情况 2 永远不会作用在它身上，因此不需要靠返回值去回避。

**区域在情况 3 里扮演的是"解析结果"，`createContextFromVanilla` 在那里是转发开关。**

```java
BFHurtTarget actual = resolved.actualTarget();
if (actual == self) return;
BFDamageContext ctx = actual.createContextFromVanilla(source, amount);
// 目标不接受协议外伤害：交回原版流程
if (ctx == null) return;
```

（引用 `BallisticsFramework` 的 `internal/BFHurtInterceptor.java#intercept`，即情况 3 内 `resolved.actualTarget()` 之后的三步。）返回 `null` 会让拦截器直接放行原版流程：`BFDamageApi#hurt` 不会以区域为目标被调用，区域的 `hurt` 不执行、不入队，§4.8.5 的两条验收信号一条都不会出现。**因此区域必须返回一个有效上下文。**

上下文在这里是**种子**：拦截器紧接着会用 `api/BFDamageApi.java#contextForResolvedTarget` 按解析结果覆盖命中点、命中面法线与扩展数据，而 `source` 与 `baseDamage` 原样保留。种子需要自行给出的量：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `source` | 拦截器传入的 `DamageSource` | 原样透传 |
| `baseDamage` | 拦截器传入的 `amount` | 原样透传 |
| `penetration` | 取 `amount` | mock 没有装甲厚度来源，用伤害量充当穿深（单位仍按 mm RHA 解释）。判定链是 `api/ArmorLevel.java#fromRha` 向上取整 → `api/ArmorLevel.java#canDefeat` 比较 `ordinal`，因此"能不能打穿"与伤害量的对应关系要按区域分别算，见下表 |
| `hitPoint` | 任意非空世界坐标 | 必填；拦截器随后会用 `correctedHitPoint` 覆盖它 |

种子不设置 `hitVelocity` 与 `hitNormal`，走构建器默认值。三个区域的穿甲判定只用 `penetration`（`api/BFHurtTarget.java#getRHA` 默认取等级中位值、`#modifyPenetration` 默认原样返回 `ctx.penetration()`），因此这两个默认值不改变本阶段的结果。

**`penetration = amount` 时各区间的判定结果。** 取值为 `amount` 而不是更小的数，是因为默认的 `api/BFHurtTarget.java#calculateFinalDamage` 在同级击穿时会打折、未击穿时归零，而这两个现象在日志里都能直接看出来：

| 区间 | 区域等级 / 中位 RHA | `amount ≤ 10` | `amount` 为 11–12 | `amount ≥ 13` |
| --- | --- | --- | --- | --- |
| 头、核心 | `MEDIUM` / 15mm | 判 BLOCKED，最终伤害 0 | 同级击穿：`baseDamage × 0.65` | 越级击穿：`baseDamage` 全额 |
| 腿 | `LIGHT_2` / 7.5mm | `amount ≤ 5` 判 BLOCKED | `amount` 为 6–10 同级击穿 ×0.65 | `amount ≥ 11` 全额 |

即"低于 10 就完全投递不出量"只对头和核心成立，腿的门槛是 5。挑选验收用的伤害值时按本表取值，否则会把"装甲吃掉了"误判成"管线没接通"。

`getBFEntity()` 返回 `null` 与 `api/BFHurtTarget.java#getBFEntity` 的 Javadoc 并不冲突，理由见 §4.8.3。

#### 4.8.5 验收方式

本阶段的验收不依赖任何渲染或 UI，只有两条可观测输出：

1. **路由记录**：区域的 `hurt` 被调用时打印一行日志，携带区域名、伤害量与伤害来源。看到它即证明"伤害进得来、路由到了正确区域"。
2. **投递结果**：`BFDamageApi.deliverTo` 的返回值与玩家生命值变化。看到它即证明"汇总得起来、投递得出去"。

伤害量的核对要留意 §4.5 的语义约定：区域的 `hurt` 收到的是**穿甲判定后的金额**，而投递给玩家的是**按区域汇总后的金额**，两者之间还隔着一次原版护甲与附魔减免。因此日志里同时打出这两个数才有诊断价值。

#### 4.8.6 与真装配的接缝

`ArmsCore` 侧要保留**统一的伤害账本**，使 mock 态与真装配态共用同一条投递路径：

| 数据来源 | 入口 | 说明 |
| --- | --- | --- |
| mock 区域 | 区域 `hurt` 入队 → `ArmsCore` 汇总 | 本阶段 |
| 真零件 | `Machine-Max` 的 `common/mech/vehicle/IPartAssembly.java#onPartDamage(Part, List<SubPartHitDamage>)` | 装配接入后 |

后者的批次重载在 `common/ArmsCore.java` 中**未被覆写**，因此当前走接口默认实现、把批次折算成总量后交给同名的单参方法，而单参方法是空实现——**零件伤害通告目前整个被丢弃**。装配接入时覆写批次重载即可接上同一条投递。

按残余穿深的定义（`BallisticsFramework` 的 `docs/BFDamageApi-deliverTo投递计划.md` §5.7），投递用的 `ctx.penetration` 是到达承载者的残余穿深，典型形式为 `ctx.penetration() - getRHA(ctx)`。这个值**必须在命中时刻算好、随伤害一同入队**：结算期重算会读到整批结算前的耐久（而 `getRHA` 是耐久派生量），且结算在主线程而协议伤害可能来自物理线程。mock 没有耐久，但账本要按同一形状记录，否则装配接入时这条约束会被漏掉。

**账本的入队项形状**：每条至少携带命中时刻的伤害量、命中时刻的残余穿深、命中框扩展与伤害来源四项，前两项在命中时刻定格、不留给结算期重算；汇总按批次求和；投递用的 `ctx` 按 `docs/BFDamageApi-deliverTo投递计划.md` §5.7 的构造表重建，其中命中点按 §4.7.1 换成宿主身体坐标系（无法换算时显式传 `Vec3.ZERO`）。投递遵守 `docs/BFDamageApi-deliverTo投递计划.md` §5.8 的三条约束：不重试、同一批次对同一承载者只投递一次、栈为空时投递。

**投递相位必须显式排在零件结算之后。** 真零件那条来源的到达时刻由 `Machine-Max` 决定：它的 `common/mech/ObjectManager.java#onPostTick` 在 `net.neoforged.neoforge.event.tick.LevelTickEvent.Post` 上以 `EventPriority.NORMAL` 逐个调用 `DestroyableObject#postTick`，其中才走到 `common/mech/vehicle/SubPart.java#settleAccumulatedDamage`，直到那里才发出 `onPartDamage`。本仓库现有的 `common/ArmsCoreServerEvents.java#onPostTick` **同为 `EventPriority.NORMAL`**，同优先级下两个订阅者的先后由注册顺序决定，不由代码意图决定。因此汇总与投递要单开一个 `EventPriority.LOW` 的订阅者，与写包相位分开：写包留在 `NORMAL`，投递排在零件结算之后。否则每次提交的都是上一 tick 的账本。

## 五、运动接管

### 5.1 权威方向

`MechaControl` 在物理线程推进，KCC（`common/control/MechaCharacter.java`，继承 Bullet 的运动学角色控制器）是唯一的运动权威。主线程只做一件事：**把 KCC 的位姿写进玩家实体。**

| 量 | 来源 | 写入目标 |
| --- | --- | --- |
| 位置 | `MechaCharacter#getPhysicsLocation` | 宿主实体的位置字段，写入值是**胶囊中心减去 `common/control/attr/MechaBodyPreset.java#HALF_TOTAL`**（即胶囊底面）。**这一笔是过渡态**：`docs/宿主位置权威与位移摄入设计.md` §九 第 4 步会把它删除，位置改由客户端上报与位移摄入通道维护，见本节末 |
| 朝向 | 客户端上行载荷的 `viewYaw` | 不写回宿主实体。朝向的权威在客户端：`MechaControl#applyFacing` 把它绝对赋值给 KCC 的 `currentYaw`，`common/ArmsCore.java#DATA_YAW` 只是这个值的下行回显，供渲染路径使用 |
| 速度 | `MechaCharacter#getLinearVelocity` | 宿主实体的 `deltaMovement`（注意其水平分量为每物理步位移、垂直分量为 m/s，见 `docs/角色控制器-行走物理设计.md` 的单位约定）。`noPhysics` 为真时不产生实际位移，写入的作用是让外部查询看到 KCC 的真实速度 |

**为什么要写朝向就不能写。** 若把 KCC 的 `currentYaw` 写回宿主实体的 `yRot`，而客户端下一次上行读的又是这个字段（`client/ARMSClient.java#collectAndSend` 的 `viewYaw` 取自 `player.getYRot()`），两点之间就构成「本机视角 → 上行 → 服务端 → 下行 → 本机视角」的滞后反馈环，表现为视角持续抖动。位置没有这个问题：客户端上行的位置被服务端采纳后立即被本轮 KCC 的产物覆盖，是单向下行。

**位置基准：实体位置字段是包围盒底面，不是中心。** `net.minecraft.world.entity.Entity#setPos` 把三个分量存进 `net.minecraft.world.entity.Entity#position`，再以它为原点重建包围盒；重建由 `net.minecraft.world.entity.EntityDimensions#makeBoundingBox` 完成，其形状是 `AABB(x − 宽/2, y, z − 宽/2, x + 宽/2, y + 高, z + 宽/2)` —— 即 `position` 是包围盒的**底面中心**（脚底）。交叉验证：玩家站立包围盒的眼高 `net.minecraft.world.entity.player.Player#DEFAULT_EYE_HEIGHT` 为 `1.62`，只有在"`position.y` 是脚底"的语义下才等于"脚上 1.62 m"。

把胶囊中心直接写进该字段会把宿主整体抬高 `HALF_TOTAL`（`1.2 m`）；正确换算是 `宿主位置 = 胶囊中心 − HALF_TOTAL`，让包围盒底面与胶囊底面对齐。`common/ArmsCore.java#enterPhysicsSpace` 的入参是胶囊中心，`common/control/attr/MechaBodyPreset.java#capsuleCenterFromFeet` 是反方向算式，三处不要混用。

回写经 §3.1.1 的宿主接口进行（`IArmsHost#applyPose` 写位置，`IArmsHost#applyVelocity` 写 `deltaMovement`），而不是在 `ArmsCore` 里写死 `ServerPlayer`：这样同一份 `ArmsCore` 代码在玩家以外的宿主形态（Doll、AI 敌人）下不需要分支。玩家宿主的实现就是写自己的实体位置，参数基准与单位见 `docs/IArmsHost宿主接口设计.md` §2.1。

写入相位与现有同步写包一致（`common/ArmsCoreServerEvents.java#syncToClients` 所在的 `LevelTickEvent.Post`），使同步出去的 `DATA_POS` 与实体位置取自同一次采样。

**位置那一笔将被删除，速度那一笔保留。** `docs/宿主位置权威与位移摄入设计.md` §九 第 4 步规定：服务端不再每 tick 把 KCC 位置写进宿主实体，位置由客户端上报（§5.3）与位移摄入通道（该文 §5 的分类 + §6 的 warp）共同维护，本节的"位置"一行在该设计落地后作废。理由是该文 §3 的两处回写之一就在这里——每 tick 写一次位置会把同一 tick 由 `/tp` 一类入口写入的外部位移直接覆盖，控制器因此永远不知道那次位移发生过。速度写入不受影响，它不与位置构成双权威（§5.3.3 末段）。

### 5.2 让玩家自身的物理不干扰

玩家实体必须是"被搬动"的，而不是自己走。需要的设置集中在两处：

- **关闭地形碰撞**：`net.minecraft.world.entity.Entity#noPhysics` 是实体上的公开字段，置位后 `Entity#move` 直接位移而不做碰撞求解；KCC 承担全部地形交互。
- **重置坠落距离**：实体被外部搬动时，原版会按位置差累计坠落距离。每 tick 回写位置后调用 `net.minecraft.world.entity.Entity#resetFallDistance`（与兄弟仓库 `Machine-Max` 的 `common/mech/subsystem/SeatSubsystem.java#onTick` 对乘客所做的处理同形）。这一笔挂在位置回写上，因此随它一起失效：位置回写删除之后，坠距重置要另外指派（见 `docs/IArmsHost宿主接口设计.md` §5.2 的同一处说明）。

**`noPhysics` 不是一次性设置：`net.minecraft.world.entity.player.Player#tick` 的第二条语句把它重置为 `isSpectator()`**（首条是 NeoForge 的 `net.neoforged.neoforge.event.EventHooks#firePlayerTickPre`）。绑定形态必须在每次 `net.minecraft.world.entity.player.Player#tick` 的**末尾**重新置位，而那个位置有现成钩子：`Player#tick` 在开头与结尾分别调用 `net.neoforged.neoforge.event.EventHooks#firePlayerTickPre` 与 `net.neoforged.neoforge.event.EventHooks#firePlayerTickPost`，对应的 `net.neoforged.neoforge.event.tick.PlayerTickEvent` 的 `Post` 一侧双端都会触发。本项不需要新增 Mixin。

**相位必须是它，不能是 `LevelTickEvent.Post`。** 服务端一个 tick 内的先后是固定的：`LevelTickEvent.Post` 在 `net.minecraft.server.MinecraftServer#tickChildren` 的关卡循环内触发，而服务端玩家要到循环结束之后的 `net.minecraft.server.network.ServerConnectionListener#tick` → `net.minecraft.server.network.ServerGamePacketListenerImpl#tick` → `net.minecraft.server.level.ServerPlayer#doTick` → `Player#tick` 才步进。在 `LevelTickEvent.Post` 置的位会被随后的 `Player#tick` 首行清掉，撑不到下一次包处理。

两处相位性质：

- **末尾置位不改变本 tick 内实体自身的移动。** `Player#tick` 的 `aiStep` / `travel` / `Entity#move` 都跑在首行重置之后、末尾事件之前，仍按碰撞求解。这对本设计无害——位置每 tick 都被覆盖——不必去改首行那次赋值。
- **真正需要它为真的读点在 tick 之外**：`ServerGamePacketListenerImpl#handleMovePlayer` 在包处理时读它，而包处理跨 tick 发生，末尾置位恰好覆盖该窗口。这一条同时是 §5.3 客户端上行路径成立的前提。

**一条必须留意的副作用：原版的"飞行过久"检测。** `Entity#move` 在 `noPhysics` 为真时不再设置 `verticalCollisionBelow`，而 `ServerGamePacketListenerImpl#handleMovePlayer` 的 `clientIsFloating` 判据里有一项正取自它；该标志连续为真超过 `ServerGamePacketListenerImpl#getMaximumFlyingTicks` 的返回值（玩家重力 `0.08` 时为 `80` tick）就会以 `multiplayer.disconnect.flying` 断开连接。走路不受影响（脚下有方块时该判据的另一项不成立），但悬停、滑翔、喷气以及被外力顶在空中这类"高度不掉且周围无方块"的形态会被踢。规避方式是绑定期间授予飞行许可——在 `NeoForgeMod#CREATIVE_FLIGHT` 属性上挂一个修饰符，再调用 `net.minecraft.server.level.ServerPlayer#onUpdateAbilities` 同步给客户端——或由服务器开启 `allow-flight`。本项列入阶段 4 的实机验收。

### 5.3 位置权威：客户端上行，服务端采纳

**玩家实体的位置在原版里就是客户端权威的**（服务端无条件采纳客户端位置包，且从不把玩家自己的位置发给他本人的客户端）。本设计顺着这条既有路径走：**客户端按 `DATA_POS` 写自己的玩家实体，服务端自然收到**，服务端不需要每 tick 下发位置包。

#### 5.3.1 链路

```text
[物理线程] KCC 积分
[服务端] LevelTickEvent.Post
    → common/ArmsCoreServerEvents.java#syncToClients：DATA_POS = KCC 位置
    → MechaCoreSyncPayload 广播
[客户端] MechaCoreSyncPayload#handle 更新客户端 ArmsCore 的 syncedData
[客户端] PlayerTickEvent.Post（落在 LocalPlayer#tick 的 super.tick() 之内；`client/ClientHostPoseEvents.java#onPlayerTickPost`）
    → Minecraft.player 按 DATA_POS 写位置（胶囊中心 − HALF_TOTAL，见 §5.1）
    → 清 deltaMovement、写朝向
[客户端] LocalPlayer#tick 继续 → LocalPlayer#sendPosition
    → 位移超阈值或满 20 tick 时发 ServerboundMovePlayerPacket
[服务端] ServerGamePacketListenerImpl#handleMovePlayer
    → noPhysics 为真（§5.2）→ 采纳位置，跳过"移动错误"回拉
```

**位置回写是过渡态。** 上面链路里的服务端位置回写由 `docs/宿主位置权威与位移摄入设计.md` §九 第 4 步删除，该文 §5.3 的检测层与 §6 的动作层接管「外部位移如何进入控制器」；客户端那一侧的回写本身由该文 §5.6 处理。

#### 5.3.2 客户端写的位置赶得上发包

`net.minecraft.client.player.LocalPlayer#tick` 的顺序是 `super.tick()`（整个 `Player#tick`，末尾派发 `PlayerTickEvent` 的 `Post`）**然后**才调用 `LocalPlayer#sendPosition`。因此在 `PlayerTickEvent.Post` 里写的位置会被本 tick 的位置包带上。`LocalPlayer#sendPosition` 的发包条件是位移平方超过 `2.0E-4`（约 `0.014 m`）或累计 20 tick；KCC 的行走速率远高于前者，因此移动中每 tick 都发包，静止时退化为每 20 tick 一次。

#### 5.3.3 服务端的位置回写不能放在 `PlayerTickEvent.Post`

服务端玩家不在 `Entity#tick` 路径上：`net.neoforged.neoforge.event.tick.PlayerTickEvent` 的类注释写明服务端依赖 `ServerPlayer#doTick`，而它由 `ServerGamePacketListenerImpl#tick` 调用。而 `ServerGamePacketListenerImpl#tick` 在调用 `doTick` 之后**紧接着**把玩家位置重置为本次连接 tick 开始时记录的基准坐标。在 `PlayerTickEvent.Post` 里写的服务端位置会被这一步直接抹掉。

因此两个量分处两个相位，不能合并成一个订阅者：

| 量 | 服务端相位 | 客户端相位 |
| --- | --- | --- |
| 位置、朝向 | `LevelTickEvent.Post`（与 `common/ArmsCoreServerEvents.java#syncToClients` 同相位） | `PlayerTickEvent.Post`（`client/ClientHostPoseEvents.java#onPlayerTickPost`） |
| `noPhysics` | `PlayerTickEvent.Post` | `PlayerTickEvent.Post` |

两端各有一个订阅者，且**客户端那一个必须单独成一个标注 `Dist.CLIENT` 的类**：`net.minecraft.client.player.LocalPlayer` 只在客户端发行版里存在，把它写进双端共用的类会让专用服务端在构造事件订阅者时就去解析该类，加载期直接报「Attempted to load class net/minecraft/client/player/LocalPlayer for invalid dist DEDICATED_SERVER」。因此双端一致的那一半（`noPhysics` 与坠距重置）放在 `common/PlayerHostEvents.java#onPlayerTickPost`，客户端专属的位姿落地放在客户端包内。

服务端放在 `LevelTickEvent.Post` 是安全的：该相位在关卡循环内触发，而 `ServerGamePacketListenerImpl#tick` 的基准记录发生在其后的连接相位，写入的坐标会被原样保留。

**`noPhysics` 只豁免"移动错误"回拉，不豁免"移动过快"检测。** `net.minecraft.server.network.ServerGamePacketListenerImpl#handleMovePlayer` 里两条判据的位置不同：`noPhysics` 出现在 `serverlevel.noCollision(...)` 那条合取式的最前面，而"移动过快"是更早的一次独立判断——比较 `d10 - d9 > f2 × i`，其中 `d10` 是客户端上报位置与本连接 tick 基准坐标的位移平方、`d9` 是服务端玩家当前 `getDeltaMovement().lengthSqr()`、未处于鞘翅飞行时 `f2` 取 `100`、`i` 为本 tick 收到的位置包数（上限 5）。它是"位置相对上一基准跳了多远"的绝对量测，因此宿主实体每 tick 被外部搬动时这条检查照常生效。

`d9` 项让正常行走与冲刺都远低于阈值（每 tick 位移 1 m 时 `d10 = 1`，而阈值是 `100` 量级），但两类动作会踩到它：单 tick 内被搬动超过约 10 m，以及客户端在一 tick 内连发多个位置包使 `i` 抬升。前者的规避手段是搬动改走 §5.3.4 的 `teleport`（它同时进入"等待客户端确认"状态，期间位置包被整体忽略），后者不需要处理——`i > 5` 时服务端自身会把它夹回 1。

#### 5.3.4 `player.teleport` 的定位：校正，不是常态

稳态不需要 `net.minecraft.server.network.ServerGamePacketListenerImpl#teleport`。它保留给三类场合，并作为兜底：

- 位置确实跳变（`common/ArmsCore.java#enterPhysicsSpace` 之外对 KCC 的显式搬动）；
- 传送、换维度、重生；
- 客户端掉帧或丢包导致服务端代理停在原地。

**"按阈值判断位置是否偏了"只能用作兜底，不能用作外部位移的判据。** 两者问的不是同一个问题：兜底问「KCC 是不是已经明显偏离实体」（判据宽、容忍误判，触发代价是多一次传送），检测问「这次写入是不是外部位移」（判据窄，漏判会让整条回路吃掉一次 `/tp`）。`docs/宿主位置权威与位移摄入设计.md` §5.4 否掉的是后者——阈值小则稳态滞后每 tick 误判、大则小距离传送漏判，两边都无解；该文的位移检测改为调用点枚举式的分类（§5.1 的四类 + §5.3 的锚点）。本节与该文的 §5.3.6 所要求的兜底因此仍然需要，落点见 `docs/宿主位置权威与位移摄入设计.md` §6.2 的 pin 预算。

**本项目不按"与出生点的偏移"做兜底。** KCC 的位置就是宿主实体的位置（§5.1），因此以入世点为锚点、偏移超限就把 KCC warp 回去的判据会把一个正在正常行走的机体拉回出生点——它与"KCC 位置即玩家位置"直接冲突。触发条件是玩家离开出生点超过阈值，表现是走到一定距离后被拽回。需要兜底时应改为按"实体上报位置与 KCC 位置之差"判断，而不是按与出生点的距离。

它有一个别的手段没有的效果，值得知道：绝对式 `net.minecraft.network.protocol.game.ClientboundPlayerPositionPacket` 在客户端会把 `deltaMovement` 清零，并把插值用的上一帧坐标一并设到目标点，因此是硬贴合、无拖影；同时它让服务端进入"等待客户端确认"状态，期间客户端的位置包被整体忽略——等于一个服务端夺回位置权威的开关。

#### 5.3.5 客户端写位置时必须一并清速度

客户端自己调用 `net.minecraft.world.entity.Entity#setPos` 不会清 `deltaMovement`，而下一 tick 的 `aiStep` / `travel` 会按客户端自己的速度把实体再推走。因此客户端订阅者在写位置后必须显式把速度写为零矢量（`net.minecraft.world.entity.Entity#setDeltaMovement`）。原版处理 `ClientboundPlayerPositionPacket` 的 `net.minecraft.client.multiplayer.ClientPacketListener#handleMovePlayer` 就是这么做的。

#### 5.3.6 残留风险

| 风险 | 说明 |
| --- | --- |
| 服务端代理滞后 | 服务端玩家位置来自客户端上行，比 KCC 落后约 1 至 2 tick。可达性校验、拾取、AI 索敌都读服务端位置，这些语义整体滞后同样的量。单机客户端与服务端同机，滞后不可见；专用服务器上是既定代价 |
| 客户端停顿时服务端代理冻结 | 客户端不再发包时服务端位置停住而 KCC 继续推进；客户端恢复后由下一次 `DATA_POS` 拉回。需要 §5.3.4 第一条的阈值兜底 |
| 反作弊 | §5.2 末段的"飞行过久"检测 |
| 客户端可信性 | 玩家位置由客户端上报意味着客户端可以伪报位置。这与原版对玩家的信任级别相同，不是本模组引入的新风险；但由此**服务端位置不能被当作反作弊判据** |

#### 5.3.7 外部位移的摄入

本节描述的链路是**稳态**：宿主位置每 tick 由 KCC 产出，客户端按 `DATA_POS` 跟随，上行的位置包只带来这套闭环自身的滞后回声。

一旦有本模组之外的写入改变宿主实体的位置（`/tp` 与 `/execute … run tp`、`/spreadplayers`、末影珍珠、紫颂果、旁观者相机切换、起床、骑乘、其它模组调用传送 API），闭环的两处回写会把这次位移抹掉：`client/ClientHostPoseEvents.java#onPlayerTickPost` 在客户端用旧 `DATA_POS` 覆盖它并把旧位置重新上报，`common/ArmsCoreServerEvents.java#applyPoseToHost` 在服务端用旧 KCC 位置覆盖它，而 KCC 全程不知道这次位移。净结果是传送瞬间到达目标、随后两端都回到原位。

处置方案——**写入来源分类 + KCC warp + 位姿钉住，并规定乘客态的位置权威在载具**——见 `docs/宿主位置权威与位移摄入设计.md`（含原版位移路径地图、四类写入的判据、验收矩阵与残留风险登记）。该文是待实施设计。**它会改动本文 §5.1 至 §5.3.6 里的两处**：§5.1 的「位置」一行与 §5.3.3 末段的服务端位置回写，由该文 §九 第 4 步删除（速度那一笔保留），理由是那笔写入正是覆盖外部位移的两处回写之一；§5.3.4 的阈值兜底与它并存而不冲突（判据不同，见该节）。

## 六、原版交互

主机形态下这些全部沿用原版，不需要额外实现：

| 能力 | 依赖 |
| --- | --- |
| 挖方块 / 放置方块 | 准星射线从相机实体出发、`reach` 取自玩家实体，两者是同一个对象 |
| 拾取掉落物 | 玩家实体就是服务端那个实体 |
| 快捷栏 / 背包 / 用物品 | 客户端按键逻辑作用于 `Minecraft.player` |
| 与方块交互（箱子、工作台等） | 方块交互的服务端可达性校验同样以玩家实体的眼位为基准 |
| 区块加载 / 实体追踪 | 玩家实体的位置即 KCC 的位置 |

**一条硬约束**：玩家实体的眼位必须与相机实际使用的位置一致。原版的准星射线起点是相机实体眼位，而服务端对可达性的校验用的是玩家实体的眼位；两者若出现系统性偏移，客户端会瞄准一个服务端认为够不到的方块，表现为"瞄得准但挖不动"。若为第一人称视角在 `Camera` 上加偏移，必须同步调整玩家实体的眼高，而不是只动相机。

**第二条硬约束**：命中几何来自实体包围盒，而机体轮廓来自 KCC 胶囊，两者不是同一个体积。原版的投射物求交（`entity.getBoundingBox().inflate(pickRadius).clip(from, to)`）与近战射线都以 `net.minecraft.world.entity.Entity#getBoundingBox` 为准，而胶囊（直径 `0.8`、全高 `2.4`）比 `net.minecraft.world.entity.player.Player#STANDING_DIMENSIONS` 的 `0.6 × 1.8` 更宽更高。本阶段有意让命中体积停在包围盒上（§4.8.2 末段），代价是机体高出 `1.8 m` 的那一段不可命中、§4.8.1 的分区按 `1.8 m` 归一化。把它接到胶囊上的入口与两个陷阱见 §八 第 12 项。

**一条已经落地的视觉分支：玩家模型被取消，改画机体。** 有机体时 `client/MechaPlayerRenderer.java#onRenderPlayerPre` 在 `net.neoforged.neoforge.client.event.RenderPlayerEvent#Pre` 上取消原版玩家渲染，并把占位模型就地画在同一位姿上。取消是"整具让位"——玩家模型连同其全部 `RenderLayer`（护甲、手持物、披风、鞘翅）与实体阴影一并消失；名称牌是独立的渲染通道，不受影响。

**这一分支只改视觉，不改任何判据。** 包围盒、眼位、`reach`、实体追踪都仍按玩家实体的原版尺寸走，因此"看到的机体比能打中的体积大一圈"是当前形态的固有现象（上一条硬约束说的同一件事），不是渲染缺陷。要消除它必须把命中体积与包围盒接到胶囊上，属 §八 第 12 项。

**模型的位姿取自宿主实体自身，与 `DATA_POS` / `DATA_YAW` 无关。** 渲染事件传入的 `PoseStack` 已经位于该玩家的渲染原点（原版按部分 tick 插值），朝向取宿主的**头朝向**：本机玩家是 `net.minecraft.world.entity.Entity#getYRot`（与上行同源、零延迟），其他玩家是 `net.minecraft.world.entity.LivingEntity#yHeadRot` 的相邻 tick 插值结果，两者都不经过同步通道。`DATA_POS` 因此只剩两个消费者：`client/ClientHostPoseEvents.java` 摆放客户端玩家的实体位置，以及供外部查询。这是刻意的——同步延迟不进渲染路径。

**朝向为什么取头朝向而不是 `yBodyRot`。** `yBodyRot` 是原版按**移动方向**推进的身体朝向（`LivingEntity#tick` 里以本 tick 水平位移² > 0.0025、即 > 1 m/s 为门槛，目标角取移动方向），并被 `LivingEntity#tickHeadTurn` 把「头 − 身体」夹角夹在 ±50°（`Player#getMaxHeadRotationRelativeToBody`，格挡时 15°）。而控制器的朝向权威是上行载荷里的 `viewYaw`，它在客户端读的就是 `Entity#getYRot()`：玩家身上 `yHeadRot ≡ getYRot()`（服务端 `Player#serverAiStep` 置值）。两者在横移（身体停在视线 ∓ 50°）与原地转视角（身体几乎不动）时可差到 50°，因此机体朝向必须取头朝向这一侧，才能与 KCC 的朝向、以及 WASD 的参照系一致。

## 八、已知风险与待确认项

| # | 项 | 说明 |

| 1 | 拦截点的位置由协议决定 | 玩家的受击转发由 `BallisticsFramework` 的 `LivingEntityHurtMixin`（注入 `LivingEntity#hurt` 的 HEAD）承担，见 §3.4。本仓库不实现自己的 `hurt` 钩子，因此"钩子挂在 `Player#hurt` 还是 `ServerPlayer#hurt`"这个问题不存在。代价是拦截点位于 `Player#hurt` 自身检查（创造模式无敌、死亡判定、难度缩放）**之下**：这些检查拒绝的伤害不会进入机甲管线，而 `super.hurt` 之前的 `ServerPlayer#hurt` 检查（`spawnInvulnerableTime`、PvP 许可）拒绝的伤害同样不会。两条路径的语义都正确 |

| 10 | 持久化 | 本次落地不做正反序列化：断线只注销装配体并解绑，重启与重连后玩家回到人类形态（与 §3.1.3 的"登录 → 无机体"一致）。将来接入持久化路径时，形态与 `docs/总体设计文档.md` §2.1 的"宿主 NBT + Capability 序列化"对齐；届时它同时会成为 §3.1.3 里"跨维度重建"那一行的状态来源——现在那一行只能重建出复位状态的新机体 |

| 12 | 命中体积与胶囊不一致 | 命中判定用实体包围盒（`0.6 × 1.8`），机体轮廓用 KCC 胶囊（直径 `0.8`、全高 `2.4`），后果与分区基准见 §4.8.2 与 §六第二条硬约束。接入入口是覆写 `net.minecraft.world.entity.player.Player#getDefaultDimensions`（非 final）。`net.minecraft.world.entity.EntityDimensions` 由 `net.minecraft.world.entity.Pose` 索引，双端都会调用，因此**不需要网络同步**。三个注意点：其一，`net.minecraft.world.entity.player.Player#updatePlayerPose` 会用 `net.minecraft.world.entity.player.Player#canPlayerFitWithinBlocksAndEntitiesWhen` 逐级降级，包围盒升到 `2.4 m` 后站在低矮空间会自降为 `CROUCHING` / `SWIMMING`，而 `setPose` 又会再次触发尺寸重算，表现为尺寸与眼高在数帧内反复跳；其二，`net.minecraft.world.entity.Entity#getEyeHeight` 必须一并覆写，否则 §六第一条硬约束立刻失效；其三，`net.minecraft.world.entity.Entity#getBbHeight` 是 `api/BFArmorMaterial.java#mapHitToSlot` 计算着弹槽位的分母，改尺寸会连带改变贴身护甲的槽位选择，需要一起回归 |
| 13 | 绑定关系的唯一性 | **一个宿主实体至多绑定一个装配体**（§二 的绑定字段是单值），但反方向没有上限：同一时刻可以有多个装配体都持有指向同一个玩家的宿主引用，此时"谁是机娘"这个问题有两个答案。因此绑定字段的写入方法必须在写入新值之前先解除旧值的绑定，判定点与 §3.1.3 的规则表同一处。同一玩家所在维度里已经存在一个未绑定的装配体时（例如断线注销漏做、或调试命令建了多个），玩家不会自动认领它 |
| 14 | 伤害解析的幂等性与宿主位置 | §4.7.1 第 1 条要求同一组 `(hitPoint, delta)` 恒返回同一结果，而 §4.8.2 的求交对象是宿主包围盒，它的位置每 tick 被 §5.2 的位姿回写覆盖。同一次命中若横跨两次 tick 被解析（投射物在 `net.minecraft.world.entity.projectile.Projectile#onHit` 解析一次、`hurt` 阶段缓存未命中再解析一次），分档可能落进不同 Y 区间。**本阶段不为此冻结状态**：单 tick 内"命中 → 结算 → 投递"不跨 tick，而求交对象在装配接入后会从宿主包围盒换成零件碰撞形状，这条限制随之消失。实现时在该处写一条注释登记本项即可 |

| 15 | 外部权威位移的摄入 | **未落地。** §5.3 的稳态链路不覆盖「本模组之外的写入改变宿主实体位置」：`client/ClientHostPoseEvents.java#onPlayerTickPost` 与 `common/ArmsCoreServerEvents.java#applyPoseToHost` 两处回写会把 `/tp` 一类的位移抹掉，KCC 不跟随，表现为到达目标后被吸回原位。方案、路径地图与验收见 `docs/宿主位置权威与位移摄入设计.md`。同源但机制不同的另一项是外部冲量（击退、爆炸、`net.minecraft.world.entity.Entity#push`）：宿主实体的 `deltaMovement` 每 tick 被 KCC 速度覆盖，实体自走量又被 `net.minecraft.server.network.ServerGamePacketListenerImpl#tick` 的基准复位抹掉，因此外部冲量目前不产生效果，登记在该文 §八 第 6 项 |

**第 1 项的推论**：协议侧不需要为本模组补玩家类的注入，本仓库也不需要。玩家受击的守卫与转发完全由 `BFHurtInterceptor` 的情况 3 完成，本仓库提供的只是 `resolveHit` 一个方法。

## 九、实施顺序

1. **宿主接口与绑定字段**：新建 `common/IArmsHost.java`（§3.1.1 的方法集）；`@Mixin(Player.class)` 声明 `implements IArmsHost`，注入绑定字段与读写方法，`getHostEntity()` 返回自身；`ArmsCore` 持有 §3.1.2 的宿主引用（可空，绑定建立时运行时注入，三条使用路径按该节的空值规则表处理）；绑定字段的写入方法必须先解除旧装配体的绑定，使一个宿主实体至多绑定一个装配体（§八 第 13 项）；`common/MechaInputHandler.java` 的控制权表并入绑定字段（§6.3 的表）；创建包携带真实 `hostEntityId`，客户端只在它与本地玩家 id 相等时填自己的字段（§3.1）。三个方向的解绑都要做：宿主字段的写入、注册表注销（`common/MechaCoreRegistry.java#removeServer`、`#onLevelUnload`）、以及客户端移除包（`network/payload/ArmsCoreRemovePayload.java#handle`）——只清注册表会让玩家仍以为自己是机娘而输入路径找不到装配体。
2. **位置与朝向回写**：服务端在 `LevelTickEvent.Post` 经 §3.1.1 的宿主接口写位姿与速度（`common/ArmsCoreServerEvents.java#applyPoseToHost`），位置按 §5.1 换算到包围盒底面，换算由宿主实现承担；客户端在 `PlayerTickEvent.Post` 按 `DATA_POS` 写自己的位置并清速度（`client/ClientHostPoseEvents.java#onPlayerTickPost`）；两端的 `noPhysics` 都在 `PlayerTickEvent.Post` 置位，配套重置坠落距离（`common/PlayerHostEvents.java#onPlayerTickPost`）。三个读取量都是主线程可读的：`common/control/MechaCharacter.java#getPhysicsLocation`、`common/control/MechaCharacter.java#getLinearVelocity`、`common/control/MechaCharacter.java#currentYaw`（`common/ArmsCoreServerEvents.java#syncToClients` 已在同一相位读它们），不需要新开跨线程通道。
3. **`resolveHit` 的实现**（放在 `ArmsCore`，Mixin 只转调，§4.7）：`@Mixin(Player.class)` 声明 `implements BFHitResolver`；`ArmsCore` 内选区域并把命中几何写进 `BFHitResolveResult`。装配尚未接入期间，被命中的目标是 §4.8 的三个临时区域，分档按 §4.8.2 先与宿主包围盒求交。这一步之后服务端玩家受击即自动解析到区域、投射物也自动获得精确命中判据（§4.7.3），无需本仓库做任何守卫（§3.4）。
4. **`ArmsCore` 侧实现汇总与投递**：建立 §4.8.6 的统一伤害账本，投递单开一个 `EventPriority.LOW` 的订阅者；装配接入前由 §4.8 的区域入队，接入后覆写 `Machine-Max` 的 `IPartAssembly#onPartDamage(Part, List<SubPartHitDamage>)`（`common/ArmsCore.java` 的同名单参方法是空实现，批次重载未被覆写，因此当前走接口默认实现后被丢弃）。两条来源共用同一次 `BFDamageApi.deliverTo` 投递回宿主实体。**本步的前置改动**：给 `common/control/MechaControl.java#LogicStateSnapshot` 增加无敌窗口字段并同步 `common/control/MechaControl.java#snapshotLogicState`，然后投递前读该快照字段、把结果并入可受击窗口的判定（§八 第 5 项）。
5. **装配体生命周期**：按 §3.1.3 的规则表接线——断线注销并解绑（不做序列化）、`PlayerEvent#Clone` 一处判完残骸 / 跨维度重建 / 同维度保留三档、`PlayerEvent#PlayerChangedDimensionEvent` 处理跨维度搬迁，以及环境字段在过渡时刻的来源规则（§八 第 8 项）。

### 10.3 已知与设计不符之处

- **飞行许可的收回不还原玩家原值。** `#armsCore$syncFlightAbility` 解除绑定时只移除自己那个修饰符、并把 `flying` 置假；它没有记录"玩家此前是否本来就能飞"。创造模式玩家的飞行许可由游戏模式提供、与本修饰符无关，因此不受影响；但如果将来有别的模组也用这个属性授权，"收回"只会撤掉本模组的份额——这正是选择属性而不是直写 `Abilities#mayfly` 的原因，此处记录以免与 §八 第 5 项（无敌窗口）一类真正的缺口混淆。
- **渲染路径的位姿与同步通道解耦。** 模型位置取宿主实体的渲染原点、朝向取宿主头朝向（本机玩家 `net.minecraft.world.entity.Entity#getYRot`、其他玩家 `net.minecraft.world.entity.LivingEntity#yHeadRot` 的插值结果），两者都不过同步通道；`DATA_POS` 只用于摆放客户端玩家实体。因此 `client/ClientMechaAnchor.java` 的插值结果当前只服务于 `client/MechaAnimatable.java#getWorldPositionMatrix`，而本模组不经过那条通用渲染路径（`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/renderer/IGeoRenderer.kt#render`），属待清理项而非缺口。
