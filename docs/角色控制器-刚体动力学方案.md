## 1. 背景与目标

### 1.1 现行控制器与它的三个阻断性问题

现行的运动学胶囊控制器是 `common/control/MechaCharacter.java`，它继承 `com.jme3.bullet.objects.PhysicsCharacter`，承载 Bullet 的 `btKinematicCharacterController`（下称 KCC）。KCC 不是刚体，而是「幽灵体 + 手写三段扫掠 + 纯速度推导着地」，没有质量。由此派生出三个**阻断性**问题——它们不是"不够好"，而是相关能力**做不到**：

| # | 问题 | 证据坐标 |
| --- | --- | --- |
| 1 | **姿态轮廓无法接入**（蹲伏 / 卧倒的低矮胶囊） | `PhysicsCharacter#setCollisionShape` 带「不得在物理空间内」的断言；在世换形会让原生侧挂接一个未重建的碰撞对象，原生内存被破坏，进程以 `0xC0000409` 中止。因此 `MechaCharacter.java#applyPostureShape` 是一个永远返回 `false` 的弃用壳，`common/control/MechaControl.java#applyLogicOutputToKcc` 里对应的换形代码是注释掉的 |
| 2 | **撞墙时速度不归零** | KCC 的水平通道是「本步位移命令」，原生侧从不把实际走了多远写回，因此顶墙期间 `getLinearVelocity` 仍报告那份没能执行的命令（登记为 `docs/角色控制器-KCC制约调研与替换评估.md` §3.2 的 `B1`、`B2`；上游报告 `https://github.com/stephengold/Libbulletjme/issues/58`） |
| 3 | **无质量、不受外力** | 幽灵体不产生也不承受冲量，因此外部冲量（击退、爆炸）与子系统合力都没有可施加的对象——`common/control/MechaControl.java#addSubsystemForce` 至今是空实现，没有消费方 |

### 1.2 本方案替换什么、不替换什么

**替换**：只替换「动起来」这一层——从运动学胶囊换成动力学刚体胶囊，并随之重写接触摩擦、速度语义与落地处理的归属。

**不替换**：

- 双体结构。控制器仍是胶囊，躯干仍是动力学刚体，两者由约束相连，胶囊为躯干提供约束位姿（`docs/角色控制器-行走物理设计.md` §1.2）。
- 服务端权威、客户端零仿真（`docs/ArmsCore双端权威与网络同步实现计划.md` D1、D18）。
- 逻辑层与物理层的分工：状态机、动画、MoLang 调制**不动**（承载物换掉之后它们消费的仍是同一份输入与快照），`MechaControl` 仍是编排者。

### 1.3 可行性已实测

这条路线的关键未知——引擎是否提供所需能力——已用最小原型在真实 `PhysicsSpace` 上量过：锁转刚体的站立稳定性、撞墙速度归零、自写越障的判决阈值、引擎摩擦的标定、姿态自由度与角因子、地面姿态控制方案对照、落地摆正。全部数据与四条实现坑见 `docs/角色控制器-刚体原型与引擎约束.md` §2–§11。

## 2. 动力学代理

### 2.1 胶囊承担什么

角色在物理世界中由**一个胶囊刚体**表示，承担：

- 与场景几何体的碰撞求解；
- 位置积分与速度积分；
- 接收所有合力与合力矩；
- 为躯干约束、布娃娃与视觉提供位置与姿态参考。

胶囊**不对应可见形体**。可见形体由布娃娃节点或程序化动画承担；胶囊仅作为物理代理存在，命中判定也不使用它——受击盒的来源属于可见形体那一层，随双体结构一起接入（§1.2、§12.3）。

### 2.2 四项已定型的选择

| # | 选择 | 内容 | 理由 |
| --- | --- | --- | --- |
| 1 | 承载物 | **动态刚体**（有质量、受求解器约束），不用运动学刚体 | 运动学刚体拿不到求解器的碰撞响应，滑墙、贴地、撞墙归零都要自己写，等于重写一遍 KCC；动态刚体让「被动响应」这一半回到引擎手里 |
| 2 | 姿态保持 | **分轴锁转**：`PhysicsRigidBody#setAngularFactor(Vector3f)` 逐轴给出旋转自由度的开关 | 该因子乘在角冲量/力矩的**累加处**，不修改逆惯量矩阵本身，因此 `(0, 1, 0)` 能同时做到「锁 pitch / roll 保持竖直」与「留 yaw 自由转身」。机制与实测见 `docs/角色控制器-刚体原型与引擎约束.md` §6 |
| 3 | 接触摩擦 | **引擎接管**：抓地、无输入制动与爬坡上限由求解器给出的法向力与引擎摩擦承担；控制力的饱和上限由控制器自己按 `m·g·cosθ` 与配置里的组合摩擦算，不读接触点的瞬时法向力 | 让引擎承担被动响应是选择动态刚体的初衷；逐方块材质差异（冰面 / 湿滑）走按接触点**写入**组合摩擦的路径（§7.5）。分层与理由详见 §7 |
| 4 | 碰撞过滤 | 控制器本体的碰撞组只与**地形**碰撞（组 `PAWN`、掩码 `TERRAIN`） | 与现行 `common/control/MechaCharacter.java` 一致，迁移期不引入新的碰撞对；与躯干的碰撞由约束层处理，不靠碰撞组 |

## 4. 姿态自由度

### 4.1 状态划分

| 状态 | `angularFactor` | 姿态权威 |
| --- | --- | --- |
| 地面站立 / 行走 | `(0, 1, 0)` | 每物理步写入朝向（yaw 取视野偏航）；pitch / roll 锁死，不需要姿态控制器 |
| 落地 / 进入地面 | `(0, 1, 0)` + 运动学收敛 | 姿态写入：朝向每物理步、倾斜由收敛律，见 §4.1 下文与 §5 |
| 飞行 / 悬浮 | `(1, 1, 1)` | 飞行控制层，见 §12.2 |
| 布娃娃 | `(1, 1, 1)` | 无（朝向写入一并停用，与现行 `applyFacing` 在死亡 / ragdoll 时跳过一致） |

`(0, 1, 0)` 的语义是「锁 pitch / roll、留 yaw」：站立必须竖直，但朝向可以自由旋转。因为该因子只按**轴**过滤，绕 Y 轴的角冲量（包括力臂产生的偏航力矩）仍然完整生效。

**yaw 由位姿写入驱动，并且是躯干的目标朝向。** 本方案的地面力全部施加在质心上、接触法向也过质心，偏航轴上没有任何**力矩**来源，因此朝向不走力矩通道：每物理步在朝向写入点把视野偏航绝对写进刚体姿态（§6.1 的位姿写入），得到的胶囊朝向即躯干的目标朝向——双体层接入后由约束 / 伺服消费（§1.2、§12.3）。

yaw 轴保持自由有两个理由：**① 让约束能双向作用**。约束冲量与接触冲量在求解器里同样要乘角因子（`../Libbulletjme/src/main/native/bullet3/BulletDynamics/ConstraintSolver/btSolverBody.h#applyImpulse` 里 `m_deltaAngularVelocity += angularComponent * (impulseMagnitude * m_angularFactor)`），全锁会把偏航分量整段丢掉，约束的相对朝向需求就只能由躯干一侧承担，胶囊在偏航上退化成不可被改变的参考体。**② 朝向写入与角因子互不干扰**：`setPhysicsRotation` 不经角冲量通道（§5.2），所以「yaw 轴自由」与「朝向绝对复现」可以同时成立。

### 4.2 为什么地面不用 PD 姿态控制器

一个自然的想法是让旋转自由度全开、用条件启用的 PD 姿态控制器同时满足「地面稳定」与「空中自由」。**空中那一半成立，地面这一半实测不成立**：六组增益下胶囊全部先翻过头（最大倾角 178.66°–179.89°）并被弹离地面（脚底升到 +0.75 ~ +1.08 m），末倾角散在 0.58° 到 102° 之间。

机制是**单接触点**：胶囊只通过一个接触点与地面作用，任何绕质心的回正力矩都无法产生「把接触点移回质心正下方」的效果，反而主动把接触点甩到质心侧面，接触法向力随之出现向上的分量，胶囊起飞后进入自由翻滚。这是拓扑的固有形态，不是调参问题——完整数据与解释见 `docs/角色控制器-刚体原型与引擎约束.md` §7。

因此地面状态**不引入任何姿态控制器**，直接用角因子锁死。这也让「站立必须竖直」与「方向自由」这两个需求由同一个参数满足，比 PD 少一整层。

### 4.3 PD 归属飞行控制层

PD 的输入是期望姿态 / 期望角速度、输出是力矩，落点在飞行控制层（意图 → 力矩的路径），本文不展开。两条无论它落在哪一层都必须遵守的实现约束记在 `docs/角色控制器-刚体原型与引擎约束.md` §7.2（角加速度必须限幅；逆惯量为 0 的轴必须跳过）。

**角因子的切换点只有一个。** §4.1 那张表里的每一行都由同一处代码写 `setAngularFactor`——`common/control/MechaControl.java` 里与姿态自由度状态机绑定的那一处（§9.4 的活行掩码表也从它导出）。飞行控制层接入时，起飞放行那一跳（`(0, 1, 0)` → `(1, 1, 1)`）落在这同一处，不另建门控表；这条是落点约定，与飞行控制层的其余设计无关。

## 5. 落地处理

落地要解决两件事：把已经歪掉的姿态**摆正**，以及让姿态**此后再也不歪**。前者只能靠姿态写入，后者靠角因子锁死；两者可以在同一个物理步里同时开始。

### 5.1 锁与摆正是两个独立动作

**锁只负责「不再改变朝向」，不会把已经歪掉的姿态扶正。** 实测：躺倒 90° 的锁转胶囊静置 3 s 仍是 90.0000°、角速度恒为 0——胶囊水平躺地时重力过质心、接触法向也过质心，合力矩为零，是中性平衡。因此摆正必须由姿态写入完成，省不得。数据见 `docs/角色控制器-刚体原型与引擎约束.md` §8.1。

### 5.2 落地第一步即锁，而且只锁 pitch / roll

`PhysicsRigidBody#setPhysicsRotation(Quaternion)` 是直接的位姿写入，不经角冲量通道，因此**不受角因子影响**。这一条让「锁」与「摆正」不必分阶段：落地第一个物理步就把角因子写成 `(0, 1, 0)`，同一步开始收敛，不存在「先留自由度做收敛、收敛完再锁」的那个窗口，也就不需要为一个窗口设计打断条件。

实测这个配置（初态绕世界 X 轴 30° 纯俯仰）把求解器在收敛窗口内注入的 pitch / roll 角速度完全挡在门外：峰值 pitch / roll 角速度 **0.0000 rad/s**、水平位移 **0.0000 m**、朝向漂移 **0.0000°**。对照组在收敛期保持全开，注入的 pitch / roll 角速度随 `λ` 增大而减小（λ=0.05 → 0.722、0.10 → 0.112、0.20 → 0.074、0.35 → 0.061 rad/s），且 **λ=0.05 时根本收不住**——2 s 内没收敛，胶囊被推着水平漂了 0.82 m。数据见 `docs/角色控制器-刚体原型与引擎约束.md` §8.2。

**为什么留 yaw 不锁它。** 三条理由：

1. **锁 yaw 拦不住它想拦的东西。** 角因子只作用在角冲量 / 力矩的**累加处**，不作用在积分处：`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btRigidBody.h#applyTorque` 是 `m_totalTorque += torque * m_angularFactor`，`#applyTorqueImpulse` 是 `m_angularVelocity += m_invInertiaTensorWorld * torque * m_angularFactor`，而 `m_angularVelocity` 本身没有任何一处被乘以该因子。落地那一帧自带的 yaw 角速度照转不误，清掉它是 §5.3 的活。
2. **yaw 不与姿态写入打架。** §5.3 读的是**当前**姿态，物理步里新产生的 yaw 会在下一步被读进去、当作既定朝向保留。互相打架的只有 pitch / roll。
3. **地面阶段只切换一次姿态自由度。** 若收敛窗口锁 yaw，角因子会走 `(1,1,1) → (0,0,0) → (0,1,0)` 三段，分配问题的行表随之 6 → 3 → 4（`docs/控制分配-作动器wrench分配设计.md` §8）。留 yaw 就是 6 → 4 一次切换，与 §4.1「地面 = `(0,1,0)`」一致。

三条理由说明「留 yaw 不比锁它差」；它「必须留」的理由在别处——**yaw 是胶囊与躯干之间那条朝向通道**（§4.1）：约束冲量的偏航分量要走角冲量通道，全锁会把它丢掉。朝向本身由每物理步的位姿写入驱动，因此留 yaw 不会留下无人管理的自由度。

### 5.3 收敛律

每物理步施加一次姿态写入，全部输入都取自**该步开始时的当前姿态**：

```
u     = 当前姿态下刚体局部 +Y 的世界方向
tilt  = u 与 (0, 1, 0) 的夹角
最小旋转：轴 = (u × (0, 1, 0)) 的单位化，转角 = λ · tilt
f     = 当前姿态下刚体局部 +Z 的水平投影方向
朝向误差：绕世界 Y 轴把 f 转到视野偏航，转角 = 该二方向的有符号夹角
合成：先施加朝向写入，再按新姿态施加倾斜写入（各步各一次）
锁       倾角 < 阈值 → 清角速度，角因子 → (0, 1, 0)
ω        pitch / roll 分量 ← × (1 − λ)；yaw 分量不动
```

**两个修正量都每步现算，任何一步都不缓存、不复用上一拍的旋转量。** 写入是幂等的绝对对齐而不是增量累加：本步开始时刚体既吃了上一拍的写入、也吃了求解器在上一拍注入的角速度，而两个误差都从这份当前姿态重新量出来，因此写入之后朝向恒等于视野偏航、上轴按 `λ` 记一次衰减，与上一拍被转走多少无关。这条纪律必须写进实现：把修正四元数缓存下来的版本在求解器每拍都注入偏航角速度时才会累积误差，而两种写法在代码上只差一行、在数值上一个累积一个不累积（本仓库的朝向观测量是 `RigidBodyControllerPrototypeTest.java#yawDegrees`）。

旋转轴垂直于倾角平面，把 `u` 沿「过 `u` 与竖直方向的大圆」拉向竖直，因此 `tilt ← (1 − λ) · tilt` 严格成立，时间尺度可以直接由 `λ` 算出：从 30° 收敛到 0.5° 需要 `ln 60 / ln(1/(1−λ))` 步，λ = 0.05 / 0.10 / 0.20 / 0.35 分别是 80 / 39 / 19 / 10 步。该步只用得到 `tilt` 一个角：`u × (0, 1, 0)` 的模长恒为 `sin(tilt)`，除以模长即得单位轴，`acos`、`asin`、`atan2` 都不出现。

角速度的 pitch / roll 分量按同一系数衰减，yaw 分量不动（§5.2 第 2 条）。衰减不是可选项——即便锁转已经挡住求解器的角冲量，落地那一帧自带的角速度仍在，不清掉会与姿态写入互相打架。**yaw 分量不需要清**：它每步被朝向写入重设（下文），残留只表现为步内的那一小段转动。

**朝向写入与收敛写入正交，同一步里各施加一次。** 朝向写入是绕世界 Y 轴、把局部 +Z 的水平投影转到视野偏航的一次旋转；收敛写入是绕水平轴、把上轴拉向竖直的一次旋转。绕世界 Y 的旋转不改变上轴与竖直方向的夹角，因此两者互不抵消：倾角衰减仍严格按 `tilt ← (1 − λ) · tilt`，而朝向每步被重设。先写朝向、再按**写入之后**的姿态算倾斜，两个目标的输入姿态因此是同一份、顺序也不再有可选项。

**朝向的残留量是步内转动，不是累积误差。** 写入把朝向对到目标的下一刻，本步剩余的角速度仍会把它转走 `ω_y·Δt`，直到下一步写回，因此朝向在目标附近摆动，幅度正比于求解器注入的偏航角速度、上界就是 `ω_y·Δt`，方向与大小每步重取、不跨步叠加。`docs/角色控制器-刚体原型与引擎约束.md` §8.2 的「朝向漂移 0.0000°」测的是**只施加收敛写入**、且初态为纯俯仰的形态，它不代表这个摆动。

**实测这个摆动根本不存在，因此不清 `ω_y`。** 平地上每步写 yaw、走 400 步：步内偏差峰峰值 **0.000000°**（写入前 / 写入后 / 步进后三个采样点都是 0），峰值 `|ω_y|` **0.000000 rad/s**，峰值 `|ω|` 也是 0；判据是 `src/test/java/io/github/sweetzonzi/arms_core/common/control/RigidBodyControllerMeasurementTest.java#measureYawJitterPerPhysicsStep`。原因是平地接触的求解器不向偏航轴注入角冲量（接触法线过质心、绕竖直轴的力臂为零）。因此「顺手把 `ω_y` 归零」这条兜底不接——它唯一的收益是丢掉引擎的偏航接触冲量。上界 `ω_y·Δt` 仍然是成立的写法性质，只是当前地形上右端为 0；地面接触几何变化（斜坡、台阶棱角）时它会变成非零，届时要重量。

**近躺倒时朝向写入必须让位。** `f` 取的是局部 +Z 的水平投影，`pitch` 超过约 90° 时该投影趋零，朝向误差的轴随之无定义。这种姿态只在「空中未收敛就再次落地」时出现，处置是跳过本步的朝向写入、交由上面的收敛写入摆正，等倾角回到可用范围再恢复——判据用同一个 `tilt`，落在阈值链的同一处。

**地面上的原地自旋没有可依赖的摩擦力矩。** 平地上接触点落在胶囊的对称轴上，自旋时该点没有切向相对速度，摩擦因此不产生衰减力矩。它不影响姿态——朝向每物理步由位姿写入重设，积分出来的偏航角下一步被覆盖；倾角小于阈值（原型取 0.5°）时清掉全部角速度，收敛结束，此后一直保持锁转。

`λ` 同时是「冲击吸收可见度」的旋钮：λ 越大立正越快、角速度丢得越干净；λ 越小，落地后「歪一下再站稳」的过程越看得见。

**单轴初态下朝向无偏，斜置初态下朝向会被带走，这是收敛律单独作用时的行为。** 绕水平轴旋转不改变**水平面内**矢量的方位角；纯俯仰与纯侧滚下局部 +Z 的水平投影恰好落在该平面内，所以走完全程朝向一动不动。倾斜方向斜置时该投影一般不在水平面内，每步被转走 `tilt · λ` 量级，累计量随倾角超线性增长——实测倾角 20.59° 给 0.93°、27.99° 给 3.53°、48.36° 给 6–11°、71.25° 给 29°、85.30° 给 57°。数据见 `docs/角色控制器-刚体原型与引擎约束.md` §8.4。

**在控制器里这一项不累积。** 朝向每物理步由位姿写入重设（§4.1），因此收敛写入在一步里转走的偏航在下一步被复位，偏差不会跨步叠加；原型 §8.4 那张表描述的是只反复施加收敛写入、不加朝向写入时的累计结果。

**旋转矢量不做「归一化」那一手。** 把 `(旋转矢量, 1)` 归一化成四元数，等价于把每步转角取成 `2·atan(‖r‖)` 而不是 `‖r‖`；`‖r‖ = 0.33` 时每步转角被放大到约 1.9 倍，倾角衰减明显快于 `(1−λ)`，把真实的时间尺度掩盖掉。正确形式是正则的轴角式——`sin(θ/2)` 作矢量部、`cos(θ/2)` 作标量部，其中 `θ = λ · tilt`。

**「上轴」与「朝向」是两个量。** `u` 只描述上轴歪向哪边、不含任何朝向信息：姿态竖直时 `u` 恒为 `(0,1,0)`，这个量在竖直处退化；纯俯仰 30° 时（`u = (0, 0.866, 0.5)`）它的水平投影只剩 `sin θ` 一项。由 `u` 反求一个「朝向」再据它拼目标姿态，目标本身就是错的——这是上面两条要避开的同一个混淆。

### 5.4 落地不需要平滑过渡

落地那一瞬间最容易出事的是姿态突变（穿地、弹跳）与比例增益产生的巨大角加速度。本方案里这两件事都没有来源：收敛窗口**没有任何力矩参与**，姿态每步只转 `λ · tilt` 那一小段；地面状态**没有比例增益**，角因子直接锁死，求解器的角冲量根本进不来。因此不需要引入「地面约束强度」之类的权重从 0 平滑升到 1，也不需要为它配落地前预判或缓和曲线——实测全程脚底最高 0.0000 m，从不弹起。

## 6. 速度与位姿写入

| 项 | 现行 KCC | 本方案 |
| --- | --- | --- |
| 量纲 | 水平两个分量是「每物理步位移」、垂直分量是 m/s，同一向量两种量纲（`docs/角色控制器-行走物理设计.md` §11） | 三轴同为 m/s |
| 撞墙时的读数 | 是没能执行的命令（`docs/角色控制器-KCC制约调研与替换评估.md` §3.2 `B1`） | 就是求解器给出的真实速度，被挡住即归零（`docs/角色控制器-刚体原型与引擎约束.md` §3） |
| 动画位移 | 与物理位移共用同一个水平通道，读速度时必须扣掉自记账的叠加量（KCC 承载时期的 `overlayDispX` 字段） | 走标准力 / 冲量通道，不占用物理位移通道（`common/control/MechaCharacter.java#setAnimRootDelta` 是接入点） |

### 6.1 三种写入形态与四条规则

控制器对刚体只用三种写入形态：

| 形态 | 引擎入口 | 用途 |
| --- | --- | --- |
| 力 / 冲量 | `../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#applyCentralForce`、同文件 `#applyCentralImpulse`、同文件 `#applyTorque` | 常规运动（行走控制力、跳跃冲量、闪避的冲量、外部击退）与飞行姿态力矩 |
| 速度 | `../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#setLinearVelocity` | 闪避的速度赋值；外部位移落点后的速度处理 |
| 位姿 | `../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#setPhysicsLocation`、同文件 `#setPhysicsRotation`、同文件 `#setCollisionShape` | 越障的抬升与前移（§6.2）、外部位移落点（§6.3）、落地摆正与朝向写入（§5）、换形（P5） |

位姿写入**不受角因子影响**——`setPhysicsRotation` 不经角冲量通道，实测见 `docs/角色控制器-刚体原型与引擎约束.md` §8.2，这是「锁转 + 仍能摆正」成立的前提。

**四条规则**（前三条来自 KCC 与 Minie 在各自的位置写入里都做过的同一件事）：

| # | 规则 | 依据 |
| --- | --- | --- |
| 1 | **写位置的同一物理步处理速度。** 只写位置会留下与位置不一致的速度，下一步被积分回去，表现为反复吸附或抖动 | `../Libbulletjme/src/main/native/bullet3/BulletDynamics/Character/btKinematicCharacterController.cpp#stepDown` 命中时把 `m_verticalVelocity` 与 `m_verticalOffset` 一并清零 |
| 2 | **落点留净空，不追求贴死。** 写进地形内部会让求解器在下一步做穿透恢复 | `docs/角色控制器-刚体原型与引擎约束.md` §4：判决把脚底对齐台阶顶面后，该步剩余的重力积分让胶囊下落约 0.7 cm；刚体上这一份交给求解器 |
| 3 | **写完 `activate()`。** 休眠的刚体不响应后续写入 | `PhysicsRigidBody#applyCentralForce` 一类入口内部都会 `activate()`，位姿写入不会 |
| 4 | **位姿写入只碰物理体。** 宿主实体永远只由每 tick 的 `common/ArmsCoreServerEvents.java#applyPoseToHost` 驱动 | 位置摄入的判据挂在 `Entity#setPos` 上，控制器内部的物理体写入不经它（§6.3）；反过来若写宿主实体位置，那一笔会落在栈空上被判成一次外部位移，而采纳路径每次都终止跳跃助推窗口，于是助推窗口活不过一帧 |

**相位**：全部落在物理线程的步进前相位（`PhysicsLevelTickEvent.Pre` → `ArmsCore#prePhysicsTick`），与力 / 冲量同一处。力每步重算（引擎在每个物理步之后清空 `m_totalForce` / `m_totalTorque`），位姿写入是事件驱动的（越障、传送、落地、换形）。

### 6.2 越障：抬升 → 前移 → 落位

越障是**位置写入**，不是力：胶囊底部是半径 0.4 m 的半球，台阶棱角一旦高于球心，接触法线的竖直分量就朝下，接触力只能把人顶住。`docs/角色控制器-行走物理设计.md` 的 `step_height_base` 是 0.6 m，而半径只有 0.4 m——0.5 m 半砖正落在自然接触上不去的那一段。先例也印证这一点：Minie 的 `BetterCharacterControl` 没有越障，而它的 `setMaxUpwardVelocity` Javadoc 自述「把上限设为零可避免过台阶时的弹跳」，说明「过台阶会弹」是这条路线上的已知现象。

做法与 KCC 同形（`btKinematicCharacterController.cpp#stepUp`、同文件 `#stepForwardAndStrafe`、同文件 `#stepDown`）：**抬升 → 前移到台阶前缘上方 → 落到顶面**，三步在**同一个物理步内**走完，落位那一步按规则 1 一并处理垂直速度。

- **判决沿用** `docs/角色控制器-刚体原型与引擎约束.md` §10 的判据与常量（探针长度、抬升量、净空探针、最小前移），其中第 ① 步的两处按本方案修正：命中取「通过法线筛的那些里 fraction 最小的一条」（依据见 §7.7 与 `docs/角色控制器-刚体原型与引擎约束.md` §11.5），「接近水平」的判据与着地阈值统一为 0.35。
- **必须同一步内**：跨步会留下一个无接触的物理步，而着地窗口只有 0.1 m（§7.7），0.5 m 的抬升跨步一定翻成 `air`——地面驱动力断一拍，状态机的 posture 也会翻一次。
- **落位清垂直速度**：不清的话，下一步的积分会把判决刚对齐的脚底再拽下去（`docs/角色控制器-刚体原型与引擎约束.md` §4 的 0.5067 m）。
- **水平速度原样保留，越障不改它。** 落位只把胶囊的前缘写到台阶立面上，这一步的积分仍按写入前的水平速度走，因此多出的 `v·Δt` 恰好把胶囊中心送到顶面支撑区里——6 m/s 时是 6 cm，而贴墙后中心到立面的水平余量是半径 0.4 m，两者相差一个量级，这一步只会踩实、不会越过去。反过来说，清零水平速度会让人物卡在台阶前缘并丢掉动量，那正是刚体路线要修掉的那类表现（§6 的撞墙读数）。越障因此不改变速度通道，也就**不需要在越障期间把刚体切成运动学**：位姿写入不受角因子与运动学状态影响，动态刚体照写不误（§5.2 的机制）。越障期间唯一可能碰到的是贴墙那一拍的斜向接触（法线水平），它由引擎按普通接触处理；控制力的饱和上限走 §7.4 的静态 `μ_eff·N`，不读这一拍的接触点，所以那里没有需要特殊对待的时效问题。

### 6.3 warp：纯位置操作

`common/control/MechaCharacter.java#warp` 现在承担四件事：① 改幽灵体落点；② 清垂直速度、保留水平动量（其中「先写零向量再写水平分量」是 KCC 通道语义的产物）；③ 复位「上一步落点上下文」——跳跃助推窗口、待发闪避冲量、动画位移叠加记账；④ 作废当步输入意图。

刚体上收成两项：

| 项 | 迁移后 |
| --- | --- |
| 落点 | `PhysicsRigidBody#setPhysicsLocation`。位置写入之后下一步仍会被求解器解算一遍（`docs/角色控制器-刚体原型与引擎约束.md` §12 的 E1），因此落点留净空（规则 2） |
| 速度 | 直接 `../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#setLinearVelocity`。刚体上水平与垂直同为一个量纲，不存在 KCC 那种「只有整向量为零才清掉垂直通道」的约束 |
| ③ 的动画位移叠加记账 | 随位移叠加通道一起消失（§6 的量纲统一） |
| ③ 余下两项与 ④ | 移到「采纳外部位移」的路径上（`common/HostPositionIntake.java#intake` 的采纳分支），`warp` 收缩为「位置 + 速度」 |

**「传送终止跳跃助推窗口」保留，但归属采纳那一步**：一次大位移之后继续助推不合理，而这件事是位移的后果、不是位置操作的语义。收成两项正是 `docs/角色控制器-KCC制约调研与替换评估.md` §7 的 E1 验收条目（传送是位置操作，不承担复位施力状态这类复合语义）。

**摄入层不需要新类别。** 位置摄入的判定点是 `Entity#setPos`，而控制器内部的位姿写入改的是物理体（`PhysicsRigidBody#setPhysicsLocation`），两者不相交；位姿到达实体只有一条路——每 tick 的 `common/ArmsCoreServerEvents.java#syncToClients` → `#applyPoseToHost`，它已经压在「本模组运行时回写」作用域里（`docs/宿主位置权威与位移摄入设计.md` §5.1 第 4 类）。因此规则 4 是纪律，不是新机制。

## 7. 接触：摩擦归属、行走力律与着地判据

### 7.1 三处摩擦项从力模型移出

引擎接管接触摩擦之后，下面三处不再由力模型承担：

| 现有位置 | 现有内容 | 处置 |
| --- | --- | --- |
| `docs/角色控制器-行走物理设计.md` §3.8 第 ③ 步 | 侧向抓地：按 `μ·g·cosθ` 抹掉不沿输入方向的速度 | 移出。引擎的接触摩擦对切向相对速度施加约束，承担同一职责 |
| `docs/角色控制器-行走物理设计.md` §3.9 | 无输入摩擦刹车：同一个减速度 | 移出。地面的无输入制动同样由接触摩擦给出，该分支只保留「不施加控制力」 |
| `docs/角色控制器-行走物理设计.md` §3.5 | 控制力的抓地力钳制 `min(驱动力, μN)`；以及 KCC 的 `setMaxSlope` | 移出。抓地力由接触层的摩擦锥给出，控制力侧要的那一道饱和上限按 §7.4 由控制器自己算 |

`docs/角色控制器-行走物理设计.md` §4.6 的方向冲量抓地折减也随接触摩擦的接管而移出。

### 7.2 保留内阻；坡度分量交给重力

`docs/角色控制器-行走物理设计.md` §3.6 的沿向内阻 `c₀·m·g` **保留在力模型里**：它的语义是「蹬地推进的效率损失」，不是接触摩擦。

**坡度分量由重力承担，力模型不扣它。** 刚体上重力是求解器真实施加的力，沿坡分量自己就存在；力模型再扣一次等于把同一次重力算两遍。内阻仍按 `c₀·m·g` 计、不随坡度缩放——`common/control/attr/MechaWalkingAttr.java#C0` 的导出式 `c₀ = P_base / (v_ref·m·g)` 是按平地标定的，坡度带来的差异全部由重力项表达。

### 7.3 摩擦系数的新落点

`μ_naked` / `μ_foot` 这两个参数**不消失**，只是它作为**角色侧**摩擦进入刚体的 `setFriction`（写法见 `common/control/MechaCharacter.java#getEffectiveFriction`）。取值按实测换算：要爬坡上限 45° 就取 2.0（× 地形 0.5 → 组合 1.0），要 35° 就取 1.4。标定表见 `docs/角色控制器-刚体原型与引擎约束.md` §5。

**当前落地取值就是 2.0**（`common/control/attr/MechaWalkingAttr.java#MU_NAKED`），地形侧是 `#TERRAIN_FRICTION` = 0.5，组合 1.0。**取 2.0 而不是 1.0 是必须的**：组合摩擦同时是控制力的饱和上限 `μ_eff·N`，而 `m·g = 686.7 N`——角色侧取 1.0 时上限只有 343 N，比 `F_MAX = 700 N` 低一半，低速区的驱动力被锥截一半。

因此 `docs/角色控制器-行走物理设计.md` §8.1 的 `θ_max = atan(μ_effective)` 语义成立，只是 `μ_effective` 现在天然含入地形侧的材质差异。

**`getEffectiveFriction()` 的语义随之改变**：从「角色侧 μ」变成「组合 μ_eff（= 角色侧 × 地形侧）」。当前取值下两边的数值相差一个地形侧因子（角色侧 2.0、组合 1.0），因此实现与注释必须写明它取的是**组合值**、且这个组合值是配置约定（§7.6 第 2 条），不是每拍问引擎要的读数；否则以后有人再乘一次地形侧就会差 2 倍。它同时是构造器里反解 `setFriction` 的输入（除以地形侧），因此覆写体不能读子类实例字段。

**`docs/角色控制器-行走物理设计.md` §3.5–§3.9 的既有标定只复现了一半**：起步加速度那一行逐项复现（实测 9.908 对解析 9.81），顶速与倍率等比那两行不复现，原因与数值见 §7.4 的对账表与 §12.10。

### 7.4 行走力律（当前形态）

地面上的驱动是**力**，不是期望速度（§9.5）。每步用的全部是已知量：

```
θ          ← 支撑法线与竖直方向的夹角（§7.7 的扫掠筛后取最竖直）
N           = m · g · cosθ                        m 取 common/control/attr/MechaWalkingAttr.java#MASS
μ_eff       = 角色侧 setFriction × 地形侧          两侧都是配置常量（§7.3）
F_drive     = min( k · computeDriveForce(v),  μ_eff · N )        k = MOVE_SPEED_MODIFIER
前馈         = μ_eff · N · (1 + FEEDFORWARD_RELEASE) · û          û = 目标移动方向（世界系）
F_applied   = F_drive · û + 前馈
```

`F_applied` 以质心中心力施加（`PhysicsRigidBody#applyCentralForce`，§8.1）。落地形态见
`common/control/MechaCharacter.java#updateWalk`，两个可覆写钩子是 `#usesFrictionFeedforward` 与
`#getEffectiveFriction`，常量是 `#FEEDFORWARD_RELEASE`。

**引擎对受力接触体给的是静摩擦锁定，这是整条力律的机制前提。** 实测（同一个 70 kg 锁转胶囊、
角色侧摩擦 2.0、地形侧 0.5、平地）：

| 施加的水平恒力 | 50 步平均加速度 | 说明 |
| --- | --- | --- |
| 171.7 N（= 0.25 `μ_eff·N`） | **0.0000 m/s²** | 静摩擦精确抵消，位移 0 |
| 343.4 N（= 0.5 `μ_eff·N`） | **0.0007 m/s²** | 同上，残差只是数值噪声 |
| 1000 N | 9.38 m/s²（合力 656.6 N） | 超出部分才走：`1000 − 343.4 = 656.6` |
| 343.4 N 且角色侧摩擦取 0 | 4.905 m/s² | 无摩擦时全额兑现 |

即引擎给出的是 `F_net = max(0, |F_applied| − μ_eff·N)·(F_applied 方向)`，**不是**「从受力里减掉
`μ_eff·N` 之后照常加速」。这条差别决定了三件事：

1. **`μ_eff·N` 那条前馈必须恰好把这份摩擦抵消掉，净力才等于 `F_drive`。** 这是本力律里前馈的
   唯一职责，也是 §9.6 简化 4 之外的第二处「必须靠实测才能定形状」的地方。
2. **施加值必须严格大于 `μ_eff·N`，否则落在锁定面上、净力恒为 0。** 恰好的 `μ_eff·N` 实测给出
   0.0007 m/s²（50 步位移 0.05 mm），因此前馈取 `μ_eff·N·(1 + 0.01)`：把工作点推离锁定面，
   代价是 1%（当前参数下 6.9 N）的净力偏置。没有这一项，角色在 `F_MAX` 与 `μ_eff·N` 接近时
   完全不动——`F_MAX = 700 N`、`μ_eff·N = 686.7 N` 时净力只有 13 N，实测 10 步末速率 0.000 m/s。
3. **`F_MAX` 必须显著大于 `μ_eff·N`，否则起步推力被锥吃掉大半。** 这是 §12.10 登记的标定项。

**它只在有支撑时非零。** `grounded` 为假时 `N = 0`（或者更直接地：不取 `θ`），于是 `F_drive = 0`，
空中不需要单独一条分支来关掉地面力律。

**为什么必须有 `min(·, μ_eff·N)`。** 引擎不会限制我们能造出多大的净力：去掉这一条，施加
`3μ_eff·N` 就能得到 `2μ_eff·N` 的净力，冰面上照样起步。把 `F_drive` 自己截到摩擦锥上，等价于
「腿蹬地、地面能传多少就只能拿多少」；冰面上 `N` 不变而 `μ_eff` 趋零，于是起步与加速都趋零。
它与 `docs/角色控制器-行走物理设计.md` §3.5 的抓地力钳制同构，钳的是净力而不是施加的力。

**`N` 取静态估算，不读接触点的瞬时法向冲量。** 这是本方案的一处已定型简化，理由与代价见 §9.6 简化 4。

**`common/control/attr/MechaWalkingAttr.java#F_MAX` 限的是净力**：施加的峰值是
`k·F_MAX + μ_eff·N·(1 + 余量)`（k = 1、`μ_eff = 1.0`、平地时约 1380 N）。「腿能出多大力」与
「接触面能传多大力」是两件事，后者由 `μ_eff·N` 表达。

**与 KCC 承载时期的标定对账**（`μ_eff = 1.0`，即角色侧 `common/control/attr/MechaWalkingAttr.java#MU_NAKED`
= 2.0 × 地形侧 `#TERRAIN_FRICTION` = 0.5；`m = 70 kg`、`N = 686.7 N`）。第二列是
`docs/角色控制器-行走物理设计.md` §3.5–§3.9 按旧力模型推出的解析值，最后一列是
`src/test/java/io/github/sweetzonzi/arms_core/common/control/RigidBodyControllerMeasurementTest.java`
在裸 `PhysicsSpace` 上驱动**正式控制器**量到的值：

| 量 | KCC 承载时期（`docs/角色控制器-行走物理设计.md` §3.5–§3.9） | 本力律解析值 | 本力律实测值 | 偏差 |
| --- | --- | --- | --- | --- |
| 静止起步加速度 | 7.9 m/s² | `μ_eff·g` = 9.81 m/s² | **9.908 m/s²** | +1.0%（前馈余量） |
| 站立顶速 | 6.0 m/s | `P_base / (μ_eff·m·g)` = 6.0 m/s | **25.0 m/s** | 见下文 |
| 蹲伏顶速 | 1.8 m/s | 解析值 1.8 m/s（`k` 只改平衡式系数） | **10.7 m/s** | 同上，且比值 2.14 而非 0.3 |
| 无输入刹车 | `μ·g` = 9.81 m/s² | 9.81 m/s²（引擎动摩擦） | 未单独量（由 A–B 组推出） | — |
| 爬坡上限 | 45° | 45°（`tanθ = μ_eff`） | 未在合并地形上量，见 P1 | — |

**起步加速度那一行是恒等式，实测已复现到 1%。** 低加速区 `F_drive` 被锥截到 `μ_eff·N`，前馈
恰好抵消引擎那份摩擦，净力 `= μ_eff·N`，加速度 `= μ_eff·g`，`m` 在锥截里约掉。实测
9.908 m/s² 与 9.81 的 1% 差额就是前馈余量。

**顶速那一行不是恒等式，实测明显高于解析值。** 平衡式是 `F_drive = 引擎接触摩擦`，
`F_drive` 被截在 `μ_eff·N` 上，因此平衡点是 `computeDriveForce(v_eq) = μ_eff·m·g`，
而不是 `= c₀·m·g`。`P_base/(μ_eff·m·g) = 1.17 m/s`，加上 `F_drive ≤ F_MAX` 的锥截，数值上给出
十几 m/s；而前馈在高速区**不再把摩擦完全抵消**（引擎实际给出的那份随速度略有变化，前馈是静态
估算），因此实测落在 12–25 m/s 并随运行时长缓慢上爬。这一项是 §12.10 的标定项。

**前馈把摩擦从「未知负荷」变成「已知项」之后，它不参与平衡式**，因此 `MOVE_SPEED_MODIFIER` 的
等比性在**净力**层面成立：`F_drive` 按 `k` 等比缩放，而锥截上限是常数，所以只有在
`k·computeDriveForce(v) < μ_eff·N` 的区间里顶速才与 `k` 成正比。

三条直接后果：

1. **「2μN」只在低加速区成立。** 等速区里 `k·computeDriveForce(v)` 已小于 `μ_eff·N`，施加的是
   `P/v + μ_eff·N·(1 + 余量)`（v = 6 m/s 时约 133 + 694 ≈ 827 N）。
2. **倍率只改变顶速，不改变低加速区的净力。** 低加速区一律被锥截到 `μ_eff·N`，k 只进高速区；
   `common/control/attr/MechaWalkingAttr.java#MU_NAKED` 与 `#F_MAX` 因此只影响顶速与起步推力
   的配比。
3. **转向必须写成矢量。** 摩擦的方向是「反着实际滑动方向」（−v̂），不是反着输入方向；`û ≠ v̂`
   时前馈与引擎摩擦不再共线，差额那一份表现为侧向抓地。`docs/角色控制器-行走物理设计.md` §3.8
   那种「按输入方向分解成沿向 / 侧向、各吃各的机制」的写法在本力律下不成立——侧向抹除不再是
   一个独立步骤，而是同一份接触摩擦的另一面。实测在同一份测量里量到最大侧向速率 **0.000000 m/s**
   （起步段），说明平地直行时两份力共线、没有侧向残差。

**术语**：无输入时让速度衰减的是**动摩擦**（减速度 `μ_eff·g`），静止之后才是静摩擦保持不动。

**空中**：没有接触 ⇒ `N = 0` ⇒ 地面力律不适用；空中沿用 `F_MAX × AIR_CONTROL`
（`docs/角色控制器-行走物理设计.md` §3.7 的语义），不做摩擦前馈。

**着地判据的上升门限必须是量级而不是严格大于 0。** 求解器在稳定接触上会间歇给出 0.0x m/s 的
**正**垂直速度（接触迭代残差）。严格用 `vy > 0` 当「上升中，不判着地」，着地布尔就会在「有支撑」
与「上升中」之间来回翻，地面摩擦随之周期性断开——实测的速度因此不再收敛（周期性出现一拍
`grounded = false`、施加力掉到空中控制力的 210 N，而引擎摩擦照旧 686.7 N）。落地形态取
`common/control/MechaCharacter.java#GROUNDED_VERTICAL_SNAP`（0.5 m/s）作为门限：跳跃的起跳速度
（8 m/s 量级）照旧封掉，噪声被滤掉。

**本节与 §7.1 的关系**：§7.1 移出的三处是「谁承担摩擦」，本节给的是「移出之后地面驱动怎么算」。
剩余待细化的范围见 §12.4，标定项见 §12.10。

### 7.5 接触材质：只用于写入，不在运行期读

`μ_eff` 与 `N` 都不再从接触点读（§7.3、§7.4）之后，接触点在本方案里只剩一件事要做：**让逐方块的材质差异生效**——冰面、湿滑这类差异必须按接触对写入组合摩擦，因为引擎的组合摩擦取双方之积（`docs/角色控制器-刚体原型与引擎约束.md` §5），而地形侧的系数存在方块数据里。

| 事项 | 内容 |
| --- | --- |
| 触发时机 | 地形方块的摩擦数据变化时，**不是每个物理步**。因此没有逐点累加器、没有回调里的瞬时读数、也没有「读取晚一拍」的时序问题 |
| 写入内容 | 该接触对的组合摩擦（先例：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/collision/CollisionHandler.java#setupContactFriction`） |
| 数据来源 | `../Spark-Core/src/main/java/cn/solarmoon/spark_core/util/BlockCollisionUtil.java#getBlockFriction` 与同文件 `#getSlip`；数据包在 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/terrain/BlockPhysicsDataMaps.kt` 的 `friction`（默认 0.7，另有湿滑系数——不是原版 `slipperiness` 的乘数语义） |
| 接线前提 | 地形侧默认值是 Bullet 的 `btCollisionObject` 默认 0.5，而全仓没有任何一处对地形调用 `setFriction`；接入材质映射要新增一条按点写入的路径（`docs/角色控制器-刚体原型与引擎约束.md` §1、§5） |

**未接入之前，`μ_eff` 是一个配置常量。** 角色侧取 2.0（组合 1.0，爬坡上限 45°）、地形侧取 Bullet 默认的 0.5，两者在标定表里就是这么取的；材质接入之后 `μ_eff` 随接触对变，而力律的形式不变。

**它是独立项，不挡任何其它工作。** 接口落在哪一层（`../Spark-Core` 侧补一条按点写入的路径，还是本仓库侧订阅 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/event/PhysicsContactEvent.kt#Process` 自己写）与「每块只写一次」的触发点都还没定，但力律、着地判据、位姿写入都与它无关，可以后补。

### 7.6 接触量：`N` 与 `μ` 都取静态估算

每物理步需要两个量，两者都**不需要接触清单**：

| 量 | 取法 | 说明 |
| --- | --- | --- |
| `N` | `m · g · cosθ` | `θ` 是 §7.7 扫掠筛后取到的那条支撑法线与竖直方向的夹角；无支撑时 `N = 0` |
| `μ_eff` | 角色侧 `setFriction` × 地形侧系数 | 两侧都是配置常量（§7.3、§7.5），材质接入后随接触对变 |

**放弃的东西写在这里，不留暗账。** 三条代价，全部静默：

1. **额外法向载荷不进 `N`。** 被踩、被推进器下压、落地冲击那一拍的真实法向力可达 `m·g` 的数倍，静态估算会低估，于是那一拍控制力的可用上限小于实际可传的摩擦。现行场景里这些载荷没有来源（控制器只与自己、与地形发生接触，§2.2 选择 4），所以代价可接受；开放碰撞掩码或接入双体之后要重新审这一条。
2. **`μ` 不再由引擎上报。** 组合摩擦取双方之积这件事是实测出来的（实测证据见 `docs/角色控制器-刚体原型与引擎约束.md` §5——引擎侧的 `btManifoldResult::calculateCombinedFriction` 不在本仓库的三个源码目录里），此后它作为配置约定使用，而不是每拍向引擎问一次。材质差异的接入路径因此也从「读 `combinedFriction`」变成「写进去的时候就知道」（§7.5）。
3. **引入对支撑法线的依赖。** `cosθ` 来自扫掠的着地判据，于是「合并矩形接缝处法线在几条接触间跳」这件事从表现层问题升级为**力模型输入**。处置是同一处：仍取最竖直的那一条（§7.7），跳动幅度与它带来的控制力上限波动在 P1 的地形回归里一并量。

**为什么值得换。** 触发器与它的收益是同一件事——每物理步不需要订阅接触事件、不需要遍历全场 manifold、不需要为「瞬态冲量到底是本步总量还是迭代增量」设计一次测量，也不需要处理「接触发生的那一步 `N = 0 ⇒ F_net = 0`」这个一拍空档。代价只落在上面三条上。

### 7.7 着地判据与地面法线

判据的形态取自 KCC：它每物理步做一次向下形状扫掠，命中即着地（`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Character/btKinematicCharacterController.cpp#stepDown`、同文件 `#onGround`）。本方案取这条机制，并按 Minie 的 `BetterCharacterControl#checkOnGround` 补两条：

```
① 竖直速度 > 0 → 本步不判（KCC 的 stepDown 直接 return；同时封掉「0.4 m 探针 = 二段跳窗口」）
② 向下扫掠胶囊形状（或半径球）：
     起点 = 当前位置 + 0.3·up      终点 = 当前位置 − 0.1·up     （长度 0.4 m，引擎下限）
③ 结果筛：排除自己 → 只留对方组 == CollisionGroups.TERRAIN → 只留法线竖直分量 ≥ 0.35
④ grounded = 存在通过 ③ 的命中 ∨ 本步有支撑接触
   gap = 0.3 − fraction × 0.4       （fraction 只用于测距：表现层与落地收敛的触发，不作接受判据）
```

**为什么用端点定窗口，而不是扫满再比 fraction。** `../Spark-Core/src/main/java/com/jme3/bullet/CollisionSpace.java#sweepTest` 要求起点与终点至少相距 0.4 物理单位，而需要的窗口只有 0.1 m：把终点放在「允许探测的距离」上（Minie 的做法——终点取下半球心减 margin，于是「有任何命中」就等于「贴地」），长度下限与窗口上限同时满足，接受判据退化成「有没有合法命中」。

**扫掠结果是无序的，必须自己筛。** `#sweepTest` 的 Javadoc 原文是 "store the results in an existing list, **in arbitrary order**"（同文件的 `#rayTest` 才写明 sorted）。KCC 之所以没有这个问题，是因为它在回调内部把不合格命中丢掉、再由 Closest 回调保证取最近（`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Character/btKinematicCharacterController.cpp#btKinematicClosestNotMeConvexResultCallback`）。我们拿到的是列表，因此要「筛完再取」；只取 `results.get(0)` 会得到与地形分块顺序有关的不确定行为（`docs/角色控制器-刚体原型与引擎约束.md` §11.5）。

**阈值 0.35（≈70°）** 是「地面还是墙」的分界线，与「站得住 / 爬得上」无关——后者由摩擦锥自然涌现（`θ_max = atan(μ_eff)`，见 `docs/角色控制器-行走物理设计.md` §8.1）。它有一个硬约束：**阈值角必须大于 `atan(μ_eff_max)`**，否则超出爬坡上限的可行坡度会被判成墙。当前组合 `μ_eff = 1.0` → 45°；腿部件把组合 μ 抬到 2.0 → 63.4°，0.35 仍留有余量，0.707（45°）则会被削。

**地面法线取通过筛的那些里最竖直的一条**（先例：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/mixin/EntityMixin.java` 用最接近竖直的命中面法线判着地并补写宿主的 `onGround`）。它有两个消费者：越障判决（§6.2）与**力模型的 `cosθ`**（§7.6），后者是这条读数升格为输入的地方。已知代价：V 形谷与合并矩形接缝处，法线可能随哪一条接触瞬时占优而逐步跳，于是 `N = m·g·cosθ` 与随之而来的控制力上限也跟着跳——幅度与影响在 P1 的地形回归里量。

**唯一出口。** 状态机读的 `ON_GROUND`（`common/control/MechaControl.java#writeStateInputs`）、力模型读的着地布尔（`common/control/MechaCharacter.java#updateWalk`）与宿主写回用的值都取这一份，并加一个最小保持时间，防止高频抖动把 posture 在 `air` 与地面之间来回翻（现行实现里状态机读 `kcc.onGround()`、力模型读 `MechaCharacter#grounded`，是同一来源的两个读点）。最小保持时间的时长与计法（按 `dt` 还是按步）在 P1 的地形回归里一并定。

**备用判据。** 接受窗口可改用 fraction 门（扫满 0.4 m、只接受 `fraction ≤ 窗口 / 0.4`），代价是必须依赖「筛后取最小 fraction」这个有序化步骤。它只在实测发现「端点定窗口」在合并地形的接缝处漏判时才启用。

## 8. 力与力矩如何作用于胶囊体

本节只讲**已经拿到力以后怎么进物理**，不涉及力的来源（力的来源见 §9）。

### 8.1 施加方式：预计算合力与合力矩，一次性应用到胶囊

**不逐推进器、也不逐气动计算点施加。** 全部力先在**世界系**里汇总成一个合力 `F` 与一个合力矩 `τ`，然后每物理步只做两次调用：

| 通道 | 引擎入口 | 作用 |
| --- | --- | --- |
| 合力 | `PhysicsRigidBody#applyCentralForce` | 作用于质心，只改变线速度 |
| 合力矩 | `PhysicsRigidBody#applyTorque` | 只改变角速度，不改变线速度 |

`../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#applyCentralForce`、`#applyTorque`。两者每步生效一次、随后被引擎清零（`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btDiscreteDynamicsWorld.cpp#clearForces` 在 `stepSimulation` 末尾逐体清空 `m_totalForce` / `m_totalTorque`）。

**归约在世界系里做。** 两个入口都吃世界系：`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btRigidBody.h#applyCentralForce` 只把 `m_linearFactor` 逐分量乘上去，`#applyTorque` 对 `m_angularFactor` 同理，`#applyTorqueImpulse` 里的 `m_invInertiaTensorWorld` 也是世界系。§8.1 的力矩式 `τ = Σ (p_i − c) × F_i` 中 `p_i` 与 `c` 同样取世界坐标。本体坐标系只出现在**单个力源**计算自己的力与方向那一层（气动在计算点自己的坐标系里算，§10.1），不参与归约。

**为什么不用 `applyForce(力, 作用点)`。** 引擎提供了一个便利入口：把力与作用点一起交给它，它内部自己算力臂力矩——

```cpp
void applyForce(const btVector3& force, const btVector3& rel_pos)
{
    applyCentralForce(force);
    applyTorque(rel_pos.cross(force * m_linearFactor));
}
```

坐标见 `../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btRigidBody.h#applyForce`。

那为什么不逐作动器调用它？三条理由，第一条是硬性的：

1. **纯力偶没有「作用点」。** 反扭矩（推进器喷流的反作用）与其它直接力矩项不是「力 × 力臂」的产物，写不成 `(力, 作用点)` 的形式——§8.2 说明它们必须显式建模。只要存在一项这样的力矩，`applyTorque` 就必须有；既然它已经在，把全部力矩都走它就不再多出一条通道。
2. **归约点必须唯一。** §9.1 约定**没有任何一个力源自己把力施加到刚体上**，全部力源只产出数据、由单一施加点汇总。逐作动器 `applyForce` 会让每个作动器自己成为施加者，这条约定就废了——而气动的数据来自 SubPart（§10.1），它必须与推进器走同一条路，否则同一份气动力会一次进 SubPart 自己的刚体、一次进胶囊（§12.7）。
3. **一次调用胜 N 次。** 两条路在数学上**等价**——引擎的实现就是上面那段代码，且内部同样走 `applyTorque`，所以角因子的门控行为一致。区别只在每步调用 N 次还是 2 次。

**力矩仍由真实几何导出。** 每个作动器的力矩写在它的雅可比列里，就是 `(p − c) × F`（`docs/控制分配-作动器wrench分配设计.md` §3.1），`p` 是该作动器的真实作用点。手工归约不等于丢掉几何，只是把这一次乘法的位置从引擎挪到分配器，好让它与力一起参与分配。

**力矩的参考点只有一个：胶囊质心。** 全部力源（推进器、接触型、气动）的力矩都在这一个点上算，写成 `τ = Σ (p_i − c) × F_i`，`c` 就是胶囊质心。`p_i` 各自不同（推进器是安装点，气动是流体动力计算点），但 `c` 必须统一——否则各通道的力矩不可相加。

### 8.2 反作用与对称性

两个必须显式建模的量：

- **反扭矩**：推进器喷射本身产生绕喷射轴的力矩（喷流的反作用），与推力方向无关，不能由力臂导出。它是**直接力矩项**，与 `Σ(r × F)` 并列相加。舵面偏转的**铰链反作用力矩**属于同一类，但本方案不建模——理由见 §9.6 的简化 2。
- **力矩相消**：多个推进器同时出力时，各自的力臂力矩可能互相抵消（对称布置的推进器只出力不出力矩），也可能叠加（单侧布置的推进器出力必然带力矩）。因为力矩由我们自己归约而不是由引擎从作用点导出，**这个相消关系必须在雅可比列里显式保留**（`docs/控制分配-作动器wrench分配设计.md` §3.1 的 `(p − c) × d`）——引擎不会替我们做。

### 8.3 分轴锁转下各轴力矩的可用性

角因子置 0 的轴上，力矩**施加不上去**（§2.2 选择 2 的机制）。这不是副作用而是设计的一部分：

- 地面状态 `(0, 1, 0)` 下，pitch / roll 力矩一律无效，只有 yaw 力矩生效——而这恰好是地面状态需要的全部（转身）；
- 因此地面状态下**不需要**为 pitch / roll 做任何力矩分配，也不会因为推进器带出的 pitch / roll 力矩而失衡。失衡表现留给飞行状态。
- 这条事实在分配层表现为**行表**：pitch / roll 两行直接不进分配问题（`docs/控制分配-作动器wrench分配设计.md` §8）。留着一个引擎会丢掉的维度，只会让分配器把权限花在无效方向上、并报出不存在的饱和缺口。

## 9. 力的来源：从 SubPart 到作动器

本节只讲**力怎么算出来**，不涉及如何施加（见 §8）。

### 9.1 力源是数据，不是对刚体的施加

本节先立一条贯穿全部力源的约定。

**没有任何一个力源自己把力施加到刚体上。** 每个力源每物理步只产出一个数据结构，统一为：

```
力源 = ( 世界作用点 p, 世界力矢量 F )
```

归约只有一件事：

```
F_total += F
τ_total += ( p − c ) × F        c 是胶囊质心，全场唯一（§8.1）
```

这条约定有两个直接后果：

- **气动与推进器走完全相同的归约路径。** 气动力不再由每个 SubPart 施加到自己身上，而是作为数据交给同一个汇总点。
- **逐点施加的入口被废掉。** `PhysicsRigidBody#applyForce(力, 作用点)` 与这条约定不兼容，理由已在 §8.1 给出（纯力偶没有作用点可给、归约点必须唯一、一次调用胜 N 次）。

因此本方案里凡是「算力」的地方，终点都是这个数据结构，而不是一次引擎调用。

### 9.2 四类驱动，两个去向

分类判据是**控制器能不能命令它**——也就是这个力源有没有一个**可命令的致动器状态**：

| 类型 | 可命令量 | 力由什么决定 | 典型例子 |
| --- | --- | --- | --- |
| **推进器** | 出力（油门） | 指令，与速度、姿态**无关** | 喷射推进、悬浮 |
| **接触型** | 落脚点选择 | 指令 + 接触状态（受摩擦锥限制） | 双足、轮足、履带 |
| **固定零件气动** | **无** | 完全由当前运动与姿态决定 | 机翼、机身、尾翼 |
| **舵面气动** | 偏转角 | 指令 + 动压 `q = ½ρv²` | 副翼、升降舵、方向舵 |

**有可命令量的一类进分配器，而且是同一个分配器。** 推进器、舵面、以及被当作减速板用的气动面**全部是同一件事**：各有一个可命令量 `u`，各对胶囊贡献一份力与一份力矩。它们之间的差别只落在两份数据上——每个作动器的**界**（§9.4）与它的**雅可比列**（`docs/控制分配-作动器wrench分配设计.md` §3.1）——而不是落在几条不同的处理路径里。分配问题不区分器件的「类型」，只读这两份数据。

减速板因此不是第五类，而是舵面的一个特例：可命令量同样是偏角，只是外形让它的雅可比列偏向沿来流方向的力而不是力矩。这件事由列自动表达，不需要类型标记。

接触型也产出一份力，但它的方向不是安装出来的（§9.5），因此留在分配器之外。

**没有可命令量的一类去目标上的矢量减法。** 固定零件气动的力完全由当前运动与姿态决定，控制器无法支配它；环境已经把它给了胶囊，于是控制器的任务是**减掉它**：期望净 wrench 减去这一份，剩下的才是作动器要凑的量（§10.4）。这个去向不是「另加一股力」，而是**同一个目标上的减法**。

**「固定零件」与「舵面」按可命令量划分，不按外形或安装位置划分。** 同一片翼面，作为固定零件时装它就完全不参与控制、只被减掉；装上作动器后它就成为舵面。判据是那台作动器，不是那片翼面。

### 9.3 从 SubPart 到作动器数据

一个**作动器**是「有一个可命令量、并对胶囊贡献一份力与一份力矩」的对象。它对分配器只需要交出四样东西：

| 项 | 内容 | 从哪来 |
| --- | --- | --- |
| **可命令量 `u` 的界** | `[u_min, u_max]`。归一化后大多是 `[0, 1]`（油门）或 `[−1, +1]`（偏角 / `δ_max`） | 零件属性与当前状态，见 §9.4 |
| **雅可比列 `J_k`** | 该作动器的 `u` 变化一单位对合力与合力矩的贡献 | `docs/控制分配-作动器wrench分配设计.md` §3 |
| **作用点 `p`** | 世界作用点，用于算力臂 | 定位点的世界位姿 |
| **力函数** | `u → (p, F)`，代回复核要用（`docs/控制分配-作动器wrench分配设计.md` §7） | 该器件自己的模型 |

映射分三层，每层对应作动器的一类信息：

| 层 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| **位置 → 力臂** | 定位点的世界位姿 | 该点相对胶囊质心的位移 `r = p − c` | 决定这份力**能产生多大力矩** |
| **姿态 → 方向** | 定位点的世界旋转 | 力在本体坐标系下的方向 | 决定这份力**落在哪一轴**，也决定雅可比列的方向 |
| **属性 + 状态 → 大小** | 零件属性（最大出力、响应时间、能耗）与状态（接触 / 动压） | 该作动器当前能出多大 | 决定 `u` 的界，也决定雅可比列的模长 |

**力臂 `r` 必须每物理步按实际位姿重算**，不能在配装期缓存。部件之间存在约束余量、损伤与相对运动，这与「姿态朝向只在配装期算一次」不是一回事。

**界的来源分两种：配装期定死形状，运行期缩放。** 推进器的**方向**是配装期常数，**大小**不必是——推力包络随高度与空气密度、损伤、燃料变化。分配器只需要当前值，所以这一点不构成负担。舵面的界由**最大偏角** `δ_max` 在配装期定死形状，运行期**随动压 `q` 缩放**：

```
该作动器在某方向能出的力 = q 决定的比例因子 × ( 最大偏角下的力在该方向上的分量 )
```

**力矩的可达范围不能从力的范围导出。** 每个作动器的力矩是它的力与力臂的叉积 `(p − c) × F`，这套关系写在雅可比列里（`docs/控制分配-作动器wrench分配设计.md` §3.1），不是另一组独立的界。参考点全场唯一为胶囊质心，理由见 §8.1。

### 9.4 分配目标与各作动器的界

#### 目标的语义

```
w_des    = 胶囊的期望净 wrench（控制层的意图）
w_known  = 一切不由本控制器作动器提供、但已知的 wrench
           （固定零件气动、舵面 δ=0 基准项、重力、其它可测的已知扰动）
分配目标 w_alloc = w_des − w_known          ← 矢量减法
```

**`w_des` 的语义必须钉死为「胶囊的期望净 wrench」**，否则这条减法无从写起：环境已经给了胶囊的那一份必须先从目标里减掉，剩下的才是作动器要凑的量。完整约定与算式见 §10.4。

**为什么是减法而不是「在输出上再加一股抵消力」**：见 §10.6 的三路对比。一句话版本——§8.1 决定了我们手工算合力再 `applyCentralForce`，**引擎不会替我们检查这个力作动器出不出得来**，因此加在输出上会凭空造力；而减去之后，这份需求会进入分配器的饱和判断，缺口与 windup 回退全都自洽。

#### 各作动器的界

| 来源 | 界的形状 | 什么时候变 |
| --- | --- | --- |
| **推进器** | `u ∈ [0, 1]`（归一化油门，单侧） | 方向是配装期常数；大小随推力包络、损伤、燃料变 |
| **舵面 / 减速板** | `u ∈ [−1, +1]`（偏角 / `δ_max`，双侧） | 形状配装期定死，模长随动压 `q` 缩放（§9.3） |
| **接触型** | 不进分配器 | 见 §9.5 |

**两个端点都要给，而且不必对称。** `[0, 1]` 说的是「这台推进器只能推不能拉」，不是「油门关不小」；`u = 0` 永远在界内，因此**零出力永远可达**。这条在分配层表现为一个不变量：`w_alloc = 0 ⟹ u = 0`（`docs/控制分配-作动器wrench分配设计.md` §7）。

**界与雅可比列合起来才是能力。** 界说明「能推多远」，列说明「推一单位得到什么」。两者都按当前状态取，所以「舵面的能力随速度变」不需要任何特判——低速时它的列模长趋零，分配器自然不会用它（`docs/控制分配-作动器wrench分配设计.md` §3.1）。

#### 行表

分配问题不是恒定 6 维：**引擎不接受的 wrench 分量不该进目标**。地面 `(0, 1, 0)` 下 pitch / roll 力矩会被 `applyTorque` 门控丢掉（§8.3），把它们留在问题里会让分配器把权限花在无效方向上、并让残差报出一个不存在的缺口。角色控制器这边按当前 `angularFactor` 导出活行掩码：

```
活行 = { 力 x, 力 y, 力 z } ∪ { 力矩 i | angularFactor_i ≠ 0 }
```

| 状态 | `angularFactor` | 行数 | 构成 |
| --- | --- | --- | --- |
| 飞行 / 悬浮 | `(1, 1, 1)` | **6** | 3 力 + 3 力矩 |
| 地面站立 / 行走 | `(0, 1, 0)` | **4** | 3 力 + yaw 力矩 |
| 落地收敛窗口 | `(0, 1, 0)` | **4** | 3 力 + yaw 力矩（首步即锁，与地面同一组行；§5.2） |
| 布娃娃 | `(1, 1, 1)` | 不分配 | §4.1：姿态权威为「无」 |

**地面 yaw 行的权限范围要写清。** 它只覆盖作动器能提供的那部分（偏心力源的力臂力矩）。双足的转向能力来自**落脚点选择**，而接触型在分配器之外（§9.5），所以**分配器不管走路转向**；胶囊自身的朝向也不占这一行——它由每物理步的位姿写入驱动（§4.1），作动器那部分与它无关。

**切换瞬间的指令阶跃**，两个方向不对称：**收行**（飞行 6 → 地面 4）时需求本来就在趋零——摆正已经把 pitch / roll 的力矩需求往零收敛，「先摆正、后降维」是自然顺序，不需要额外过渡逻辑；**放行**（起飞 4 → 6）时两行突然出现，突然可用的 pitch / roll 力矩由飞行控制层（§4.3、§12.2）吸收并限幅，但**控制层必须知道当前行表**，否则它在什么维度上工作都是猜的。

**死行上出现非零分量有两种来源，处置完全不同**：`w_des` 在死行上非零（地面上控制层还在要 pitch 力矩）是**上层搞错了**，应当断言或记日志；`w_known` 在死行上非零（地面上一片机翼的升力在质心上方产生 pitch 力矩）是**正常、静默丢弃**——引擎也会吃掉那份力矩（§8.3），所以它既进不了胶囊、也不需要被抵消。

它只覆盖角色控制器的这四种状态；分配器侧怎样用这个掩码降维、为什么降维与乘零掩码逐位等价，见 `docs/控制分配-作动器wrench分配设计.md` §8。

### 9.5 接触型驱动

接触型与其余三类在映射上的根本差别：**它的力不是安装出来的，而是地面给的**。

| 环节 | 内容 |
| --- | --- |
| 可用性 | 需要至少一个支撑相。无接触时该类型出力为零 |
| 方向 | 由落脚点与地面法向决定：法向分量只能推（不能拉），切向分量受摩擦锥 `\|F_t\| ≤ μ_eff·N` 限制 |
| 大小 | 上限是摩擦锥，而不是某个零件属性 |
| 落脚点 | 决定力臂，因而决定这一步能产生多大偏航力矩——双足的转向能力来自落脚点的选择，不是来自某个"转向执行器" |

因此接触型的三样东西让它**留在分配器之外**：

1. **方向不在本体坐标系里**。推进器与舵面的力方向由安装姿态给出，因此能写成一个固定的列；接触型的方向由「这一步脚踩在哪」决定，**本体坐标系里没有「落脚点」这个量**，写不出列。
2. **单侧约束、而且约束来自摩擦锥**。推进器的单侧界是 `[0, 1]`，与状态无关（§9.4）；接触型的界是 `|F_t| ≤ μ_eff·N`，两者都是瞬时状态——`N` 随支撑法线变，`μ_eff` 在材质接入后随接触对变（§7.6）。
3. **力的产生者与支配者是分开的**。地面反力本身由接触求解器给出，我们不手工预生成（§9.6 简化 1）；控制器能支配的只是**落脚点的选择**。

**接触型控制力保留。** 地面行走、轮式 / 履带驱动一律走接触层，由角色控制器给出平面控制力、受摩擦锥钳制。它的落脚点同时也是地面偏航力矩的来源——因此**地面上的 yaw 分配只覆盖作动器能提供的那部分，不含落脚点带来的那一份**（`docs/控制分配-作动器wrench分配设计.md` §8）。

**输出的是力，不是期望速度**（§12.1 已定）：控制器交出的是摩擦锥内的平面控制力，力律见 §7.4、两个量的取法见 §7.6。

### 9.6 已知简化

只列**本方案实际承担**的简化。

| # | 简化 | 后果 | 性质 |
| --- | --- | --- | --- |
| 1 | **地面反力不手工预生成** | 无 | 不算简化而是纪律：地面反力由接触层自己的求解器给出。角色控制器预先算一份"腿力"再让求解器重解一遍，就是同一次接触被算两次 |
| 2 | **舵面的铰链反作用力矩不建模** | 少一项直接力矩。它相对舵面自身控制力矩约小一个量级 | 可忽略，理由是**结构性**的：舵面若无刚体则不存在铰链；若是有刚体的 SubPart，铰链力矩由铰链上的作动器反力矩承担（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java` 在 6DOF 的旋转自由度上开伺服）。两种情况都不需要我们在 `τ` 里补一项 |
| 3 | **雅可比在当前工作点线性化** | 气动力对偏角不是线性的：升力与阻力两个分量随攻角各自转动，`cl` 还在失速处被硬性裁剪（§10.1、§10.3）。列只在当前工作点附近有效 | 用**界上的割线**把它压到最小：模型在 `u = 0` 与 `u = u_max` 两端严格精确，残差只剩区间内的曲率，实测峰值 **7.5%**（`docs/控制分配-作动器wrench分配设计.md` §3.2） |
| 4 | **控制力的饱和上限用静态法向力估算** | `μ_eff·N` 里的 `N` 取 `m·g·cosθ`，不取接触求解器给出的瞬时法向冲量。额外法向载荷（被踩、被下压、落地冲击那一拍）与瞬态摩擦上限都不进 `N`，`μ_eff` 也由配置约定给出而不是引擎上报 | 可接受，理由是**被放弃的那两个量的来源在现行形态里都不存在或不可靠**：控制器的碰撞掩码只含 `TERRAIN`（§2.2 选择 4），因此没有第三方压在身上；而接触点那条路要先确认 `../Spark-Core/src/main/java/com/jme3/bullet/collision/ManifoldPoints.java#getAppliedImpulse` 的读数含义、再承担「接触发生的那一步 `N = 0`」的一拍空档。三条代价与换来的收益见 §7.6 |

**简化 2 的定量依据**：铰链力臂是铰链到压心的距离，对后缘襟翼约弦长的 0.25、对全动翼面约弦长的 0.35；而同一份力对胶囊的力臂通常是米级。两者之比约为 `0.08 / 1.0 ≈ 8%`，且 `q` 与面积在两边同时出现、约掉了，**这个比例不随速度变化**。唯一可能推翻它的情形是「全动翼面 + 需要模拟失速手感」——失速时压心突然后移会让这一项出现非线性跳变。

**简化 3 的边界在哪**：割线在区间的两个端点严格精确，误差只来自区间内的曲率，实测峰值 7.5%（`docs/控制分配-作动器wrench分配设计.md` §3.2）。误差这个量级**不需要设阈值去防**，理由是结构性的：分配器的输出是**净 wrench 指令**，它经气动力函数与接触层回到胶囊的加速度，环路上因此带一个增益近似为 1 的反馈——几 % 的增益误差只影响收敛速度，不影响收敛性。**真正需要盯的不是曲率，而是列的模长**：它在整个可用区间上永远是正的（`cl` 的裁剪对两端同向生效），零列只出现在 `u = u_max` 那一端也失速之后（§12.6）。

**简化 4 的边界在哪**：被放弃的是「真实法向力的瞬时值」与「引擎实际使用的组合摩擦」这两个读数。前者在碰撞掩码只含 `TERRAIN`、且胶囊不与第三方接触的形态下，与 `m·g·cosθ` 的差额只来自顶点/接缝处的接触点数目与求解器迭代收敛，量级由 P1 的地形回归给出；后者的差额由 §7.5 的材质写入路径补回，届时 `μ_eff` 从常量变成接触对的函数，力律形式不变。**两条都不影响力律的形状**，只影响 `μ_eff·N` 这个上限取多大。

**饱和与 windup 的边界**：作动器撞界时实际出力被截住，而环路上若存在积分项，控制器内部会继续累积。本方案不另设饱和判据——**分配器的残差就是饱和缺口**（`docs/控制分配-作动器wrench分配设计.md` §5.1），按 `实际出力 / 期望出力` 回退积分即可。

**力矩相消必须显式保留**：因为力矩由我们自己算（§8.1）而不是由引擎从作用点导出，`Σ(r × F)` 的相消关系不会自动成立。若不显式保留，会出现「要到一份净力，却连带得到一份并不存在的净力矩」。

## 10. 空中气动

### 10.1 复用 SubPart 已有的气动系统

`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#prePhysicsTick` 已经在每物理步为每个流体动力计算点算气动力，模型是**一阶 + 二阶双项**：

```
一阶（粘性）：  F₁ = viscosity · c₁ · |v| · wettedArea
二阶（惯性）：  F₂ = 0.5 · density · c₂ · |v|² · projectedArea
```

坐标：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/util/mechanic/DynamicUtil.java#applyAxisDrag`。设计说明见 `../Machine-Max/docs/wiki/4-物理与战斗机制/4.2-流体动力学与气动.md`。

要点：

- 系数是**每个方向一对**（一阶 / 二阶），六个方向各自独立，默认 `[0.1, 1.0]`（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/HydrodynamicAttr.java#DEFAULT`）；
- **逐轴各向异性已经存在**：`DynamicUtil.java#applySimpleDragAllDirections` 对三轴分别使用 `projectedArea.x/y/z`（`SubPart.java#projectedArea`，可由 `SubPartAttr#projectedArea` 显式配置，或由 `../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/Part.java#calculateProjectedArea` 自动算出）；
- 还有跨音速增益、升力（简易系数或升力线模型带失速裁剪）、以及**部件互相遮挡**（沿来流方向射线，按 `SubPartAttr#hydroPriority` 判定谁遮谁）；
- **升力与诱导阻力是耦合的，但只在高级气动分支里**：`DynamicUtil.java#advancedAeroForce` 用 `cd = cd0 + kInduced · cl²`（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/AdvancedAeroAttr.java#kInduced`），`cl` 由**局部来流攻角**算出。所以「偏转 → 攻角变 → `cl` 变 → `cd` 跟着变」这条耦合在力函数内部成立。而简易模型（`advanced` 为假，`HydrodynamicAttr#advanced` 的默认值就是假）走 `applySimpleDragAllDirections` 与 `xLift/yLift/zLift`，**升力与阻力之间毫无关联**；
- 施加方式在 `SubPart.java#prePhysicsTick` 里是 `PhysicsRigidBody#applyForce`（力 + 作用点），**施加在每个 SubPart 自己的刚体上**。本方案改为只取该步算出的力与作用点，交由 §9.1 的归约汇总到胶囊——施加权的归属见 §12.7；
- 只在服务端、且 |v| > 0.1 m/s 时计算。

**因此不需要新增气动模型**，需要定的是它与其他力通道的关系，以及两个输入量（计算点位姿、当地速度）取谁。

### 10.2 逐计算点的速度

气动力的输入是**那个计算点自己的速度**，不是某个全局速度。这不是新增要求，是现有实现的既有做法：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/util/MMMath.java#relPointLocalVel` 取的就是「该 SubPart 质心线速度 + `ω × r`」，其中 `r` 是计算点相对该 SubPart 质心的位移。

```
v_点 = v_SubPart + ω_SubPart × r_点
```

**这个 `ω × r` 项就是后掠、上反角与滚转阻尼的全部来源**：

| 特性 | 靠什么产生 | 用统一速度会怎样 |
| --- | --- | --- |
| **后掠的风向标稳定性** | 偏航时翼根与翼尖看到的来流方向不同，两侧展向流动不对称 | 各点来流一致，恢复力矩**恒等于零** |
| **上反角的滚转恢复** | 侧滑时两侧局部攻角一增一减，升力的横向分量给出恢复力矩 | 两侧攻角相同，恢复力矩**恒等于零** |
| **滚转阻尼** | 滚转时一翼下压一翼上抬，`ω × r` 给出相反的法向速度，阻力差形成反滚转力矩 | 两侧法向速度相同，阻尼**恒等于零** |

三者都是**静默失效**：公式不报错，只是那几项再也算不出来。因此有三个"不能用"：

- **不能用胶囊的速度场。** 分轴锁 `(0, 1, 0)` 把 pitch / roll 的角冲量全部吃掉（§2.2 选择 2），落地摆正期间角因子更是 `(0,0,0)`，所以胶囊的 `ω` 对俯仰与滚转恒为零——**上反角与滚转阻尼会精确地等于零**。
- **不能用躯干速度代偿。** 用躯干或任何单一刚体的 `ω` 等于假设整个装配体是刚性的，而 SubPart 之间是约束连接的。各 SubPart 自己的 `(v, ω)` 是它们作为真实动力学刚体的真实状态，不需要这个假设。
- **不能用配装期的静态位姿代替 `p_i`。** 力臂必须每步重算，理由见 §9.3。

用 SubPart 自身的状态还有一个额外收获：**舵面相对机翼的偏转速率被自然算进 `v_点`**，而它是舵面控制力的时间导数来源。用任何别的刚体的角速度都会把这一项丢掉。

**气动点随舵面一起转。** 定位点相对所在 SubPart 的局部变换是个**装配期常量**——`SubPart.java#getLocatorLocalTransform` 只查 `attr.getLocatorTransforms()`，而这个映射由模型加载器在装配期烘焙一次（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/SubPartAttr.java#locatorTransforms`），运行期不再变。因此气动计算做的是「把世界速度转进**该 SubPart 当前朝向**的坐标系」，解出的力与力矩也相对那个坐标系——舵面整体偏转时，气动点与它所在的坐标系一起转。这件事有两个直接后果。

**一、方向由偏角与来流共同决定。** 一份力要变成控制力，靠的就是它的方向随 `δ` 转，而它能转多少取决于**铰链轴与来流所在平面的夹角**：这个函数只认定位点局部坐标系的 y-z 分量，铰链轴若落在那个平面**内**，偏转只搬动升力平面的法向，同一份计算实测下来的列模长会掉两个量级（`δ_max` = 25° 时从 1118 N 掉到 25 N），**舵面等于装了不动**。铰链轴垂直于该平面时，绕它转 `δ` 把局部来流角**精确**平移 `δ`，而 `q` 与该平面内的模长都不变——这正是「偏角变攻角」这个作用要的形态。所以配装期的几何约束是：**铰链轴垂直于局部来流的 y-z 平面**，等价于「铰链轴同时垂直于弦向与来流法向」。判据不是角度本身，而是「装上之后割线列的模长够不够大」（`docs/控制分配-作动器wrench分配设计.md` §3.1 的取法）。

**二、偏转必须真的转那个刚体，而且动画骨骼不算。** 气动计算读的是 `body` 的世界朝向（`SubPart.java#getLocatorWorldTransform` → `PhysicsRigidBody#getTransform`），因此让偏角生效的唯一途径是**铰链作动器把舵面那一块 SubPart 在 Bullet 世界里真的转过去**（`JointDriverSubsystem.java#onPrePhysicsTick` 的 `MotorParam.ServoTarget`）。定位点变换本身由装配期烘焙（`SubPartAttr.java#buildHydrodynamicLocatorsCache` 与同文件 `#addLocator`，后者把骨骼静置姿态一并烘进去），**骨骼动画不会更新它**：偏转若只做成视觉动画（`Part.java#onPrePhysicsTick` 的 `animController.physTick()` 那条路），气动力**完全不变**，舵面不产生任何控制力，而且不报错。判据是「气动点所在的那个 SubPart 的刚体在转」。

**一个物理步内的时序是「先写指令、后算气动、再步进」。** `VehicleCore.java#prePhysicsTick` 先跑 `subSystemController.prePhysicsTick()`（本步的偏角指令在这里落地成伺服目标），再跑各 `Part` / `SubPart`（气动在这里算），最后才是求解器步进。因此**本步气动用的偏转角是上一步末的关节角**，比指令晚一步，而这一步的差距正由 `docs/控制分配-作动器wrench分配设计.md` §7 的代回复核按实际值补上。

**服务端与客户端的差别**：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#setKinematic` 只在客户端被调用（构造函数里按 `isClientSide()` 判定），所以客户端的气动刚体是运动学的。气动只在服务端计算，因此服务端读到的是求解器给出的真实角速度，而客户端的运动学刚体给出的角速度是零——那里不跑气动，所以不影响结果，但读速度的实现要知道这个差别。

**实现备注**：`MMMath.java#relPointLocalVel` 内部每次调用 `getAngularVelocityLocal(null)` 都会分配一个 `Vector3f`。归约层按点每 tick 调用，应当复用暂存向量。

### 10.3 仿射模型：基准项与增量项

**先把气动力怎么来的说清楚：它是每物理步现算的，不是任何形式的缩放。** 分配器只决定「该出多少偏角」，那个偏角下能出多大力由 §10.1 的力函数当场给出——力函数在气动计算点自己的坐标系里跑，输入是**该点当前速度**（含 `ω × r` 与偏转速率，§10.2），有效攻角就是来流角与当前偏角的合成。所以本方案里**不存在一个「按动压缩放控制力」的系数**。

这件事与 §9.4 那句「模长随动压 `q` 缩放」不冲突，两者说的不是同一个量：

| 量 | 是什么 | 谁决定 |
| --- | --- | --- |
| **气动力本身** | 求解器这一拍真正要吃进胶囊的力与力矩 | 力函数按**当前**位姿与**当前**速度现算（本方案） |
| **雅可比列的模长** | 分配器**预期**「每单位 `u` 能换来多少」 | 与 `q` 成正比，用作权重与饱和判据 |

**控制分配拿列去解方程，施加的是力函数算出的力**（§8.1 的单一施加点照实收）——预测量与实际量之间没有替代关系。

**分配器要的那一步近似，是在这个每步计算之上叠一次线性化。** 气动力里含有**偏转带来的那一份**，而那一份就是控制力。这件事在分配器里不需要「切分」——它就是**一次仿射建模**：

```
w_aero(u) = w_aero(0) + J · u
             └─截距─┘   └斜率┘
```

| 那"一遍"力函数 | 同时是什么 |
| --- | --- |
| `u = 0`（基准偏角） | **截距**：固定零件与舵面的基准气动力，进目标减法（§10.4） |
| `u = u_max` | **斜率端点**：给出割线列 `J_k`（`docs/控制分配-作动器wrench分配设计.md` §3.1） |
| 实际 `u` | **代回复核**：校验实际出得来多少（`docs/控制分配-作动器wrench分配设计.md` §7） |

三样东西出自同一个力函数、同一套输入，因此**不重不漏是构造性质**，不依赖「拆一份结果时对不上参考点」这类约定。固定零件只需要第一遍（它没有偏角这个量），舵面需要前两遍，第三遍对所有作动器都要做。

**低速失效因此也是构造性的**：`q = ½ρv²` 趋零时舵面的列模长趋零，分配器自然不会用它，不需要额外加一条「速度不够就没有舵效」的规则。

**基准项不能走错通道**，否则二选一都是错的：

- 把它当控制力 → 基准阻力被当成了可支配的机动能力；
- 把它从目标里漏掉 → 作动器被要求去凑一份**环境已经给过**的力，等于凭空造力。

**这个力函数的真身，以及「它的方向也随偏角转」这件事的实测**：入参里没有偏角——偏角是通过定位点自身坐标系的旋转、把局部来流角平移 `δ` 进入的；动压 `q = ½ρ(v_y² + v_z²)` 与投影面积在这个旋转下都不变。于是当场能写出来的只有两项：升力 `q·S·cl(α)` 垂直于来流，阻力 `q·S·(cd0 + kInduced·cl²)` 沿来流，`cl(α) = liftSlope·(α − alpha0)` 并在失速处被裁剪，而 `α` 是**来流攻角与偏角的和**。因此它不是一个「沿固定方向、大小随 `u` 线性增长的力」——来流在翼面坐标系里随 `δ` 转，升力方向跟着转，力矢量在本体坐标系里也就转；**控制力正是这一份**。本体坐标系下的力场表、割线在区间上的实测误差（两端精确、中点峰值 7.5% 列模长）、以及两个曲率来源的相消关系，都在 `docs/控制分配-作动器wrench分配设计.md` §3.2。

**截距与斜率是每拍重取的，不是配装期标定值。** 它们与偏角无关，但与**当前工况**有关——当前速度决定攻角与 `q`、当前位姿决定力臂与力的方向、当前遮挡因子决定列模长、当前气动系数（含损伤）决定 `cl` 与 `cd`。每物理步现算这四项的清单与理由见 `docs/控制分配-作动器wrench分配设计.md` §3.2；气动侧要保证的是**这四项数据本身每步都是新的**（§10.2 的三个"不能用"）。

### 10.4 气动的去向：目标上的减项

基准项（`u = 0` 的那一份）在**分配目标**里被减掉；施加时它与作动器的力一起进入合力：

```
w_alloc      = w_des − w_known                         目标：作动器要凑的量
u            = 级联伪逆(J, 界, W, λ, w_alloc)          求解（`docs/控制分配-作动器wrench分配设计.md` §5）
F_out, τ_out = 各力源实际 wrench 之和 = J·u + w_known    施加：每物理步各一次（§8.1）
```

`w_known` 的内容：**固定零件气动的全部、舵面的 `δ = 0` 基准项、以及其它已知且可测的干扰力矩**。重力是否算在内，取决于控制层希望 `w_des` 表示「胶囊的净受力」还是「除重力之外的受力」——无论取哪种，**这条减法与它保持一致**即可。

**它不是「输出上加一份抵消力」。** 施加的永远是**各力源的实际力**：机翼的升力是真的（由气动模型给出），推进器的推力是真的（由油门与力函数给出）。所谓「抵消」发生在**目标那一侧**——因为目标里减掉了基准项，作动器才会被要求多出一份去顶它；顶不动时缺口照实报出来，胶囊就真的减速了。

反过来，若把基准项当作「输出上的额外抵消量」，那一份就**没有任何作动器在提供**，而 §8.1 的手工合力让引擎不会替我们检查这件事——那才是凭空造力。三条路的完整对比见 §10.6。

### 10.5 为什么不能折进界（权限）

一个自然的想法是把气动并入作动器的能力描述，作为界的偏置——即把某作动器的可用区间整体平移一个 `−D`（阻力反方向）。设某轴推进器配置为 `F ∈ [0, 1000] N`（单侧推进器，零下限的含义见 `docs/控制分配-作动器wrench分配设计.md` §6 的四种区间），当前该轴阻力 `D = 500 N` 且与速度反向：

| 速度方向 | 偏置后的可用区间 | 问题 |
| --- | --- | --- |
| 沿 −轴（阻力指向 +轴） | `[0 − 500, 1000 − 500] = [−500, 500]` | 新下界 −500 落在**没有反向推进器**的方向上，这个负值是假的 |
| 沿 +轴（阻力指向 −轴） | `[0 + 500, 1000 + 500] = [500, 1500]` | 上界超出推进器能力 500，**执行层做不出来**；且下限 500 > 0，等于宣称这台推进器**关不掉**，而它其实随时可以不出力 |

即偏置法让区间的两端**同时**失去物理意义（一端是假的、一端不可实现），第二行还额外丢掉了「零出力永远可达」这一条。根本原因是它把「环境施加的力」与「引擎能出的力」混进了同一个区间。

除此之外还有三条理由：

1. **升力不是阻力。** 升力垂直于来流，不可用"沿速度方向的偏置"表达；带倾角时升力可以指向侧向甚至向下，标量偏置编码不了。
2. **偏置是速度平方的、界是缓变的。** 上面的 `[−500, 500]` 只是当前速度下的瞬时值，速度一变整个区间就变了，界随之每步变形状——而界本该是配装期确定、运行期缓变的能力描述。
3. **每轴独立假设在斜流下失效。** 气动系数是按流体动力计算点本地坐标系的六个方向给的，而气流相对本体是任意方向；斜流下 Z 轴的阻力耦合进 Y 轴，逐轴盒的对角结构保不住。

### 10.6 三条路的对比：改界、改目标、绕开分配器

同一份气动力可以放在三个位置，后果完全不同：

| 做法 | 改的是什么 | 模型偏差的后果 | 判断 |
| --- | --- | --- | --- |
| **折进界** | 作动器的**界**（权限） | 界就是权限。预测偏差直接吃掉机动权限——连"想出的力"都出不了 | ✘ 见 §10.5 |
| **折进目标（矢量减法）** | 需求的**大小** | 只是**当拍问错了量**。权限完好，下一拍由 `w_des` 重算目标继续纠 | ✔ 本方案（§10.4） |
| **加在输出** | 绕开分配器 | 那一份**没有作动器在提供**，而手工合力让引擎不会检查（§8.1）——凭空造力 | ✘ |

**第二行与第一行的区别必须说清：折进目标不损失权限。** 它只改**需求**——`J` 与 `u` 的界一根毫毛都不动。模型不准时给出的只是「这一拍问错了量」，而 `w_alloc` 每拍都由 `w_des` 重算，反馈下一拍继续纠。所以它与「把偏差当残余扰动」是同一个性质，**不是** §10.5 批的那种污染权限。

**第三行为什么是凭空造力。** 以「沿 +x 想保持速度、阻力 500 N 反向、推进器上限 300 N」为例：

| | 分配目标 | 分配结果 | 实际施加 | 净力 | 缺口报告 |
| --- | --- | --- | --- | --- | --- |
| 加在输出 | `w_des = 0` | `u = 0` | `0 + 500 = 500 N` | `−500 + 500 = 0` | **0（谎报）** |
| **矢量减法** | `0 − (−500) = +500` | 饱和，`Ju = 300 N` | 实际力之和 `300 − 500 = −200 N` | `−200 N` | 200 N ✔ |

第一行的 500 N 里**有 200 N 没有任何作动器提供**，是靠算术变出来的；而且缺口报成 0——残差是 windup 保护的输入（`docs/控制分配-作动器wrench分配设计.md` §5.1），这个谎会被用上。第二行把这份需求送进级联，饱和、`u_actual`、缺口、windup 回退全部自洽。

**对模型精度的要求不高**：只要把扰动压到反馈带宽以内，剩下的由反馈处理。而气动模型本来就在每物理步跑，`w_known` **复用的是同一份模型、同一份数据**，不需要为它单建一套预测器。代价是那道力函数要多跑两遍（`u = 0` 与 `u = u_max`，见 §10.3），但不算新的模型开销。

**配平有了明确的归属。** 协调盘旋要求 `n = 1/cos φ` 倍的升力、进而 `n²` 倍的诱导阻力（量级：20 m/s、翼面积 1.0 m²、`cd0 = 0.05`、`kInduced = 0.06` 时，30° 盘旋的阻力比同速平飞高约 22%）。在「前馈 + 反馈两路相加」的写法里，这份多出来的推力没有归属。在目标减法里它自己就出来了：`w_known` 每拍按**当前**状态算（含当前的 `cl` 与 `cd`），`w_des` 要的是净受力，**差额自动落进 `w_alloc`，由分配器去找谁来出**。飞行控制层因此只剩一件事——把意图翻译成 `w_des`（§12.2）。

### 10.7 目标减项的取模取向（待定）

目标减法把气动**预**减掉了，于是「损伤后自然失衡」这个期望表现会被压掉一部分：如果 `w_known` 用的就是当前（已损伤）的气动模型，那它减掉的是"现在真实的气动"，失衡被主动纠正。

因此要明确一个取向：

- **失衡作为表现** → `w_known` 只能用**未损伤的基准模型**，让损伤造成的那部分偏差留给反馈去纠（纠不动就是失衡）；
- **抗扰优先** → `w_known` 用当前完整模型。

这不是技术选择而是手感选择。它同时决定飞行控制层的增益该多大，因此与 §12.2 绑在一起。

1. **意图 → `w_des` 的完整路径与增益整定**。`w_des` 的语义已经定死为「胶囊的期望净 wrench」（§9.4），剩下的全在这一层：姿态环与速度环怎么串、增益取多少、要不要积分项（要的话其抗饱和按 §9.6 的缺口回退做）。

| 质量变化后的重标定 | §7.4 的对账表按 70 kg 给出。表里的静值本身与质量无关（`m` 在锥截里约掉、顶速只由 `c₀·m·g` 与功率给出），因此损伤改变质量后要重算的是内阻的导出式 `c₀ = P_base / (v_ref·m·g)`；锁与惯量在改质量后仍有效已实测（`docs/角色控制器-刚体原型与引擎约束.md` §6.2） |

**需要谁定**：专门一轮讨论，可以在 P1（真地形回归）之后。

**定了之后动什么**：§7.5 的写入路径与 §7.6 的静态估算，以及是否在 `../Spark-Core` 侧为地形接触补一条按点写入的路径。

### 12.5 速度相关阻力的唯一来源

**卡在哪**：仓库里已经有一个速度相关耗散通道——`common/control/attr/MechaWalkingAttr.java#C1` 映射到 KCC 的 `setLinearDamping`（当前取值为 0，即实际未启用）；`docs/角色控制器-行走物理设计.md` §3.6 也把 `c₁` 列为待映射的粘滞阻尼参数；而 §10.1 的气动系统自带一阶粘性项。三者若同时存在，同一台机娘身上就会出现多套速度相关阻力。

**需要谁定**：可以与 §12.4 一起定。**气动挂起期间这一条不阻塞任何人**：气动的一阶项此刻不存在，因此当下只有两个候选（`C1` 映射与力模型自带项），可以先把 `C1` 到 `setLinearDamping` 的映射归零并标注来源待定。

**定了之后动什么**：确定唯一来源；若最终由气动一阶项承担，则删掉 `C1` 到 `setLinearDamping` 的映射，并在 `docs/角色控制器-行走物理设计.md` §3.6 与 §5.1 里把 `c₁` 标注为「由气动一阶项承担，不再是独立参数」。

### 12.6 默认气动系数对行走的影响（挂起：随 §12.2 一起）

**挂起的理由**：本条全部落在气动参数上，而气动的来源是 SubPart（§12.2 的挂起理由）。它不挡地面角色控制器。

**接入气动时要定的头一件事，是用默认系数与一组假定值粗算的结果**：6 m/s 的二阶阻力约 11.6 N、约 0.17 m/s² 减速度，相对地面低速区约 8 m/s² 的控制力加速度几乎无影响——**这是参数估算而不是实测**，`projectedArea` 的取值是按机娘尺度假定的 0.5 m²，实际值由 `Part.java#calculateProjectedArea` 从模型算出。

另外遮挡检测的 `HydrodynamicAttr#effectiveRange` 默认 **1.0 m**，即 1 m 内的同装配体部件默认会互相遮挡；该默认值是按载具尺度给的，机娘的部件间距是否落在同一量级需要确认。

**还有一个开关必须显式确认**：`HydrodynamicAttr#advanced` 的默认值是 **`false`**，而**只有高级气动分支里才有升力与诱导阻力的耦合**（`cd = cd0 + kInduced · cl²`，见 §10.1）。默认配置下走的是简易模型，升力与阻力互不关联——对一架要做盘旋、失速、跨音速的机体来说，这个默认值不能就这么留着。**它同时决定气动面在分配器里有没有用**：简易模型下舵面的列几乎只剩 `cd` 的二次项，`∂/∂δ` 很小，分配器会**自动不用它们**——不报错，只是气动面等于没装（`docs/控制分配-作动器wrench分配设计.md` §3.1）。

**失速之后列不是变成零，而是两端同向失速之后才变成零。** `DynamicUtil.java#advancedAeroForce` 把 `cl` 硬性裁剪到 `±clMax`（该文件里 `clMax = aero.liftSlope() · aero.alphaStall()`），而 `δ` 使攻角**单向**变化，所以工作包络内的两种形态是：

| `α_free` 相对失速角 | `u = 0` 端 | `u = u_max` 端 | 列 |
| --- | --- | --- | --- |
| 小于失速角 | 线性段 | 可能已裁剪 | 有限值，与未失速时同量级 |
| 大于失速角 | 已裁剪 | 已裁剪 | `cl` 在两端相同，只剩 `q` 与来流方向之差 → **远小于有限值，但不为零** |
| 两端完全重合（`α_free` 足够大） | 裁剪 | 裁剪且来流方向之差也趋零 | **零** |

按默认系数（`AdvancedAeroAttr#DEFAULT`：`liftSlope = 6.28`、`alphaStall = 0.52` rad ≈ 29.8°）实测列模长：`α_free` = 29.8° 时 1136 N（峰值），35° 时 930 N，45° 时 611 N，50° 时 545 N（谷值），60° 时 578 N（已到零列区的边界形态）。

**因此零列死区在 `α_free > 29.8°` 才开始，而边界上的跳变比「跳到零」轻得多。** 要处置的是那一段列模长的**快降**（30° → 50° 掉到一半）与它带来的方向变化。候选处置：对列做低通（按上一拍插值）、把硬裁剪换成饱和过渡、或接受它（失速本来就是非线性区）。

**需要谁定**：需要在真实装配体上取一次实际 `projectedArea`，并显式决定 `advanced` 的取值与 `AdvancedAeroAttr` 的系数（`liftSlope` / `alphaStall` / `cd0` / `kInduced`）。

**定了之后动什么**：§10.1 的参数取值、§10.6 里 `w_known` 的精度、`docs/控制分配-作动器wrench分配设计.md` §10.2 的割线列在失速区的处置。

### 12.7 怎么让 SubPart 不再自行施加气动力（挂起：随 §12.2 一起）

**挂起的理由**：本条的四个选项都要求 SubPart 已经接入本仓库——它要决定的是「谁把那份气动力加到哪个刚体上」，而 SubPart 与装配体的双体结构都还没有落点（§12.2、§12.3）。气动不接入时不存在「同一份气动力算两次」的风险，因此它不再是「接线前必须先定」的阻塞项。

**接入气动时这一条会立刻变成前置项**，因为 §10.1 的现有实现是**每个 SubPart 把气动力施加到自己身上**（`SubPart.java#prePhysicsTick` 里的 `this.body.applyForce(...)`），而 §9.1 的归约要求这份力作为数据交给胶囊侧的单一施加点。两者并存会把同一份气动力算两次——一次进了 SubPart 自己的刚体，一次进了胶囊。

**已经排除的选项**：「保留 SubPart 自施加、胶囊不重复接收」不可行。SubPart 自施加改变的是**它自己的角动量**，而约束不会把这份力矩转交给胶囊，因此这条路的代价是**永久放弃气动姿态控制**；它换来的是省掉一次改造。

**剩下的两条路，区别只在改造放在哪一层**：

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| **改 Machine-Max** | 让 `SubPart` 不再对自己的刚体施加气动力，或把它抽出来由装配体统一施加 | 要动同级仓库；施加权收口在装配体层，语义最干净 |
| **ARMS-Core 侧拦截** | 在 `SubPart.prePhysicsTick` 的施加调用点上注入并接管 | 不动 Machine-Max；注入点与上游实现耦合，上游改一行即断 |

Machine-Max 自己已有第二种形态的先例——`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/mixin_native/VehicleCoreMixin.java` 用 `@Inject(method = "prePhysicsTick", at = @At("HEAD"))` 把 `VehicleCore` 的物理步挂进 `PhysicsTestBus`。

**需要谁定**：与 §10.4 目标减项的接线一起定。

**定了之后动什么**：§10.1 的施加方式那一行，以及 §10.4 的接线。选定之前 §10.4 不能接线。

**本条与分配决策解耦。** 无论物理那份气动力最终由谁施加，控制器都得**用推力**去顶它（§10.4 的矢量减法），因此目标减法的形式在两条路线下都成立——少一个悬而未决的耦合。

### 12.8 朝向自由度（已定）

锁 pitch / roll、留 yaw（`(0, 1, 0)`），不采用全锁 `(0, 0, 0)`：角因子会丢掉约束冲量的偏航分量，胶囊在偏航上退化成不可被约束改变的参考体。理由、朝向写入的形态与角速度的处理写在 §4.1、§5.2、§5.3：朝向不走力矩通道，而是每物理步由位姿写入把视野偏航绝对写进刚体姿态，得到的胶囊朝向即躯干的目标朝向。地面与落地收敛窗口因此同为一组 4 行活行（§9.4）。

**角速度的处理是「朝向左写入、倾角按系数衰减」两条，不清 `ω_y`。** 朝向由每步现算的位姿写入对齐（§5.3），求解器在一步里注入的偏航角速度只表现为步内转动，下一步写回；pitch / roll 那两轴由角因子锁死，落地首步另做一次衰减。清除 `ω_y` 只作为实测摆动可观时的兜底，判据见 §12.9 的第二项。

两条原型判据的含义随之明确：`src/test/java/io/github/sweetzonzi/arms_core/common/control/RigidBodyControllerPrototypeTest.java#singleAxisTiltSettleLeavesYawUntouched` 与 `#obliqueTiltSettleLosesSomeYawAsThePriceOfAnOffAxisLanding` 检验的是**收敛律单独作用**时的行为（后者那张累计偏差表在控制器里被每步朝向写入截断，§5.3）。

### 12.9 三处待测：已量出数值

三项都不改变任何写法，只决定「要不要加兜底」。测量落在
`src/test/java/io/github/sweetzonzi/arms_core/common/control/RigidBodyControllerMeasurementTest.java`
（真 `PhysicsSpace`、100 Hz、驱动的是正式控制器而不是裸刚体）。**结论是三项都不需要兜底。**

| 待测量 | 结论 | 实测值 |
| --- | --- | --- |
| **越障那一步的水平速率残留** | **不需要兜底。** §6.2 的「水平速度原样保留」成立，而且没有被接触吃掉 | 0.5 m 半砖：贴墙前一拍 **2.284 m/s**，越过后一拍 **2.284 m/s**，比值 **1.0000**；脚底最高 **0.5000 m**（精确等于台阶高度），越过后继续推进到 z = 40.08 |

| **起步头十步的平均加速度** | **对账表的低加速区那一行成立。** 前馈把引擎摩擦抵消掉之后净力就是 `μ_eff·N`，加速度 `μ_eff·g`，`m` 在锥截里约掉 | 平地、`μ_eff = 1.0`、前馈开：十步末速率 **0.99081 m/s** → 平均加速度 **9.908 m/s²**，解析值 9.81 m/s²，比值 **1.0100**（+1.0% 即前馈余量）；最大侧向速率 **0.000000 m/s** |

**第一项与第二项的判据形态原样落地**：第一项用「胶囊前缘离台阶立面不足 2 cm」识别贴墙那一拍
（不依赖速度），第二项用刚体旋转矩阵的局部 +Z 水平投影测朝向、并先把初始朝向对到目标再开始采样
（否则第 0 步会把一次性对齐误记成摆动）。

**第三项的对照组顺带证伪了「不要前馈」这条替代路线**：同一场景把前馈关掉，十步末速率
**0.00000 m/s**（解析值 9.81）。原因是引擎给的是静摩擦锁定而不是「从受力里减掉 `μN`」，
`F_MAX = 700 N` 与 `μ_eff·N = 686.7 N` 只差 13 N，净力恰好落在锁定量级上。机制与数据见 §7.4。

**顶速不在本表的三项内，它是新登记的标定项**：见 §12.10。

### 12.10 顶速标定：实测高于对账表

**卡在哪**：§7.4 的对账表里，起步加速度那一行是恒等式且已实测复现（9.908 对 9.81），但**顶速
那一行不是**。实测站立顶速 **25.0 m/s**（对账表写 6.0）、蹲伏 **10.7 m/s**（表写 1.8），
而且两者的比值是 **2.14** 而不是 `MOVE_SPEED_MODIFIER` 的 0.3。

**机制已经查清**：平衡式是 `F_drive = 引擎接触摩擦`，而 `F_drive` 被截在 `μ_eff·N` 上，因此平衡
点是 `computeDriveForce(v_eq) = μ_eff·m·g`（当前参数下解析给出 1.17 m/s，再叠加 `F_drive ≤ F_MAX`
的锥截与「前馈在高速区不再完全抵消摩擦」两项，数值落在十几到二十几 m/s）。它不是旧模型里
`= c₀·m·g` 那个平衡点，因此 `P_base / (c₀·m·g) = 6.0 m/s` 这条推导在本力律下不成立。

**倍率不等比的原因**同一处：锥截上限 `μ_eff·N` 是常数，而 `F_drive` 随 `k` 等比缩小，于是
`k` 越小、进入锥截越早，顶速就不再与 `k` 成正比。

**需要谁定**：专门一轮参数标定。可动的旋钮有三个，彼此约束——`MechaWalkingAttr#F_MAX`（起步推力
与锥截的相对大小）、`common/control/attr/MechaWalkingAttr.java#MU_NAKED`（角色侧摩擦，经同文件 `#TERRAIN_FRICTION` 组合后同时决定爬坡上限与锥截上限）、同文件 `#P_BASE`（力-速曲线）；三者的实测现状见 §12.10。
**其中 `F_MAX` 必须显著大于 `μ_eff·N`**：当前 `700` 对 `686.7` 只差 2%，前馈一关就完全不动，
说明这条余量本身就是设计参数而不是巧合。

**定了之后动什么**：§7.4 对账表的三行（站立顶速、蹲伏顶速、以及新增的起步推力余量），
`common/control/attr/MechaWalkingAttr.java` 的取值，以及 `docs/角色控制器-行走物理设计.md`
§3.5–§3.9 的顶速推导。

| **雅可比列 / 割线列** | 某个作动器的 `u` 变化一单位给胶囊带来的力与力矩（`J` 的一列）。气动面取 `u = 0` 与 `u = u_max` 两端之差，因此是**割线**而非切线，在两端严格精确（`docs/控制分配-作动器wrench分配设计.md` §3） |
| **分配目标 `w_alloc`** | `w_des − w_known`，即作动器真正要凑的那份 wrench。语义见 `docs/控制分配-作动器wrench分配设计.md` §2.1，本方案里气动基准项被减掉的具体算式见 §10.4 |
| **配平** | 让净受力为零所需的作动器输出（悬停顶重力、巡航顶阻力）。它由目标减法自动产生，不是独立的一路前馈（§10.6） |
| **windup** | 执行器被物理约束截住时控制器内部积分项继续累积的现象。本方案不另设饱和判据——分配器的残差就是缺口，按 `实际出力 / 期望出力` 回退积分（§9.6） |
| **位姿写入** | 直接写刚体的位置 / 姿态 / 碰撞形状，不经力或冲量通道。它不受角因子影响，因此「锁转 + 仍能摆正」成立；使用规则见 §6.1 |
| **摩擦锥前馈** | 力律里 `μ_eff·N·(1 + 余量)·û` 那一项：先把引擎在接触点上给出的反向摩擦加回去，使净力成为期望净力（§7.4） |
| **支撑接触** | 本步接触中「对方组为地形」且「法线竖直分量 ≥ 0.35」的那些接触点。着地判定取它们（§7.7），`cosθ` 由它们里最竖直的那一条给出（§7.6） |
| **着地窗口** | 向下扫掠允许的离地间隙（取 0.1 m）。它同时是 coyote 时长与「走出边缘多久之后算离地」的判据（§7.7） |
| **静态法向力估算** | `N = m·g·cosθ`：控制力的饱和上限用机体重力在支撑法线上的分量算，不读接触求解器的瞬时法向冲量。代价见 §7.6 |
| **静摩擦锁定** | 引擎对**受力接触体**给出的响应：施加的切向力不超过接触能传的 `μ_eff·N` 时被静摩擦精确抵消，超出部分才成为净力。因此「施加值等于 `μ_eff·N`」得到的是零净力而不是 `μ_eff·N`。实测与三条后果见 §7.4 |
| **摩擦锥前馈与释放余量** | 力律里 `μ_eff·N·(1 + 余量)·û` 那一项：把引擎在接触点上给出的静摩擦抵消掉，使净力等于 `F_drive`。余量取 1% 是为了把工作点推离静摩擦锁定面，否则净力恒为 0（§7.4） |
