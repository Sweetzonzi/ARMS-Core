## 1. 背景与目标

### 1.1 现行控制器与它的三个阻断性问题

现行的运动学胶囊控制器是 `common/control/MechaCharacter.java`，它继承 `com.jme3.bullet.objects.PhysicsCharacter`，承载 Bullet 的 `btKinematicCharacterController`（下称 KCC）。KCC 不是刚体，而是「幽灵体 + 手写三段扫掠 + 纯速度推导着地」，没有质量。由此派生出三个**阻断性**问题——它们不是"不够好"，而是相关能力**做不到**：

| # | 问题 | 证据坐标 |
| --- | --- | --- |
| 1 | **姿态轮廓无法接入**（蹲伏 / 卧倒的低矮胶囊） | `PhysicsCharacter#setCollisionShape` 带「不得在物理空间内」的断言；在世换形会让原生侧挂接一个未重建的碰撞对象，原生内存被破坏，进程以 `0xC0000409` 中止。因此 `MechaCharacter.java#applyPostureShape` 是一个永远返回 `false` 的弃用壳，`common/control/MechaControl.java#applyLogicOutputToKcc` 里对应的换形代码是注释掉的 |
| 2 | **撞墙时速度不归零** | KCC 的水平通道是「本步位移命令」，原生侧从不把实际走了多远写回，因此顶墙期间 `getLinearVelocity` 仍报告那份没能执行的命令（登记为 `docs/角色控制器-KCC制约调研与替换评估.md` §3.2 的 `B1`、`B2`；上游报告 `https://github.com/stephengold/Libbulletjme/issues/58`） |
| 3 | **无质量、不受外力** | 幽灵体不产生也不承受冲量，因此外部冲量（击退、爆炸）与子系统合力都没有可施加的对象——`common/control/MechaControl.java#addSubsystemForce` 至今是空实现，没有消费方 |

### 1.2 本方案替换什么、不替换什么

**替换**：只替换「动起来」这一层——从运动学胶囊换成动力学刚体胶囊，并随之重写接触摩擦、速度语义与落地处理的归属。

**不替换**：

- 双体结构。控制器仍是胶囊，躯干仍是动力学刚体，两者由约束相连，胶囊为躯干提供约束位姿（`docs/角色控制器-行走物理设计.md` §1.2）。
- 服务端权威、客户端零仿真（`docs/ArmsCore双端权威与网络同步实现计划.md` D1、D18）。
- 逻辑层与物理层的分工：状态机、动画、MoLang 调制**不动**（承载物换掉之后它们消费的仍是同一份输入与快照），`MechaControl` 仍是编排者。

### 1.3 可行性已实测

这条路线的关键未知——引擎是否提供所需能力——已用最小原型在真实 `PhysicsSpace` 上量过：锁转刚体的站立稳定性、撞墙速度归零、自写越障的判决阈值、引擎摩擦的标定、姿态自由度与角因子、地面姿态控制方案对照、落地摆正。全部数据与四条实现坑见 `docs/角色控制器-刚体原型与引擎约束.md` §2–§11。

## 2. 动力学代理

### 2.1 胶囊承担什么

角色在物理世界中由**一个胶囊刚体**表示，承担：

- 与场景几何体的碰撞求解；
- 位置积分与速度积分；
- 接收所有合力与合力矩；
- 为躯干约束、布娃娃与视觉提供位置与姿态参考。

胶囊**不对应可见形体**。可见形体由布娃娃节点或程序化动画承担；胶囊仅作为物理代理存在，命中判定也不使用它（见 §12 的待定项）。

### 2.2 四项已定型的选择

| # | 选择 | 内容 | 理由 |
| --- | --- | --- | --- |
| 1 | 承载物 | **动态刚体**（有质量、受求解器约束），不用运动学刚体 | 运动学刚体拿不到求解器的碰撞响应，滑墙、贴地、撞墙归零都要自己写，等于重写一遍 KCC；动态刚体让「被动响应」这一半回到引擎手里 |
| 2 | 姿态保持 | **分轴锁转**：`PhysicsRigidBody#setAngularFactor(Vector3f)` 逐轴给出旋转自由度的开关 | 该因子乘在角冲量/力矩的**累加处**，不修改逆惯量矩阵本身，因此 `(0, 1, 0)` 能同时做到「锁 pitch / roll 保持竖直」与「留 yaw 自由转身」。机制与实测见 `docs/角色控制器-刚体原型与引擎约束.md` §6 |
| 3 | 接触摩擦 | **引擎接管**：抓地、无输入制动、爬坡上限全部由接触点上的法向力与引擎摩擦给出 | 让引擎承担被动响应是选择动态刚体的初衷；逐方块材质差异（冰面 / 湿滑）随之可达。详见 §7 |
| 4 | 碰撞过滤 | 控制器本体的碰撞组只与**地形**碰撞（组 `PAWN`、掩码 `TERRAIN`） | 与现行 `common/control/MechaCharacter.java` 一致，迁移期不引入新的碰撞对；与躯干的碰撞由约束层处理，不靠碰撞组 |

## 4. 姿态自由度

### 4.1 状态划分

| 状态 | `angularFactor` | 姿态权威 |
| --- | --- | --- |
| 地面站立 / 行走 | `(0, 1, 0)` | 无。锁死，不需要任何姿态控制器 |
| 落地 / 进入地面 | `(0, 1, 0)` + 运动学收敛 | 姿态写入，见 §5 |
| 飞行 / 悬浮 | `(1, 1, 1)` | 飞行控制层，见 §12 |
| 布娃娃 | `(1, 1, 1)` | 无 |

`(0, 1, 0)` 的语义是「锁 pitch / roll、留 yaw」：站立必须竖直，但朝向可以自由旋转。因为该因子只按**轴**过滤，绕 Y 轴的角冲量（包括力臂产生的偏航力矩）仍然完整生效。

### 4.2 为什么地面不用 PD 姿态控制器

一个自然的想法是让旋转自由度全开、用条件启用的 PD 姿态控制器同时满足「地面稳定」与「空中自由」。**空中那一半成立，地面这一半实测不成立**：六组增益下胶囊全部先翻过头（最大倾角 178.66°–179.89°）并被弹离地面（脚底升到 +0.75 ~ +1.08 m），末倾角散在 0.58° 到 102° 之间。

机制是**单接触点**：胶囊只通过一个接触点与地面作用，任何绕质心的回正力矩都无法产生「把接触点移回质心正下方」的效果，反而主动把接触点甩到质心侧面，接触法向力随之出现向上的分量，胶囊起飞后进入自由翻滚。这是拓扑的固有形态，不是调参问题——完整数据与解释见 `docs/角色控制器-刚体原型与引擎约束.md` §7。

因此地面状态**不引入任何姿态控制器**，直接用角因子锁死。这也让「站立必须竖直」与「方向自由」这两个需求由同一个参数满足，比 PD 少一整层。

### 4.3 PD 归属飞行控制层

PD 的输入是期望姿态 / 期望角速度、输出是力矩，落点在飞行控制层（意图 → 力矩的路径），本文不展开。两条无论它落在哪一层都必须遵守的实现约束记在 `docs/角色控制器-刚体原型与引擎约束.md` §7.2（角加速度必须限幅；逆惯量为 0 的轴必须跳过）。

## 5. 落地处理

落地要解决两件事：把已经歪掉的姿态**摆正**，以及让姿态**此后再也不歪**。前者只能靠姿态写入，后者靠角因子锁死；两者可以在同一个物理步里同时开始。

### 5.1 锁与摆正是两个独立动作

**锁只负责「不再改变朝向」，不会把已经歪掉的姿态扶正。** 实测：躺倒 90° 的锁转胶囊静置 3 s 仍是 90.0000°、角速度恒为 0——胶囊水平躺地时重力过质心、接触法向也过质心，合力矩为零，是中性平衡。因此摆正必须由姿态写入完成，省不得。数据见 `docs/角色控制器-刚体原型与引擎约束.md` §8.1。

### 5.2 落地第一步即锁，而且只锁 pitch / roll

`PhysicsRigidBody#setPhysicsRotation(Quaternion)` 是直接的位姿写入，不经角冲量通道，因此**不受角因子影响**。这一条让「锁」与「摆正」不必分阶段：落地第一个物理步就把角因子写成 `(0, 1, 0)`，同一步开始收敛，不存在「先留自由度做收敛、收敛完再锁」的那个窗口，也就不需要为一个窗口设计打断条件。

实测这个配置（初态绕世界 X 轴 30° 纯俯仰）把求解器在收敛窗口内注入的 pitch / roll 角速度完全挡在门外：峰值 pitch / roll 角速度 **0.0000 rad/s**、水平位移 **0.0000 m**、朝向漂移 **0.0000°**。对照组在收敛期保持全开，注入的 pitch / roll 角速度随 `λ` 增大而减小（λ=0.05 → 0.722、0.10 → 0.112、0.20 → 0.074、0.35 → 0.061 rad/s），且 **λ=0.05 时根本收不住**——2 s 内没收敛，胶囊被推着水平漂了 0.82 m。数据见 `docs/角色控制器-刚体原型与引擎约束.md` §8.2。

**为什么留 yaw 不锁它。** 三条理由：

1. **锁 yaw 拦不住它想拦的东西。** 角因子只作用在角冲量 / 力矩的**累加处**，不作用在积分处：`../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btRigidBody.h#applyTorque` 是 `m_totalTorque += torque * m_angularFactor`，`#applyTorqueImpulse` 是 `m_angularVelocity += m_invInertiaTensorWorld * torque * m_angularFactor`，而 `m_angularVelocity` 本身没有任何一处被乘以该因子。落地那一帧自带的 yaw 角速度照转不误，清掉它是 §5.3 的活。
2. **yaw 不与姿态写入打架。** §5.3 读的是**当前**姿态，物理步里新产生的 yaw 会在下一步被读进去、当作既定朝向保留。互相打架的只有 pitch / roll。
3. **地面阶段只切换一次姿态自由度。** 若收敛窗口锁 yaw，角因子会走 `(1,1,1) → (0,0,0) → (0,1,0)` 三段，分配问题的行表随之 6 → 3 → 4（§9.8）。留 yaw 就是 6 → 4 一次切换，与 §4.1「地面 = `(0,1,0)`」一致。

### 5.3 收敛律

每物理步施加两次姿态写入：

```
u     = 当前姿态下刚体局部 +Y 的世界方向
tilt  = u 与 (0, 1, 0) 的夹角
① 最小旋转：轴 = (u × (0, 1, 0)) 的单位化，转角 = λ · tilt
② yaw 补正：绕 (0, 1, 0) 转回①带走的方位角，转角 = −Δyaw
锁       倾角 < 阈值 → 清角速度，角因子 → (0, 1, 0)
```

①的旋转轴垂直于倾角平面，把 `u` 沿「过 `u` 与竖直方向的大圆」拉向竖直，因此 `tilt ← (1 − λ) · tilt` 严格成立，时间尺度可以直接由 `λ` 算出：从 30° 收敛到 0.5° 需要 `ln 60 / ln(1/(1−λ))` 步，λ = 0.05 / 0.10 / 0.20 / 0.35 分别是 80 / 39 / 19 / 10 步。该步只用得到 `tilt` 一个角：`u × (0, 1, 0)` 的模长恒为 `sin(tilt)`，除以模长即得单位轴，`acos`、`asin`、`atan2` 都不出现。

角速度的 pitch / roll 分量按同一系数衰减，yaw 分量不动（§5.2 第 3 条）：`ω_pitch/roll ← ω_pitch/roll · (1 − λ)`。衰减不是可选项——即便锁转已经挡住求解器的角冲量，落地那一帧自带的角速度仍在，不清掉会与姿态写入互相打架；但它**只对 pitch / roll 是必需的**，地面上的原地自旋交给接触摩擦自然衰减。倾角小于阈值（原型取 0.5°）时清掉全部角速度，收敛结束，此后一直保持锁转。

`λ` 同时是「冲击吸收可见度」的旋钮：λ 越大立正越快、角速度丢得越干净；λ 越小，落地后「歪一下再站稳」的过程越看得见。

**②为什么必要——①并不保 yaw。** 「绕水平轴转」不改变**水平面内**那些矢量的方位角，但刚体朝向是局部 +Z 的**水平投影**方向，它一般不在水平面内，因此①会连带改变它：倾角斜置时每步约 `tilt · λ` 量级，整个收敛期累计可达数度——实测前倾 20° 再侧倾 20°（倾角 27.99°、λ=0.20）时不补正会漂 **3.53°**，补正后 **0.00000°**。②是绕竖直轴的旋转，按定义不改变倾角，因此倾角衰减律不受影响。纯俯仰与纯侧滚测不出这件事（那两个姿态下①恰好不改变 +Z 的水平投影），所以判据里必须有一个倾斜方向斜置的初态。

**①的旋转矢量不做「归一化」那一手。** 把 `(旋转矢量, 1)` 归一化成四元数，等价于把每步转角取成 `2·atan(‖r‖)` 而不是 `‖r‖`；`‖r‖ = 0.33` 时每步转角被放大到约 1.9 倍，倾角衰减明显快于 `(1−λ)`，把真实的时间尺度掩盖掉。正确形式是正则的轴角式——`sin(θ/2)` 作矢量部、`cos(θ/2)` 作标量部，其中 `θ = λ · tilt`。

**「上轴」与「朝向」是两个量。** `u` 只描述上轴歪向哪边、不含任何朝向信息：姿态竖直时 `u` 恒为 `(0,1,0)`，这个量在竖直处退化；纯俯仰 30° 时（`u = (0, 0.866, 0.5)`）它的水平投影只剩 `sin θ` 一项。由 `u` 反求一个「朝向」再据它拼目标姿态，目标本身就是错的——这是上面两条要避开的同一个混淆。

### 5.4 落地不需要平滑过渡

落地那一瞬间最容易出事的是姿态突变（穿地、弹跳）与比例增益产生的巨大角加速度。本方案里这两件事都没有来源：收敛窗口**没有任何力矩参与**，姿态每步只转 `λ · tilt` 那一小段；地面状态**没有比例增益**，角因子直接锁死，求解器的角冲量根本进不来。因此不需要引入「地面约束强度」之类的权重从 0 平滑升到 1，也不需要为它配落地前预判或缓和曲线——实测全程脚底最高 0.0000 m，从不弹起。

## 7. 接触摩擦的归属

### 7.1 三处摩擦项从力模型移出

引擎接管接触摩擦之后，下面三处不再由力模型承担，改由接触点上的法向力与引擎摩擦给出：

| 现有位置 | 现有内容 | 处置 |
| --- | --- | --- |
| `docs/角色控制器-行走物理设计.md` §3.8 第 ③ 步 | 侧向抓地：按 `μ·g·cosθ` 抹掉不沿输入方向的速度 | 移出。引擎的接触摩擦对切向相对速度施加约束，承担同一职责 |
| `docs/角色控制器-行走物理设计.md` §3.9 | 无输入摩擦刹车：同一个减速度 | 移出。地面的无输入制动同样由接触摩擦给出，该分支只保留「不施加控制力」 |
| `docs/角色控制器-行走物理设计.md` §3.5 | 控制力的抓地力钳制 `min(驱动力, μN)`；以及 KCC 的 `setMaxSlope` | 移出。抓地力由接触层的摩擦锥给出 |

`docs/角色控制器-行走物理设计.md` §4.6 的方向冲量抓地折减也随接触摩擦的接管而移出。

### 7.2 保留内阻与坡度项

`docs/角色控制器-行走物理设计.md` §3.6 的沿向内阻 `c₀·m·g` 与坡度项 `m·g·sinθ` **保留在力模型里**。内阻的语义是「蹬地推进的效率损失」，不是接触摩擦，因此不属于移出的范围。坡度项见 §7.4 的重复计算风险。

### 7.3 摩擦系数的新落点

`μ_naked` / `μ_foot` 这两个参数**不消失**，只是落点从力模型换成控制器刚体的 `setFriction`。取值按实测换算：要爬坡上限 45° 就取 2.0（× 地形 0.5 → 组合 1.0），要 35° 就取 1.4。标定表见 `docs/角色控制器-刚体原型与引擎约束.md` §5。

因此 `docs/角色控制器-行走物理设计.md` §8.1 的 `θ_max = atan(μ_effective)` 语义成立，只是 `μ_effective` 现在天然含入地形侧的材质差异。

### 7.4 摩擦模型本身仍需重新设计

本节只定「摩擦归谁」，没定「摩擦怎么算」。待议范围见 §12.4。

## 8. 力与力矩如何作用于胶囊体

本节只讲**已经拿到力以后怎么进物理**，不涉及力的来源（力的来源见 §9）。

### 8.1 施加方式：预计算合力与合力矩，一次性应用到胶囊

**不逐推进器、也不逐气动计算点施加。** 全部力先在胶囊的本体坐标系里汇总成一个合力 `F` 与一个合力矩 `τ`，然后每物理步只做两次调用：

| 通道 | 引擎入口 | 作用 |
| --- | --- | --- |
| 合力 | `PhysicsRigidBody#applyCentralForce` | 作用于质心，只改变线速度 |
| 合力矩 | `PhysicsRigidBody#applyTorque` | 只改变角速度，不改变线速度 |

`../Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsRigidBody.java#applyCentralForce`、`#applyTorque`。两者每步生效一次、随后被引擎清零。

**为什么不用 `applyForce(力, 作用点)`。** 引擎提供了一个便利入口：把力与作用点一起交给它，它内部自己算力臂力矩——

```cpp
void applyForce(const btVector3& force, const btVector3& rel_pos)
{
    applyCentralForce(force);
    applyTorque(rel_pos.cross(force * m_linearFactor));
}
```

坐标见 `../Libbulletjme/src/main/native/bullet3/BulletDynamics/Dynamics/btRigidBody.h#applyForce`。

那为什么不逐作动器调用它？三条理由，第一条是硬性的：

1. **纯力偶没有「作用点」。** 反扭矩（推进器喷流的反作用）与其它直接力矩项不是「力 × 力臂」的产物，写不成 `(力, 作用点)` 的形式——§8.2 说明它们必须显式建模。只要存在一项这样的力矩，`applyTorque` 就必须有；既然它已经在，把全部力矩都走它就不再多出一条通道。
2. **归约点必须唯一。** §9.1 约定**没有任何一个力源自己把力施加到刚体上**，全部力源只产出数据、由单一施加点汇总。逐作动器 `applyForce` 会让每个作动器自己成为施加者，这条约定就废了——而气动的数据来自 SubPart（§10.1），它必须与推进器走同一条路，否则同一份气动力会一次进 SubPart 自己的刚体、一次进胶囊（§12.7）。
3. **一次调用胜 N 次。** 两条路在数学上**等价**——引擎的实现就是上面那段代码，且内部同样走 `applyTorque`，所以角因子的门控行为一致。区别只在每步调用 N 次还是 2 次。

**力矩仍由真实几何导出。** 每个作动器的力矩写在它的雅可比列里，就是 `(p − c) × F`（§9.7.2），`p` 是该作动器的真实作用点。手工归约不等于丢掉几何，只是把这一次乘法的位置从引擎挪到分配器，好让它与力一起参与分配。

**力矩的参考点只有一个：胶囊质心。** 全部力源（推进器、接触型、气动）的力矩都在这一个点上算，写成 `τ = Σ (p_i − c) × F_i`，`c` 就是胶囊质心。`p_i` 各自不同（推进器是安装点，气动是流体动力计算点），但 `c` 必须统一——否则各通道的力矩不可相加。

### 8.2 反作用与对称性

两个必须显式建模的量：

- **反扭矩**：推进器喷射本身产生绕喷射轴的力矩（喷流的反作用），与推力方向无关，不能由力臂导出。它是**直接力矩项**，与 `Σ(r × F)` 并列相加。舵面偏转的**铰链反作用力矩**属于同一类，但本方案不建模——理由见 §9.6 的简化 2。
- **力矩相消**：多个推进器同时出力时，各自的力臂力矩可能互相抵消（对称布置的推进器只出力不出力矩），也可能叠加（单侧布置的推进器出力必然带力矩）。因为力矩由我们自己归约而不是由引擎从作用点导出，**这个相消关系必须在雅可比列里显式保留**（§9.7.2 的 `(p − c) × d`）——引擎不会替我们做。

### 8.3 分轴锁转下各轴力矩的可用性

角因子置 0 的轴上，力矩**施加不上去**（§2.2 选择 2 的机制）。这不是副作用而是设计的一部分：

- 地面状态 `(0, 1, 0)` 下，pitch / roll 力矩一律无效，只有 yaw 力矩生效——而这恰好是地面状态需要的全部（转身）；
- 因此地面状态下**不需要**为 pitch / roll 做任何力矩分配，也不会因为推进器带出的 pitch / roll 力矩而失衡。失衡表现留给飞行状态。
- 这条事实在分配层表现为**行表**：pitch / roll 两行直接不进分配问题（§9.8）。留着一个引擎会丢掉的维度，只会让分配器把权限花在无效方向上、并报出不存在的饱和缺口。

## 9. 力的来源：从 SubPart 到作动器

本节只讲**力怎么算出来**，不涉及如何施加（见 §8）。

### 9.1 力源是数据，不是对刚体的施加

本节先立一条贯穿全部力源的约定。

**没有任何一个力源自己把力施加到刚体上。** 每个力源每物理步只产出一个数据结构，统一为：

```
力源 = ( 世界作用点 p, 世界力矢量 F )
```

归约只有一件事：

```
F_total += F
τ_total += ( p − c ) × F        c 是胶囊质心，全场唯一（§8.1）
```

这条约定有两个直接后果：

- **气动与推进器走完全相同的归约路径。** 气动力不再由每个 SubPart 施加到自己身上，而是作为数据交给同一个汇总点。
- **逐点施加的入口被废掉。** `PhysicsRigidBody#applyForce(力, 作用点)` 与这条约定不兼容，理由已在 §8.1 给出（纯力偶没有作用点可给、归约点必须唯一、一次调用胜 N 次）。

因此本方案里凡是「算力」的地方，终点都是这个数据结构，而不是一次引擎调用。

### 9.2 四类驱动，两个去向

分类判据是**控制器能不能命令它**——也就是这个力源有没有一个**可命令的致动器状态**：

| 类型 | 可命令量 | 力由什么决定 | 典型例子 |
| --- | --- | --- | --- |
| **推进器** | 出力（油门） | 指令，与速度、姿态**无关** | 喷射推进、悬浮 |
| **接触型** | 落脚点选择 | 指令 + 接触状态（受摩擦锥限制） | 双足、轮足、履带 |
| **固定零件气动** | **无** | 完全由当前运动与姿态决定 | 机翼、机身、尾翼 |
| **舵面气动** | 偏转角 | 指令 + 动压 `q = ½ρv²` | 副翼、升降舵、方向舵 |

**有可命令量的一类进分配器，而且是同一个分配器。** 推进器、舵面、以及被当作减速板用的气动面**全部是同一件事**：各有一个可命令量 `u`，各对胶囊贡献一份力与一份力矩。它们之间的差别只落在两份数据上——每个作动器的**界**（§9.4）与它的**雅可比列**（§9.7.2）——而不是落在几条不同的处理路径里。分配问题不区分器件的「类型」，只读这两份数据。

减速板因此不是第五类，而是舵面的一个特例：可命令量同样是偏角，只是外形让它的雅可比列偏向沿来流方向的力而不是力矩。这件事由列自动表达，不需要类型标记。

接触型也产出一份力，但它的方向不是安装出来的（§9.5），因此留在分配器之外。

**没有可命令量的一类去目标上的矢量减法。** 固定零件气动的力完全由当前运动与姿态决定，控制器无法支配它；环境已经把它给了胶囊，于是控制器的任务是**减掉它**：期望净 wrench 减去这一份，剩下的才是作动器要凑的量（§10.4）。这个去向不是「另加一股力」，而是**同一个目标上的减法**。

**「固定零件」与「舵面」按可命令量划分，不按外形或安装位置划分。** 同一片翼面，作为固定零件时装它就完全不参与控制、只被减掉；装上作动器后它就成为舵面。判据是那台作动器，不是那片翼面。

### 9.3 从 SubPart 到作动器数据

一个**作动器**是「有一个可命令量、并对胶囊贡献一份力与一份力矩」的对象。它对分配器只需要交出四样东西：

| 项 | 内容 | 从哪来 |
| --- | --- | --- |
| **可命令量 `u` 的界** | `[u_min, u_max]`。归一化后大多是 `[0, 1]`（油门）或 `[−1, +1]`（偏角 / `δ_max`） | 零件属性与当前状态，见 §9.4 |
| **雅可比列 `J_k`** | 该作动器的 `u` 变化一单位对合力与合力矩的贡献 | §9.7.2 |
| **作用点 `p`** | 世界作用点，用于算力臂 | 定位点的世界位姿 |
| **力函数** | `u → (p, F)`，代回复核要用（§9.9） | 该器件自己的模型 |

映射分三层，每层对应作动器的一类信息：

| 层 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| **位置 → 力臂** | 定位点的世界位姿 | 该点相对胶囊质心的位移 `r = p − c` | 决定这份力**能产生多大力矩** |
| **姿态 → 方向** | 定位点的世界旋转 | 力在本体坐标系下的方向 | 决定这份力**落在哪一轴**，也决定雅可比列的方向 |
| **属性 + 状态 → 大小** | 零件属性（最大出力、响应时间、能耗）与状态（接触 / 动压） | 该作动器当前能出多大 | 决定 `u` 的界，也决定雅可比列的模长 |

**力臂 `r` 必须每物理步按实际位姿重算**，不能在配装期缓存。部件之间存在约束余量、损伤与相对运动，这与「姿态朝向只在配装期算一次」不是一回事。

**界的来源分两种：配装期定死形状，运行期缩放。** 推进器的**方向**是配装期常数，**大小**不必是——推力包络随高度与空气密度、损伤、燃料变化。分配器只需要当前值，所以这一点不构成负担。舵面的界由**最大偏角** `δ_max` 在配装期定死形状，运行期**随动压 `q` 缩放**：

```
该作动器在某方向能出的力 = q 决定的比例因子 × ( 最大偏角下的力在该方向上的分量 )
```

**力矩的可达范围不能从力的范围导出。** 每个作动器的力矩是它的力与力臂的叉积 `(p − c) × F`，这套关系写在雅可比列里（§9.7.2），不是另一组独立的界。参考点全场唯一为胶囊质心，理由见 §8.1。

### 9.4 分配目标与各作动器的界

#### 目标的语义

```
w_des    = 胶囊的期望净 wrench（控制层的意图）
w_known  = 一切不由本控制器作动器提供、但已知的 wrench
           （固定零件气动、舵面 δ=0 基准项、重力、其它可测的已知扰动）
分配目标 w_alloc = w_des − w_known          ← 矢量减法
```

**`w_des` 的语义必须钉死为「胶囊的期望净 wrench」**，否则这条减法无从写起：环境已经给了胶囊的那一份必须先从目标里减掉，剩下的才是作动器要凑的量。完整约定与算式见 §10.4。

**为什么是减法而不是「在输出上再加一股抵消力」**：见 §10.6 的三路对比。一句话版本——§8.1 决定了我们手工算合力再 `applyCentralForce`，**引擎不会替我们检查这个力作动器出不出得来**，因此加在输出上会凭空造力；而减去之后，这份需求会进入分配器的饱和判断，缺口与 windup 回退全都自洽。

#### 各作动器的界

| 来源 | 界的形状 | 什么时候变 |
| --- | --- | --- |
| **推进器** | `u ∈ [0, 1]`（归一化油门，单侧） | 方向是配装期常数；大小随推力包络、损伤、燃料变 |
| **舵面 / 减速板** | `u ∈ [−1, +1]`（偏角 / `δ_max`，双侧） | 形状配装期定死，模长随动压 `q` 缩放（§9.3） |
| **接触型** | 不进分配器 | 见 §9.5 |

**两个端点都要给，而且不必对称。** `[0, 1]` 说的是「这台推进器只能推不能拉」，不是「油门关不小」；`u = 0` 永远在界内，因此**零出力永远可达**。这条在分配层表现为一个不变量：`w_alloc = 0 ⟹ u = 0`（§9.9）。

**界与雅可比列合起来才是能力。** 界说明「能推多远」，列说明「推一单位得到什么」。两者都按当前状态取，所以「舵面的能力随速度变」不需要任何特判——低速时它的列模长趋零，分配器自然不会用它（§9.7.2）。

#### 行表

分配问题不是恒定 6 维：**引擎不接受的 wrench 分量不该进目标**。地面 `(0, 1, 0)` 下 pitch / roll 力矩会被 `applyTorque` 门控丢掉（§8.3），把它们留在问题里会让分配器把权限花在无效方向上、并让残差报出一个不存在的缺口。活行由当前 `angularFactor` 导出，见 §9.8。

### 9.5 接触型驱动

接触型与其余三类在映射上的根本差别：**它的力不是安装出来的，而是地面给的**。

| 环节 | 内容 |
| --- | --- |
| 可用性 | 需要至少一个支撑相。无接触时该类型出力为零 |
| 方向 | 由落脚点与地面法向决定：法向分量只能推（不能拉），切向分量受摩擦锥 `\|F_t\| ≤ μN` 限制 |
| 大小 | 上限是摩擦锥，而不是某个零件属性 |
| 落脚点 | 决定力臂，因而决定这一步能产生多大偏航力矩——双足的转向能力来自落脚点的选择，不是来自某个"转向执行器" |

因此接触型的三样东西让它**留在分配器之外**：

1. **方向不在本体坐标系里**。推进器与舵面的力方向由安装姿态给出，因此能写成一个固定的列；接触型的方向由「这一步脚踩在哪」决定，**本体坐标系里没有「落脚点」这个量**，写不出列。
2. **单侧约束、而且约束来自摩擦锥**。推进器的单侧界是 `[0, 1]`，与状态无关（§9.4）；接触型的界是 `|F_t| ≤ μN`，其中 `N` 与 `μ` 都由接触求解器给出，是瞬时状态。
3. **力的产生者与支配者是分开的**。地面反力本身由接触求解器给出，我们不手工预生成（§9.6 简化 1）；控制器能支配的只是**落脚点的选择**。

**接触型控制力保留。** 地面行走、轮式 / 履带驱动一律走接触层，由角色控制器给出平面控制力、受摩擦锥钳制。它的落脚点同时也是地面偏航力矩的来源——因此**地面上的 yaw 分配只覆盖作动器能提供的那部分，不含落脚点带来的那一份**（§9.8）。

### 9.6 已知简化

只列**本方案实际承担**的简化。

| # | 简化 | 后果 | 性质 |
| --- | --- | --- | --- |
| 1 | **地面反力不手工预生成** | 无 | 不算简化而是纪律：地面反力由接触层自己的求解器给出。角色控制器预先算一份"腿力"再让求解器重解一遍，就是同一次接触被算两次 |
| 2 | **舵面的铰链反作用力矩不建模** | 少一项直接力矩。它相对舵面自身控制力矩约小一个量级 | 可忽略，理由是**结构性**的：舵面若无刚体则不存在铰链；若是有刚体的 SubPart，铰链力矩由铰链上的作动器反力矩承担（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java` 在 6DOF 的旋转自由度上开伺服）。两种情况都不需要我们在 `τ` 里补一项 |
| 3 | **雅可比在当前工作点线性化** | 气动力对偏角并不线性：`cl` 在失速处被硬性裁剪，诱导阻力对偏角是二次项（§10.1）。列只在工作点附近有效 | 用**界上的割线**把它压到最小：模型在 `u = 0` 与 `u = u_max` 两端严格精确，残差只剩区间内的曲率。见 §9.7.2 与 §12.9 |

**简化 2 的定量依据**：铰链力臂是铰链到压心的距离，对后缘襟翼约弦长的 0.25、对全动翼面约弦长的 0.35；而同一份力对胶囊的力臂通常是米级。两者之比约为 `0.08 / 1.0 ≈ 8%`，且 `q` 与面积在两边同时出现、约掉了，**这个比例不随速度变化**。唯一可能推翻它的情形是「全动翼面 + 需要模拟失速手感」——失速时压心突然后移会让这一项出现非线性跳变。

**简化 3 的边界在哪**：割线在区间的两个端点严格精确，误差只来自区间内的曲率。按 §10.1 的气动形式，偏角是通过**定位点自身坐标系的旋转**进入的（`DynamicUtil.java#advancedAeroForce` 的入参里没有偏角，只有该坐标系下的局部速度）：铰链轴沿机体纵轴时，该旋转把局部来流角精确平移 `α₀ ± δ`，且动压 `q = ½ρ(v_y² + v_z²)` 在同一个旋转下不变，于是**转回本体坐标系之后力的方向与 δ 无关，只有两个标量大小随 δ 变**——升力那一支对 δ 是仿射的，割线因此精确；唯一的曲率在诱导阻力增量 `kInduced · cl²` 上，而那一项是总阻力的千分之一量级。**这条简化剩下的是一个可以忽略的尾巴，而不是一个需要设阈值去防的风险。**

**饱和与 windup 的边界**：作动器撞界时实际出力被截住，而环路上若存在积分项，控制器内部会继续累积。本方案不另设饱和判据——**分配器的残差就是饱和缺口**（§9.7.4），按 `实际出力 / 期望出力` 回退积分即可。

**力矩相消必须显式保留**：因为力矩由我们自己算（§8.1）而不是由引擎从作用点导出，`Σ(r × F)` 的相消关系不会自动成立。若不显式保留，会出现「要到一份净力，却连带得到一份并不存在的净力矩」。

### 9.7 控制分配

把「要一份 wrench」翻译成「每个作动器出多少」，在一个线性问题里解。

#### 9.7.1 问题的形状

每个作动器**只有一个可命令量** `u_k`（推进器的油门、舵面的偏角），而它一次同时决定一份力与一份力矩。所以真实可达集不是「一个 3 维力盒加一个 3 维力矩盒」，而是 6 维 wrench 空间里由 `N` 条一维曲线张成的集合。

把每条曲线在当前工作点线性化，就得到一张矩阵：

```
列 k = 该作动器的 u_k 变化一单位，给胶囊带来多少力与多少力矩
```

分配问题于是写成

```
J u ≈ w_alloc      J: 6×N（按 §9.8 可降维）    u: N 个可命令量
u_min ≤ u ≤ u_max  逐作动器的界（§9.4）
```

**这样写的直接好处**：`J` 的列空间就是可达的 wrench 集合，解出的 `u` 对应的 wrench 必然落在里面——「命令的力出不来、命令的力矩出不来」不会成为需要事后发现的缺口，它就是问题的定义本身。力与力矩也不可能被独立钳制，因为它们由同一个 `u` 一起产出。

**这里没有「器件类型」这个概念。** 推进器、副翼、升降舵、减速板**都是列**。减速板不过是「力矩行小而力行大」的列，副翼是反过来的列。§9.7.6 说明为什么不需要给它们分类。

**推进器并入同一个解，换来一条跨速度包线。** 低速与悬停时气动列的模长趋零，只剩推进器列可解；高速时反过来。**同一个解在低速是推力混合器、在高速是气动控制器，中间连续过渡**——没有模式机、没有配平表、也没有「速度不够舵效失效」的特判。代价只是把推进器也写成列（§9.7.2）。

**附带收益（一）：气动面的力变成已知量。** `u` 是分配的输出，因此该偏角下的气动力**是算出来的，不是预测的**（§10.3 的仿射模型）——前馈一侧只需要承担 `u = 0` 的截距。

**附带收益（二）：控制量本身就是程序性动画要的那个量。** `u` 恰好是显示层的原始输入——推进器的 `u` 就是油门（尾焰大小、音效强度、粒子发射率），舵面的 `u` 乘以 `δ_max` 就是偏角（模型姿态）。三点具体好处：

| 好处 | 为什么 |
| --- | --- |
| **物理与动画同源** | 动画用的是分配器算出的那一个偏角，不是另按输入猜一个，因此不存在「模型显示 30°、物理用的是 18°」这种漂移 |
| **饱和看得见** | `u` 已经过级联钳制，撞界时尾焰会**真的到顶**、舵面会**真的停在 `δ_max`**——玩家直接看得出这台机器没权限了，不需要另做一套提示 |
| **诊断可可视化** | §9.7.4 的残差（饱和缺口）与 `u` 一起画出来，就能把「哪些方向没满足、差多少」直接摆在调试界面上 |

按 §9.7.6 的做法就没有这一份：那里分配出来的是**逐轴力**，偏角得从力反解，而且同轴多面之间存在剩余自由度、要另定一条分担规则。**分配器把「反解偏角」这一步整个省掉了——`u` 就是答案，不是中间量。** 这份输出怎么送到渲染侧，见 §9.9。

#### 9.7.2 雅可比 `J`：割线列

**推进器的列是配装期常数。** 力沿安装方向、大小与 `u` 成正比：

```
J_k = [ d ; (p − c) × d ] · F_max        d = 安装方向（本体坐标系），F_max = 当前满油门推力
```

`r = p − c` 每物理步按实际位姿重算（§9.3），代价是一次叉乘。`F_max` 取当前值，因此推力包络、损伤、燃料都能体现。

**气动面的列只能数值求导，而它几乎免费。** §10.1 的力函数入参里**没有偏角**——偏角是通过定位点自身坐标系的旋转、改变局部来流角进入的（`DynamicUtil.java#advancedAeroForce`）。因此列这样取：

```
J_k = ( w(u_k = u_max) − w(u_k = 0) ) / u_max
```

**用界上的割线，不用切向导数。** 割线在 `u = 0` 与 `u = u_max` 两端**严格精确**，误差只剩区间内的曲率；而按 §9.6 简化 3 的分析，这个模型里唯一有曲率的是诱导阻力增量项，量级在总阻力的千分之一。切向导数要在工作点两侧对称差分，既多一次求值、又丢掉端点精确性。

**成本可以忽略，因为贵的那一步与偏角无关：**

| 步骤 | 成本 |
| --- | --- |
| 遮挡 `rayTest`（JNI 往返） | 每 tick 每个气动点**一次**，与偏角无关，求导时复用 |
| 力函数本体（`atan2` + 约 40 次浮点） | 每列多一次 |
| 射线方向随偏角转动的误差 | `effectiveRange` 默认 1.0 m，`δ_max = 25°` 时射线端点横移约 0.42 m；只在有零件落在这段距离内时才有影响，且误差是**乘性因子** |

按 8 片舵面 × 2 个定位点估，每 tick 多的开销在微秒量级，100 Hz 下是噪声。

#### 9.7.3 求解：阻尼伪逆

带界的加权最小二乘没有闭式解，因此分两步：先解无界的加权伪逆，再处理越界（§9.7.4）。无界解取**阻尼最小二乘**（Tikhonov 正则）：

```
min ‖J u − w_alloc‖² + λ² · uᵀ W u
```

用 push-through 恒等式把解换到行数那一侧：

```
u = ( JᵀJ + λ²W )⁻¹ Jᵀ w_alloc
  = W⁻¹Jᵀ ( J W⁻¹ Jᵀ + λ²I )⁻¹ w_alloc
              └── 只有 6×6 或更小（§9.8） ──┘
```

`N`（作动器个数）通常大于 6，所以取右边那条：**要分解的永远是 6×6 或更小**。

**`λ > 0` 让这个矩阵恒为正定**，于是：

- 分解永远成功，不需要选主元、不需要判秩；
- 级联去掉若干列之后约化系统**照样可解**——这是 §9.7.4 那条「约化后可能减秩」的根治办法，不是补丁；
- 同构列（几片几何对称的舵面，`J` 的列几乎相同）那份量级可达 `10⁵` 的相互抵消解被 `λ` 直接压住。

**`λ` 怎么取。** 先把行按 §9.7.5 的第一职责归一化，使 `J W⁻¹ Jᵀ` 的对角元落在 1 量级，然后取

```
λ² = ρ · mean(diag(J W⁻¹ Jᵀ))        ρ 从 1e-4 起调，量级范围 1e-6 ~ 1e-2
```

物理含义是「**多小的奇异方向允许被激发**」，并且它给出命令放大的硬上界：`‖u‖ ≲ ‖w_alloc‖ / λ`。`ρ` 是纯数字、与配装无关，可以直接做成配置项。全程用 `double` 而非 `float`——正规化把条件数平方了，`double` 下 `κ(J)` 到 `1e6` 仍够用。

**计算量**（`N ≈ 10`、6 行）：组装 `J W⁻¹ Jᵀ` 约 420 次乘加、6×6 Cholesky 约 56 次乘加加 6 次开方、前代回代约 72 次、`u = W⁻¹Jᵀ y` 约 60 次——**合计不到 1000 次浮点运算**，每物理步一次。

**不需要线性代数库。** 需要的是 6×6（或 4×4、3×3）对称正定的 Cholesky 分解，约 40 行。可用的库都存在，但都不划算：

| 方案 | 情况 | 判断 |
| --- | --- | --- |
| Apache Commons Math 3.6.1 | `SingularValueDecomposition#getSolver()` 返回的 `DecompositionSolver#getInverse()` 就是 Moore–Penrose 伪逆，能完成任务 | 2 MB 量级的依赖；`RealMatrix` 面向对象，每次调用都分配对象，在 100 Hz 循环里是纯 GC 噪声。而且本问题**不需要 SVD**：`λ > 0` 已经保证可解，截断奇异值只是 `λ` 的一个替代品 |
| EJML | 有 `SolvePseudoInverseSvd_FDRM` 一类现成实现 | 同为外置依赖；为 6×6 拉一个 1–3 MB 的 jar 不划算 |
| JOML | Minecraft 1.19.3+ 已在类路径上，不需要额外依赖 | **没有 Cholesky、也没有 SVD**，只有 2/3/4 维矩阵，解决不了本问题 |
| **手写 Cholesky** | 约 40 行 | 推荐 |

**可测性是这个选择的另一半理由。** 整个分配器是一个纯函数 `(J, 界, W, λ, w_alloc) → u`，不碰 `PhysicsSpace`，因此下面这些都能在 JUnit 里逐条验证，不需要活着的世界：

| 断言 | 内容 |
| --- | --- |
| 可达即达成 | `w_alloc` 落在可达集内时 `Ju ≈ w_alloc`，残差远小于 `‖w_alloc‖` |
| 不可达时残差即缺口 | `u` 逐项不出界，且 `‖w_alloc − Ju‖` 等于饱和缺口 |
| 对称冗余等分 | 两列完全相同时两者的 `u` 相等 |
| 零指令不点火 | `w_alloc = 0 ⟹ u = 0`（§9.9） |
| 简并被压住 | 近简并配装下 `‖u‖` 被 `λ` 限制在 `‖w_alloc‖ / λ` 量级内 |
| 门控行不产生虚假缺口 | 活行之外置零之后，残差不受影响（§9.8） |

#### 9.7.4 饱和处理：级联，不追最优

伪逆解出 `u` 之后撞界怎么办。**不做二次规划、不做活跃集迭代，只用级联**：

```
① 解 u = W⁻¹Jᵀ(JW⁻¹Jᵀ + λ²I)⁻¹ w_alloc
② 取出所有越界的作动器，各自钉在它撞到的那个界上   ← 一次全取，不必逐个
③ w' = w_alloc − J_固定 · u_固定                 ← 目标减去它们已经提供的量
④ 用剩下的自由列重解 → 回到 ②，直到没有越界为止
⑤ 收尾：核一遍已钉列的乘子符号（可选，见下）
```

**终止性不成问题。** 每轮至少钉住一列、而且**永不释放**，所以最多 `N` 轮。单侧界（推进器那类 `[0, 1]`）也一样：钉在 0 上就是「这台不点火」，把它移出自由集是一次合法的集合缩减，残差照实报出来。

**为什么一次全取是安全的。** 带界约束最小二乘的 KKT 条件就是「活跃集内取边界值 + 其余解无约束最小二乘」。把同时越界的作动器一起钉死、一起移出自由集，正是活跃集法处理「一次迭代中多个约束同时活跃」的标准做法。而且**去掉饱和列之后可行集变大，残差 `‖Ju − w_alloc‖²` 单调不升**。

同构列（例如左右副翼几何对称到极致）的情形下更干脆：`J` 里两列完全相同时，伪逆给两者的分配**必然相等**，它们本来就一起饱和、一起被钉。逐个丢反而要走一圈无用的路。近简并时同时丢弃还有额外好处——它**一次消掉那条病态方向**（§9.7.3 里那份 `10⁵` 量级的抵消解），逐个丢则要把这份大数在自由集里过一手。

**不追最优的代价，明确记账。** 级联是贪心的（钉上就不再回头），因此不保证得到 KKT 点。一个两作动器、两维 wrench 的反例：某组 `J` 与 `w_alloc` 下贪心给出残差 `1`，而精确 KKT 解是 `0.91`——**差约 8%**，原因是正确的活跃集需要**释放**已钉的作动器、改钉另一个。

**接受这个差距，理由是它会被回路吃掉**：

- 偏差表现为**当拍未达成的 wrench**，下一拍反馈继续纠；
- 它**无偏**——不会系统性偏向某个轴，因此不积分、不漂移。偏差随残差一起被报出来，而残差正是 windup 保护的输入；
- 反过来，精确解要引入释放逻辑、循环保护与终止判据。**多一套会出 bug 的机制，换一个玩家感知不到的改善，是负收益。**

**第 ⑤ 步的收尾检查是可选的，而且零迭代增量。** 残差 `r = J_自由 u − w_alloc` 在解最小二乘时**本来就是副产品**，因此乘子

```
λ = J_固定ᵀ r           λ_k 符号与 u_k 所钉的界不符 ⟹ 该列被错误地钉住
```

只需一次 `N×6` 的矩阵向量积（`N ≈ 10` 时是 60 次乘加），比一次 `6×6` 分解便宜得多。它**不释放、不重解**，只把结论记进下面的缺口输出。

**残差本身就是「饱和缺口」，是本方案的有用输出。** `‖w_alloc − Ju‖` 与它的方向直接给出「哪些方向没能满足、差多少」，正好喂给 §9.6 的 windup 保护那一条（按 `实际出力 / 期望出力` 回退积分），不需要另设一套饱和判据。

**缺口是相对于 `w_alloc` 算的，不是相对于 `w_des`。** 这一点自动把**配平需求**排除在缺口之外：悬停顶重力、巡航顶阻力都是 `w_alloc` 之内的正常需求，不是饱和。`/arms` 的 dump 要能区分这两者。

**一处必须留意的求解失败**：去掉若干列之后，**约化后的系统可能减秩**（尤其近简并列被丢之后）。这跟「丢几个」无关，但它是级联法真正会崩的地方——解出垃圾而**没有地方会报错**。对策与 §9.7.3 里的 `λ` 同源：对约化系统同样加 `λ²I`，可解性由构造保证。

#### 9.7.5 权重矩阵 `W` 的两层职责

`W` 出现在 `u = W⁻¹Jᵀ(JW⁻¹Jᵀ + λ²I)⁻¹w_alloc` 里，是 controller effort 二次型的**代价**矩阵。它的两个职责要分开设，别用一个数同时干两件事。

**第一职责（必须）：把力与力矩拉到可比尺度。**

`J` 的前三行是力（N），后三行是力矩（N·m），两者数值尺度差着质量与惯量的量级。不归一化的话，伪逆会隐式地把「1 N 的力误差」与「1 N·m 的力矩误差」当成同等重要——而按本方案的几何，胶囊绕 Y 轴转动惯量约 4.4 kg·m²，**几十 N·m 就能把姿态甩飞**，两者根本不等价。

**第二职责（按表现定）：决定冗余时谁多干一点。**

`W_i` 越大表示该机构越「贵」，分到的量越少。所以「让大机构多出力」要给它们**小**权重。但要说清它能做到什么、做不到什么：

- 它分配的是**「在多个机构都能干这件事时，谁来干」**；
- 它**不能**决定谁先饱和——饱和由 `J` 与 `u_max` 决定，而 `u_max` 大的机构（大推进器、主翼面）本来就**最后**才饱和。

因此「让大机构优先饱和」这个目标本身要重新表述。而且在冗余设计上，**让大机构先满等于放弃了冗余**——小型配平面存在的意义就是在大机构用满之后接手余量。真按这个方向调，等于花一套复杂分配器做出一个简单分配器的效果。

**但它在游戏里可以是优点**，所以这条按表现需求定，不按控制理论定：

| 取向 | 表现 |
| --- | --- |
| 大机构优先用满 | 主翼面 / 大喷口先吃满，玩家看得见「它在使劲」；动作可预测、好调试、好做动画 |
| 小机构优先用满 | 大机构留余量给突风、损伤与瞬态修正；动作更细腻但不直观 |

这是**手感旋钮**，不是精度旋钮。

**但这条旋钮有一条物理上正确的取值。** 作动器的代价并不对称：推进器烧燃料、发热、有寿命；气动面不烧任何东西。把这件事编码进 `W` 就得到「推进器贵、气动面便宜」，而它一次性换来一条**跨速度包线**：

| 工况 | 结果 |
| --- | --- |
| 悬停 / 低速 / 地面 | 气动列的模长本来就趋零，只有推进器可解——**纯推力混合器**。这不是规则，是列的性质 |
| 高速 | 气动面优先干活，推进器留余量给突风、损伤与瞬态修正 |
| 中间 | 两者按列范数连续过渡，没有模式机、没有配平表 |

这一条把第二职责从「纯手感」提升为「有物理依据」，但**取向仍按表现定**：想让玩家看见大喷口在使劲，就把推进器调便宜。

**第一职责的系数是硬要求，而且尚未实测。** 胶囊绕 Y 轴的转动惯量按当前几何约 4.4 kg·m²，因此 yaw 力矩换算成角加速度时量级较大——几十 N·m 就够用，给大了会转过头；而 3 个力行是 N、几百量级。两者不归一化，伪逆会隐式地把「1 N 的力误差」与「1 N·m 的力矩误差」当成同等重要。具体系数要在真实配装下量一次。

#### 9.7.6 被取代的做法：按轴独立钳制

一种不引入任何线性代数的做法是：把每个力源的方向投影到体轴上逐轴求和，得到「各轴可用的力区间」，再把力的包络当成一个 3 维盒、力矩的包络当成另一个 3 维盒，各自独立钳制。写下来是因为它的三处代价**恰好就是本方案要消除的东西**，而且它们生效时都不报错。

**逐轴求和的形式**（本体坐标系）：

```
上限_i = Σ_力源 max(0, 方向_i) × 该力源可用出力
下限_i = Σ_力源 min(0, 方向_i) × 该力源可用出力
```

这两个量是**带符号的力**，不是出力的幅度；`方向_i` 是该力源推力方向在体轴 `i` 上的分量，取正取负由安装朝向决定。公式里只有 `max` 与 `min`，没有取绝对值、也没有下限截断，因此 `上限_i ≥ 0`、`下限_i ≤ 0` 由构造保证：

| 该轴上装了什么 | 方向分量符号 | 可用区间 | 说明 |
| --- | --- | --- | --- |
| 正反向各一组 | 两种符号都有 | `[−a, +b]`，`a, b > 0` | 双向下限非零，**这是唯一有意的非零下限情形** |
| 只有正向 | 全为正 | `[0, +b]` | 下限为零 |
| 只有反向 | 全为负 | `[−a, 0]` | 上限为零 |
| 没装 | 无项 | `[0, 0]` | 上限下限同时为零 |

**下限为零的含义是「该轴没有反向驱动能力」，不是「出力关不掉」。** 区间以零为一个端点，恰好说明零出力永远可达（不点火）；推力不可反向的推进器**不会**表现为非零下限，它只往一侧贡献，另一侧的界就是 0。这条语义在分配器里以「`u = 0` 永远在界内、且 `w_alloc = 0 ⟹ u = 0`」的形式保留（§9.4、§9.9）。

**三处代价：**

| # | 代价 | 为什么 |
| --- | --- | --- |
| 1 | **力的方向自由** | 按轴分解之后，单个机构的实际力矢量允许与安装方向或可达曲线不同。舵面比推进器严重——它的可达集是一维曲线，连盒的角点都不可达。模型因此「比真实机构更能干」 |
| 2 | **形状近似** | 逐轴求和与真实可达集的形状无关。**斜装是触发点**：一台方向为 `(0.3, 0, 0.95)` 的推进器会把上下界同时抬高一截，而它的真实贡献只是一条一维线段；逐轴求和把它铺成了二维或三维区域。最坏情况的系统性高估是体对角上的 `√3 ≈ 1.73`。纯正交安装（`±X` / `±Y` / `±Z` 各就各位）时两条代价都不产生误差 |
| 3 | **力与力矩的耦合不建模** | 同一次分配同时决定 `ΣF` 与 `Σ(r×F)`，两者可能冲突，而独立钳制会悄悄牺牲其中一方，**没有任何地方报告这个冲突**。若力矩由引擎从作用点导出，`Σ(r×F)` 的相消关系会自动成立；本方案手工算力矩（§8.1），所以相消必须显式保留 |

**为什么最终不采用它**：这三处代价都不是数值误差，而是**模型与真实能力不一致**，并且都在静默生效——高估只表现为收敛比模型预测的慢，冲突只表现为某个轴悄悄不到位。修掉它们必须在 wrench 空间里描述可达集，那正是 §9.7.1 的那张 `J`。而「各作动器的方向、满出力、最大偏角、力函数」这些数据在两种做法里都要准备，**引入分配器只多一个 6×6 求解器，却省掉整套逐轴盒的合成、合并与钳制规则**。此外它还省掉一步：这条路分配出来的是**逐轴力**，每个作动器的偏角要从力反解，而且同轴多面之间有剩余自由度、得再定一条分担规则；分配器直接输出 `u`（§9.7.1 附带收益二）。

**相关的一条做法：按主/副输出给气动面分类。** 给每个气动面标一个类型，让它的「副输出」（控制面的阻力增量、减速板的力臂力矩）换一条通道走前馈，主输出进控制力。它在动力学上不重不漏（`F` 与 `τ` 出自同一个 `δ`，分开送进两条通道后相加仍等于真实值），代价是**配装期负担 + 配错即静默失效**：把控制面配成减速板，它的力矩会被前馈预先抵消掉，副翼推不动飞机，而且不报错。分配器里没有「主输出/副输出」这个概念——一片舵面的力与力矩由同一个 `u` 一起产出，不存在「哪一半算控制力」，因此那个配置字段与配套的配装期校验都不需要。

### 9.8 分配问题的维度

**分配问题的行 = 引擎实际接受的 wrench 分量。** 引擎不接受的分量不该进目标：地面 `(0, 1, 0)` 下 pitch / roll 力矩被 `applyTorque` 的角因子门控丢掉（§8.3），把它们留在问题里会让分配器把作动器权限花在无效方向上，而且残差会报出一个**并不存在的饱和缺口**——残差是 windup 保护的输入（§9.7.4），这个谎会被用上。

行表直接从 `angularFactor` 导出，不另设门控矩阵：

```
活行 = { 力 x, 力 y, 力 z } ∪ { 力矩 i | angularFactor_i ≠ 0 }
```

| 状态 | `angularFactor` | 行数 | 构成 |
| --- | --- | --- | --- |
| 飞行 / 悬浮 | `(1, 1, 1)` | **6** | 3 力 + 3 力矩 |
| 地面站立 / 行走 | `(0, 1, 0)` | **4** | 3 力 + yaw 力矩 |
| 落地收敛窗口 | `(0, 0, 0)` | **3** | 只有力 |
| 布娃娃 | `(1, 1, 1)` | 不分配 | §4.1：姿态权威为「无」 |

**降维与「乘一个 0 掩码」逐位等价。** 零行在 `JᵀJ`、`Jᵀw_alloc` 里贡献恒为零；在 `J W⁻¹ Jᵀ + λ²I` 里它只留下一个 `λ²` 对角元，而对应右端项为 0，于是那一行的解分量 `y_i = 0`；再经 `u = W⁻¹Jᵀy` 乘回时又遇到零列。所以两者给出**相同的 `u`、相同的越界列、相同的残差**。既然如此就取更省的那个：直接砍掉行，Cholesky 从 6×6 降到 4×4 或 3×3，而且**不存在「行表与角因子走样」这种失效**。

**降维不是「忽略」那两个力矩，而是「不再试图满足」它们。** 被释放的作动器权限自动转到还活着的行上：一台装在质心上方的推进器在地面只贡献力行，不再被分一份去顶根本不生效的 pitch 力矩。这不需要任何额外规则。

**地面 yaw 行的权限范围要写清。** 它只覆盖作动器能提供的那部分（偏心力源的力臂力矩）。双足的转向能力来自**落脚点选择**，而接触型在分配器之外（§9.5），所以**分配器不管走路转向**。

**切换瞬间的指令阶跃**，两个方向不对称：

| 方向 | 后果 | 由什么吸收 |
| --- | --- | --- |
| **落地**（6 → 4，收敛窗口内 4 → 3） | 需求本来就在趋零 | §5.1 / §5.3 的摆正：落地时姿态正被往竖直收敛，控制层对 pitch / roll 的力矩需求本来就该消失。**「先摆正、后降维」是自然顺序，不需要额外过渡逻辑** |
| **起飞**（4 → 6） | 两行突然出现，分配器第一次能命令 pitch / roll 力矩 | 由飞行控制层吸收（§12.2）：§4.3 已定 PD 属它，`docs/角色控制器-刚体原型与引擎约束.md` §7.2 已定角加速度必须限幅。**但控制层必须知道当前行表**，否则它在什么维度上工作都是猜的 |

**死行上出现非零分量有两种来源，处置完全不同**：

| 来源 | 例子 | 处置 |
| --- | --- | --- |
| `w_des` 在死行上非零 | 地面上控制层还在要 pitch 力矩 | **上层搞错了**，应当断言或记日志 |
| `w_known` 在死行上非零 | 地面上一片机翼的升力在质心上方产生 pitch 力矩 | **正常，静默丢弃**——引擎也会吃掉那份力矩（§8.3），所以它既进不了胶囊、也不需要被抵消 |

### 9.9 混合作动器与代回复核

**单侧与双侧的界混在同一个 `u` 向量里。** 归一化之后推进器是 `[0, 1]`、舵面是 `[−1, +1]`（§9.4）。级联钉界时必须**记住钉的是哪一个界**，§9.7.4 第 ⑤ 步的乘子符号检查要按作动器类型取符号。这不是新算法，是记账。

**一条免费的不变量**：`w_alloc = 0 ⟹ u = 0`。因为 `u = 0` 在界内，且 `W` 正定，阻尼最小二乘的最小努力解就是零。这是「零出力永远可达」在分配层的形态，也是最值得写成单测的一条：**任何配装下，零指令都不许点火。**

**分配输出是「期望的可命令量」，不是「已实现的」。** §9.3 给作动器属性列了响应时间，速率限制会让实际值落后于指令，因此实际气动力/推力不等于 `J u`。代回复核必须走完整条链：

```
u_cmd → 作动器响应模型 → u_actual → 该作动器自己的力函数 → 实际 wrench
```

**代回复核是纪律，不是优化。** 跳过它就成了「先假设这个力可达、再按假设施加」——那不再是模型误差，而是**凭空造力**。它与 §10.4 的目标减法互补：减法保证「要的那份」进得了饱和判断，复核保证「给的那份」真的出得来。

**二值作动器（固体火箭、姿控喷口一类，`u ∈ {0, 1}`）当前不纳入。** 它们的可行集非凸，连续最小二乘会给出「50% 油门」这种不存在的中庸解，而且不报错。登记为 §12 的待定项；接入前必须先决定是 PWM 成一阶等效、还是像接触型一样留在分配器之外。

**`u` 还要跨线程、也大概率要跨端。** 分配器在**物理线程**上跑，而程序性动画（§9.7.1 附带收益二）在客户端渲染侧。通路：

```
物理线程：解出 u  →  不可变快照  →  主线程  →  同步给客户端  →  动画消费
```

三件事要一起定：

1. **不要跨线程直接读写。** 沿用既有的不可变快照形态（`common/control/MechaControl.java#LogicStateSnapshot` 就是物理线程 → 主线程的出口），不要给 `u` 另开一条可变引用。
2. **同步频率不必跟物理步。** 动画要的是平滑过渡，不是 100 Hz 的原始序列：可以按较低频率发 `u` 并在客户端插值，也可以只发已经归一化的「油门」与「偏角」两组量。
3. **它要么进 `SynchedEntityData`，要么进新的载荷字段。** 按仓库的字段表纪律，`EntityDataAccessor` 只能在末尾追加，且改动字段表或载荷字段后必须同时提升 `network/ARMSNetwork.java#PROTOCOL_VERSION`。

## 10. 空中气动

### 10.1 复用 SubPart 已有的气动系统

`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#prePhysicsTick` 已经在每物理步为每个流体动力计算点算气动力，模型是**一阶 + 二阶双项**：

```
一阶（粘性）：  F₁ = viscosity · c₁ · |v| · wettedArea
二阶（惯性）：  F₂ = 0.5 · density · c₂ · |v|² · projectedArea
```

坐标：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/util/mechanic/DynamicUtil.java#applyAxisDrag`。设计说明见 `../Machine-Max/docs/wiki/4-物理与战斗机制/4.2-流体动力学与气动.md`。

要点：

- 系数是**每个方向一对**（一阶 / 二阶），六个方向各自独立，默认 `[0.1, 1.0]`（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/HydrodynamicAttr.java#DEFAULT`）；
- **逐轴各向异性已经存在**：`DynamicUtil.java#applySimpleDragAllDirections` 对三轴分别使用 `projectedArea.x/y/z`（`SubPart.java#projectedArea`，可由 `SubPartAttr#projectedArea` 显式配置，或由 `../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/Part.java#calculateProjectedArea` 自动算出）；
- 还有跨音速增益、升力（简易系数或升力线模型带失速裁剪）、以及**部件互相遮挡**（沿来流方向射线，按 `SubPartAttr#hydroPriority` 判定谁遮谁）；
- **升力与诱导阻力是耦合的，但只在高级气动分支里**：`DynamicUtil.java#advancedAeroForce` 用 `cd = cd0 + kInduced · cl²`（`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/AdvancedAeroAttr.java#kInduced`），`cl` 由**局部来流攻角**算出。所以「偏转 → 攻角变 → `cl` 变 → `cd` 跟着变」这条耦合在力函数内部成立。而简易模型（`advanced` 为假，`HydrodynamicAttr#advanced` 的默认值就是假）走 `applySimpleDragAllDirections` 与 `xLift/yLift/zLift`，**升力与阻力之间毫无关联**；
- 施加方式在 `SubPart.java#prePhysicsTick` 里是 `PhysicsRigidBody#applyForce`（力 + 作用点），**施加在每个 SubPart 自己的刚体上**。本方案改为只取该步算出的力与作用点，交由 §9.1 的归约汇总到胶囊——施加权的归属见 §12.7；
- 只在服务端、且 |v| > 0.1 m/s 时计算。

**因此不需要新增气动模型**，需要定的是它与其他力通道的关系，以及两个输入量（计算点位姿、当地速度）取谁。

### 10.2 逐计算点的速度

气动力的输入是**那个计算点自己的速度**，不是某个全局速度。这不是新增要求，是现有实现的既有做法：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/util/MMMath.java#relPointLocalVel` 取的就是「该 SubPart 质心线速度 + `ω × r`」，其中 `r` 是计算点相对该 SubPart 质心的位移。

```
v_点 = v_SubPart + ω_SubPart × r_点
```

**这个 `ω × r` 项就是后掠、上反角与滚转阻尼的全部来源**：

| 特性 | 靠什么产生 | 用统一速度会怎样 |
| --- | --- | --- |
| **后掠的风向标稳定性** | 偏航时翼根与翼尖看到的来流方向不同，两侧展向流动不对称 | 各点来流一致，恢复力矩**恒等于零** |
| **上反角的滚转恢复** | 侧滑时两侧局部攻角一增一减，升力的横向分量给出恢复力矩 | 两侧攻角相同，恢复力矩**恒等于零** |
| **滚转阻尼** | 滚转时一翼下压一翼上抬，`ω × r` 给出相反的法向速度，阻力差形成反滚转力矩 | 两侧法向速度相同，阻尼**恒等于零** |

三者都是**静默失效**：公式不报错，只是那几项再也算不出来。因此有三个"不能用"：

- **不能用胶囊的速度场。** 分轴锁 `(0, 1, 0)` 把 pitch / roll 的角冲量全部吃掉（§2.2 选择 2），落地摆正期间角因子更是 `(0,0,0)`，所以胶囊的 `ω` 对俯仰与滚转恒为零——**上反角与滚转阻尼会精确地等于零**。
- **不能用躯干速度代偿。** 用躯干或任何单一刚体的 `ω` 等于假设整个装配体是刚性的，而 SubPart 之间是约束连接的。各 SubPart 自己的 `(v, ω)` 是它们作为真实动力学刚体的真实状态，不需要这个假设。
- **不能用配装期的静态位姿代替 `p_i`。** 力臂必须每步重算，理由见 §9.3。

用 SubPart 自身的状态还有一个额外收获：**舵面相对机翼的偏转速率被自然算进 `v_点`**，而它是舵面控制力的时间导数来源。用任何别的刚体的角速度都会把这一项丢掉。

**服务端与客户端的差别**：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#setKinematic` 只在客户端被调用（构造函数里按 `isClientSide()` 判定），所以客户端的气动刚体是运动学的。气动只在服务端计算，因此服务端读到的是求解器给出的真实角速度，而客户端的运动学刚体给出的角速度是零——那里不跑气动，所以不影响结果，但读速度的实现要知道这个差别。

**实现备注**：`MMMath.java#relPointLocalVel` 内部每次调用 `getAngularVelocityLocal(null)` 都会分配一个 `Vector3f`。归约层按点每 tick 调用，应当复用暂存向量。

### 10.3 仿射模型：基准项与增量项

气动力里含有**偏转带来的那一份**，而那一份就是控制力。这件事在分配器里不需要「切分」——它就是**一次仿射建模**：

```
w_aero(u) = w_aero(0) + J · u
             └─截距─┘   └斜率┘
```

| 那"一遍"力函数 | 同时是什么 |
| --- | --- |
| `u = 0`（基准偏角） | **截距**：固定零件与舵面的基准气动力，进目标减法（§10.4） |
| `u = u_max` | **斜率端点**：给出割线列 `J_k = ( w(u_max) − w(0) ) / u_max`（§9.7.2） |
| 实际 `u` | **代回复核**：按 §9.9 的链条校验实际出得来多少 |

三样东西出自同一个力函数、同一套输入，因此**不重不漏是构造性质**，不依赖「拆一份结果时对不上参考点」这类约定。固定零件只需要第一遍（它没有偏角这个量），舵面需要前两遍，第三遍对所有作动器都要做。

**低速失效因此也是构造性的**：`q = ½ρv²` 趋零时舵面的列模长趋零，分配器自然不会用它，不需要额外加一条「速度不够就没有舵效」的规则（§9.7.1）。

**基准项不能走错通道**，否则二选一都是错的：

- 把它当控制力 → 基准阻力被当成了可支配的机动能力；
- 把它从目标里漏掉 → 作动器被要求去凑一份**环境已经给过**的力，等于凭空造力。

### 10.4 气动的去向：目标上的减项

基准项（`u = 0` 的那一份）在**分配目标**里被减掉；施加时它与作动器的力一起进入合力：

```
w_alloc      = w_des − w_known                         目标：作动器要凑的量
u            = 级联伪逆(J, 界, W, λ, w_alloc)          求解（§9.7）
F_out, τ_out = 各力源实际 wrench 之和 = J·u + w_known    施加：每物理步各一次（§8.1）
```

`w_known` 的内容：**固定零件气动的全部、舵面的 `δ = 0` 基准项、以及其它已知且可测的干扰力矩**。重力是否算在内，取决于控制层希望 `w_des` 表示「胶囊的净受力」还是「除重力之外的受力」——无论取哪种，**这条减法与它保持一致**即可。

**它不是「输出上加一份抵消力」。** 施加的永远是**各力源的实际力**：机翼的升力是真的（由气动模型给出），推进器的推力是真的（由油门与力函数给出）。所谓「抵消」发生在**目标那一侧**——因为目标里减掉了基准项，作动器才会被要求多出一份去顶它；顶不动时缺口照实报出来，胶囊就真的减速了。

反过来，若把基准项当作「输出上的额外抵消量」，那一份就**没有任何作动器在提供**，而 §8.1 的手工合力让引擎不会替我们检查这件事——那才是凭空造力。三条路的完整对比见 §10.6。

### 10.5 为什么不能折进界（权限）

一个自然的想法是把气动并入作动器的能力描述，作为界的偏置——即把某作动器的可用区间整体平移一个 `−D`（阻力反方向）。设某轴推进器配置为 `F ∈ [0, 1000] N`（单侧推进器，零下限的含义见 §9.7.6 的四种区间），当前该轴阻力 `D = 500 N` 且与速度反向：

| 速度方向 | 偏置后的可用区间 | 问题 |
| --- | --- | --- |
| 沿 −轴（阻力指向 +轴） | `[0 − 500, 1000 − 500] = [−500, 500]` | 新下界 −500 落在**没有反向推进器**的方向上，这个负值是假的 |
| 沿 +轴（阻力指向 −轴） | `[0 + 500, 1000 + 500] = [500, 1500]` | 上界超出推进器能力 500，**执行层做不出来**；且下限 500 > 0，等于宣称这台推进器**关不掉**，而它其实随时可以不出力 |

即偏置法让区间的两端**同时**失去物理意义（一端是假的、一端不可实现），第二行还额外丢掉了「零出力永远可达」这一条。根本原因是它把「环境施加的力」与「引擎能出的力」混进了同一个区间。

除此之外还有三条理由：

1. **升力不是阻力。** 升力垂直于来流，不可用"沿速度方向的偏置"表达；带倾角时升力可以指向侧向甚至向下，标量偏置编码不了。
2. **偏置是速度平方的、界是缓变的。** 上面的 `[−500, 500]` 只是当前速度下的瞬时值，速度一变整个区间就变了，界随之每步变形状——而界本该是配装期确定、运行期缓变的能力描述。
3. **每轴独立假设在斜流下失效。** 气动系数是按流体动力计算点本地坐标系的六个方向给的，而气流相对本体是任意方向；斜流下 Z 轴的阻力耦合进 Y 轴，逐轴盒的对角结构保不住。

### 10.6 三条路的对比：改界、改目标、绕开分配器

同一份气动力可以放在三个位置，后果完全不同：

| 做法 | 改的是什么 | 模型偏差的后果 | 判断 |
| --- | --- | --- | --- |
| **折进界** | 作动器的**界**（权限） | 界就是权限。预测偏差直接吃掉机动权限——连"想出的力"都出不了 | ✘ 见 §10.5 |
| **折进目标（矢量减法）** | 需求的**大小** | 只是**当拍问错了量**。权限完好，下一拍由 `w_des` 重算目标继续纠 | ✔ 本方案（§10.4） |
| **加在输出** | 绕开分配器 | 那一份**没有作动器在提供**，而手工合力让引擎不会检查（§8.1）——凭空造力 | ✘ |

**第二行与第一行的区别必须说清：折进目标不损失权限。** 它只改**需求**——`J` 与 `u` 的界一根毫毛都不动。模型不准时给出的只是「这一拍问错了量」，而 `w_alloc` 每拍都由 `w_des` 重算，反馈下一拍继续纠。所以它与「把偏差当残余扰动」是同一个性质，**不是** §10.5 批的那种污染权限。

**第三行为什么是凭空造力。** 以「沿 +x 想保持速度、阻力 500 N 反向、推进器上限 300 N」为例：

| | 分配目标 | 分配结果 | 实际施加 | 净力 | 缺口报告 |
| --- | --- | --- | --- | --- | --- |
| 加在输出 | `w_des = 0` | `u = 0` | `0 + 500 = 500 N` | `−500 + 500 = 0` | **0（谎报）** |
| **矢量减法** | `0 − (−500) = +500` | 饱和，`Ju = 300 N` | 实际力之和 `300 − 500 = −200 N` | `−200 N` | 200 N ✔ |

第一行的 500 N 里**有 200 N 没有任何作动器提供**，是靠算术变出来的；而且缺口报成 0——残差是 windup 保护的输入（§9.7.4），这个谎会被用上。第二行把这份需求送进级联，饱和、`u_actual`、缺口、windup 回退全部自洽。

**对模型精度的要求不高**：只要把扰动压到反馈带宽以内，剩下的由反馈处理。而气动模型本来就在每物理步跑，`w_known` **复用的是同一份模型、同一份数据**，不需要为它单建一套预测器。代价是那道力函数要多跑两遍（`u = 0` 与 `u = u_max`，见 §10.3），但不算新的模型开销。

**配平有了明确的归属。** 协调盘旋要求 `n = 1/cos φ` 倍的升力、进而 `n²` 倍的诱导阻力（量级：20 m/s、翼面积 1.0 m²、`cd0 = 0.05`、`kInduced = 0.06` 时，30° 盘旋的阻力比同速平飞高约 22%）。在「前馈 + 反馈两路相加」的写法里，这份多出来的推力没有归属。在目标减法里它自己就出来了：`w_known` 每拍按**当前**状态算（含当前的 `cl` 与 `cd`），`w_des` 要的是净受力，**差额自动落进 `w_alloc`，由分配器去找谁来出**。飞行控制层因此只剩一件事——把意图翻译成 `w_des`（§12.2）。

### 10.7 目标减项的取模取向（待定）

目标减法把气动**预**减掉了，于是「损伤后自然失衡」这个期望表现会被压掉一部分：如果 `w_known` 用的就是当前（已损伤）的气动模型，那它减掉的是"现在真实的气动"，失衡被主动纠正。

因此要明确一个取向：

- **失衡作为表现** → `w_known` 只能用**未损伤的基准模型**，让损伤造成的那部分偏差留给反馈去纠（纠不动就是失衡）；
- **抗扰优先** → `w_known` 用当前完整模型。

这不是技术选择而是手感选择。它同时决定飞行控制层的增益该多大，因此与 §12.2 绑在一起。

### 12.6 默认气动系数对行走的影响

**卡在哪**：用默认系数与一组假定值粗算，6 m/s 的二阶阻力约 11.6 N、约 0.17 m/s² 减速度，相对地面低速区约 8 m/s² 的控制力加速度几乎无影响——**这是参数估算而不是实测**，`projectedArea` 的取值是按机娘尺度假定的 0.5 m²，实际值由 `Part.java#calculateProjectedArea` 从模型算出。

另外遮挡检测的 `HydrodynamicAttr#effectiveRange` 默认 **1.0 m**，即 1 m 内的同装配体部件默认会互相遮挡；该默认值是按载具尺度给的，机娘的部件间距是否落在同一量级需要确认。

**还有一个开关必须显式确认**：`HydrodynamicAttr#advanced` 的默认值是 **`false`**，而**只有高级气动分支里才有升力与诱导阻力的耦合**（`cd = cd0 + kInduced · cl²`，见 §10.1）。默认配置下走的是简易模型，升力与阻力互不关联——对一架要做盘旋、失速、跨音速的机体来说，这个默认值不能就这么留着。**它同时决定气动面在分配器里有没有用**：简易模型下舵面的列几乎只剩 `cd` 的二次项，`∂/∂δ` 很小，分配器会**自动不用它们**——不报错，只是气动面等于没装（§9.7.2）。

**失速处雅可比列会跳变。** `DynamicUtil.java#advancedAeroForce` 把 `cl` 硬性裁剪到 `±clMax`（该文件里 `clMax = aero.liftSlope() · aero.alphaStall()`）。失速之后 `∂cl/∂δ = 0`，于是**整列恰好为零**——分配器自动不再指望这片舵面，这是好事，不需要特判。要处置的是**边界上的跳变**：列从有限值直接跳到 0，工况停在边界附近时分配会在「用这片面」与「完全不用」之间来回。候选处置：对列做低通（按上一拍插值）、把硬裁剪换成饱和过渡、或接受它（失速本来就是非线性区）。

**需要谁定**：需要在真实装配体上取一次实际 `projectedArea`，并显式决定 `advanced` 的取值与 `AdvancedAeroAttr` 的系数（`liftSlope` / `alphaStall` / `cd0` / `kInduced`）。

**定了之后动什么**：§10.1 的参数取值、§10.6 里 `w_known` 的精度、§9.7.2 的割线列在失速区的处置。

### 12.7 怎么让 SubPart 不再自行施加气动力

**卡在哪**：§10.1 的现有实现是**每个 SubPart 把气动力施加到自己身上**（`SubPart.java#prePhysicsTick` 里的 `this.body.applyForce(...)`）。§9.1 的归约要求这份力作为数据交给胶囊侧的单一施加点，两者并存会把同一份气动力算两次——一次进了 SubPart 自己的刚体，一次进了胶囊。

**已经排除的选项**：「保留 SubPart 自施加、胶囊不重复接收」不可行。SubPart 自施加改变的是**它自己的角动量**，而约束不会把这份力矩转交给胶囊，因此这条路的代价是**永久放弃气动姿态控制**；它换来的是省掉一次改造。

**剩下的两条路，区别只在改造放在哪一层**：

| 路径 | 做法 | 代价 |
| --- | --- | --- |
| **改 Machine-Max** | 让 `SubPart` 不再对自己的刚体施加气动力，或把它抽出来由装配体统一施加 | 要动同级仓库；施加权收口在装配体层，语义最干净 |
| **ARMS-Core 侧拦截** | 在 `SubPart.prePhysicsTick` 的施加调用点上注入并接管 | 不动 Machine-Max；注入点与上游实现耦合，上游改一行即断 |

Machine-Max 自己已有第二种形态的先例——`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/mixin_native/VehicleCoreMixin.java` 用 `@Inject(method = "prePhysicsTick", at = @At("HEAD"))` 把 `VehicleCore` 的物理步挂进 `PhysicsTestBus`。

**需要谁定**：与 §10.4 目标减项的接线一起定。

**定了之后动什么**：§10.1 的施加方式那一行，以及 §10.4 的接线。选定之前 §10.4 不能接线。

**本条与分配决策解耦。** 无论物理那份气动力最终由谁施加，控制器都得**用推力**去顶它（§10.4 的矢量减法），因此目标减法的形式在两条路线下都成立——少一个悬而未决的耦合。

### 12.8 权重矩阵 `W` 的取向

**卡在哪**：`u = W⁻¹Jᵀ(JW⁻¹Jᵀ + λ²I)⁻¹w_alloc`（§9.7.3）里的 `W` 怎么取。按 §9.7.5 它有两层职责，各自要定一个基准：

| 层 | 要定什么 | 现状 |
| --- | --- | --- |
| **量纲归一化**（必须） | 把力（N）与力矩（N·m）拉到可比尺度的基准：按质量与惯量、按权限上限、还是按误差容限 | 只差一个实测系数：胶囊 yaw 惯量按当前几何约 4.4 kg·m²，**尚未在真实配装下量过**；归一化必须让这一行的权重与三个力行可比 |
| **优先顺序**（按表现定） | 冗余时谁多干一点——大机构先满（直观、好调试）还是小机构先满（大机构留余量给瞬态与损伤） | 有一条有物理依据的候选取值：「推进器贵、气动面便宜」（§9.7.5），它一次性换来跨速度包线；是否采用仍是表现选择 |

**为什么不现在定**：优先顺序依赖飞行控制层（§12.2）——那里才有 `w_des` 各分量的相对重要性；归一化基准要等 §12.3 的力学质量与惯量定下来，并在真实配装上量一次转动惯量。

**定了之后动什么**：§9.7.3 里 `λ` 的归一化前提、§9.7.5 的两层职责、§12.9 的系数。

### 12.9 分配器的数值细节

**已经定了的**（不再需要拍板）：

| 项 | 结论 | 出处 |
| --- | --- | --- |
| 饱和处理 | **级联**：一次全取、一起钉，不追 KKT 最优。每轮至少钉一列且永不释放，因此最多 `N` 轮 | §9.7.4 |
| 要不要收尾乘子检查 | **可选**。零迭代增量（残差是求解副产品，检查只要一次 `N×k` 乘），加上它就把残差明确做成「饱和缺口」输出 | §9.7.4 |
| 残差怎么用 | 直接作为饱和缺口喂给 windup 保护，不另设饱和判据。**缺口是相对于 `w_alloc` 算的**，因此配平需求不算缺口 | §9.7.4 |
| 正则化 | **必须**，取 `λ² = ρ · mean(diag(JW⁻¹Jᵀ))`，`ρ` 从 `1e-4` 起调。它让矩阵恒为正定，同时消灭「约化系统减秩」这条失效 | §9.7.3 |
| 单侧与双侧界混合 | 记账问题：钉界要记类型，乘子符号按类型取 | §9.9 |
| 线性化可信域 | **关闭**。用界上的割线，两端严格精确；唯一曲率在诱导阻力增量项 | §9.6 简化 3、§9.7.2 |
| 要不要引入线性代数库 | **不引入**。只需 6×6 或更小的对称正定 Cholesky，约 40 行，且它是纯函数、可完整单测 | §9.7.3 |
| 门控与降维的关系 | 行表直接由 `angularFactor` 导出，不设独立门控矩阵——两者逐位等价，而前者不可能走样 | §9.8 |

**仍未定的三件**：

1. **失速边界上列的跳变**（§12.6）：列在失速处从有限值跳到 0。低通、平滑裁剪、或接受，需要一次实测看它在边界附近抖得多厉害。
2. **遮挡复用的乘性误差是否可接受**：求导时复用 `u = 0` 那一次算出的遮挡因子，而射线方向随偏角转（`effectiveRange` 默认 1.0 m、`δ_max = 25°` 时端点横移约 0.42 m）。需要确认机娘的部件间距是否落在会让它出错的量级。
3. **作动器响应模型的形态**：代回复核链（§9.9）中间那一步取什么——纯速率限、一阶滞后、还是直接用上一拍的实际值。它决定复核的严格程度，也决定 §9.3 的「响应时间」属性怎么落地。

**需要谁定**：前两件要实测数据；第三件与 §12.2 一起定。

**定了之后动什么**：§9.7.2 的列构造、§9.9 的复核链。

## 13. 术语表

| 术语 | 含义 |
| --- | --- |
| **KCC** | Bullet 的 `btKinematicCharacterController`，经 `com.jme3.bullet.objects.PhysicsCharacter` 封装。幽灵体 + 手写三段扫掠 + 纯速度推导着地，无质量。本方案要替换的就是它 |
| **角因子** | `PhysicsRigidBody#setAngularFactor(Vector3f)` 的取值。它乘在**角冲量/力矩的累加处**，置 0 的轴对力矩与接触角冲量都不响应；它**不修改逆惯量矩阵**，也**不清零已有角速度**，更**不拦直接的位姿写入**（§5.2） |
| **分轴锁转** | 用角因子逐轴开关旋转自由度。本方案用 `(0, 1, 0)` 表示「锁 pitch / roll、留 yaw」，落地收敛窗口同样保留 yaw |
| **摩擦锥** | 接触点能传递的切向力上限 `\|F_t\| ≤ μN`。`N` 是法向力，`μ` 是双方摩擦系数之积 |
| **组合摩擦** | 引擎对一对接触体取双方摩擦系数之**积**作为有效摩擦系数 |
| **力源** | 能产出力与作用点数据的对象，共四类：推进器、接触型、固定零件气动、舵面气动。四类的共同约定是**都不自行施加到刚体**，只产出 `(作用点 p, 力矢量 F)` 交给单一施加点（§9.1） |
| **作动器** | 有**可命令量**的力源。推进器（油门）、舵面与减速板（偏角）都是作动器，差别只在界与雅可比列；接触型的可命令量是落脚点，方向不在本体坐标系里，留在分配器之外（§9.3、§9.5） |
| **固定零件气动** | 没有可命令量的气动面。它不由控制器支配，而是从分配目标里被**减掉**（§10.4）。与舵面按**有没有作动器**划分，不按外形或安装位置 |
| **控制分配** | 把期望的净 wrench 翻译成各作动器可命令量的过程：解 `J u ≈ w_alloc`，受逐作动器的界约束（§9.7） |
| **雅可比列 / 割线列** | 某个作动器的 `u` 变化一单位给胶囊带来的力与力矩（`J` 的一列）。气动面取 `u = 0` 与 `u = u_max` 两端之差，因此是**割线**而非切线，在两端严格精确（§9.7.2） |
| **分配目标 `w_alloc`** | `w_des − w_known`，即作动器真正要凑的那份 wrench。矢量减法保证它进了饱和判断（§9.4、§10.4） |
| **作动器控制量 `u`** | 分配器的输出：每个作动器该出多少（归一化油门或偏角）。它既是要施加的量（先经 §9.9 的复核链），也是**程序性动画的原始输入**——尾焰大小、舵面偏角直接用 `u`，不另算（§9.7.1、§9.9） |
| **活行 / 行表** | 分配问题的行 = 引擎实际接受的 wrench 分量。活行由当前 `angularFactor` 导出（地面 4 行、飞行 6 行、落地收敛窗口 3 行），不另设门控矩阵（§9.8） |
| **级联（饱和处理）** | 伪逆解撞界后，把越界的作动器一起钉在各自撞到的界上、目标减去它们已提供的量、再用剩余自由列重解。每轮至少钉一列且**永不释放**，因此最多 `N` 轮。**贪心、不追 KKT 最优**（§9.7.4） |
| **饱和缺口** | 级联收敛后未被满足的那份 wrench，即残差 `w_alloc − Ju`。它直接喂给 windup 保护，不需要另设饱和判据；配平需求不算缺口（§9.7.4） |
| **可达集** | 全部作动器一起能产生的 wrench 集合。它由 `J` 的列空间给出（每个作动器只有一个可命令量，一份量同时决定一份力与一份力矩），不是两个独立的 3 维盒（§9.7.1） |
| **配平** | 让净受力为零所需的作动器输出（悬停顶重力、巡航顶阻力）。它由目标减法自动产生，不是独立的一路前馈（§10.6） |
| **铰链反作用力矩** | 舵面偏转时气动力对转轴产生的力矩。本方案不建模：舵面无刚体时它不存在，有刚体时由铰链作动器的反力矩承担（§9.6 简化 2） |
| **动压** | `q = ½ρv²`，气动力与舵面控制力的共同来源。速度趋零时 `q` 趋零，因此舵面低速失效是构造性的。**取值必须用计算点自己的速度**，含 `ω × r` 项（§10.2） |
| **wrench** | 力与力矩的合称（6 维：3 力 + 3 力矩）。力与力矩的可达集在 wrench 空间里是一个整体，本方案用 `J` 描述它（§9.7.1） |
| **windup** | 执行器被物理约束截住时控制器内部积分项继续累积的现象。本方案不另设饱和判据——分配器的残差就是缺口，按 `实际出力 / 期望出力` 回退积分（§9.6） |
