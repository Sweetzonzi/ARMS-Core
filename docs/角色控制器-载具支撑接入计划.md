# 角色控制器：载具支撑接入计划

> 状态：待实施。2026-10-26 完成源码调查与四项临时诊断；正式控制器尚未实现本文方案。
> 目标：角色能够落在载具刚体上、随接触摩擦获得平台运动、相对甲板行走并跳离平台。
> 范围：ARMS-Core 的角色控制器，以及 Spark-Core / Machine-Max 中直接相关的碰撞组和接触接线。

## 1. 目标与边界

本计划把载具表面视为可运动的支撑面。角色使用自己的动态刚体接受求解器响应；站在甲板上属于接触运动，乘坐座位属于乘客态，两者有各自的运动权威。

完成条件包含：静止甲板着地、相对甲板的行走与制动、平移与旋转平台、升降平台、跳离与走出边缘，以及支撑体失效后的释放。载具急加速、急刹车或急转弯可以使角色滑动、失去支撑；验收不要求角色与甲板刚性绑定。

基础几何采用平底圆柱，半径 0.4 m、全高 2.4 m，来源为 `common/control/attr/MechaBodyPreset.java#newBodyShape`。服务端执行物理、客户端消费同步位姿的分工见 `docs/ArmsCore双端权威与网络同步实现计划.md` §2.1 的 D1、D18；基础地面力律见 `docs/角色控制器-刚体动力学方案.md` §7.4。本计划的碰撞过滤、支撑观测与运动参考系属于待实施的专项设计。

第一阶段不包含：载具甲板上的自动越障、角色身体部件的物理装配、布娃娃、座位绑定、命中盒接入，以及动画查询的速度口径调整。地形上的越障继续由 `common/control/MechaCharacter.java#tryStepUp` 负责；乘客态设计见 `docs/宿主位置权威与位移摄入设计.md` §七。

## 3. 碰撞身份与接触过滤

### 3.1 独立碰撞组

在 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/CollisionGroups.kt#CollisionGroups` 统一定义拟议常量 `CHARACTER_CONTROLLER`；实施时从该文件的空闲位分配，ARMS-Core 不自行硬编码位值。

| 对象 | group | 目标掩码与职责 |
| --- | --- | --- |
| 角色控制器 | `CHARACTER_CONTROLLER` | `TERRAIN | PHYSICS_BODY`，承担场景接触响应 |
| 普通实体代理体 | `PAWN` | 使用 Spark-Core 的实体代理策略；绑定期间不对同一宿主施加第二份载具人工响应 |
| 载具部件 | `PHYSICS_BODY` | 在其现有碰撞范围中显式接受 `CHARACTER_CONTROLLER` |
| 静态地形与 Create 装置 | `TERRAIN` | 角色侧显式放行；支撑处理按刚体运动属性区分静态地形与运动学装置 |

独立组负责身份与过滤，触地可用性由 §4 判定。组关系采用显式双端声明，实际行为按 §2.1 的 Libbulletjme 规则验收。

角色与同宿主代理体、同装配体身体部件之间建立忽略关系；向下扫掠另行应用相同身份排除。`../Spark-Core/src/main/java/com/jme3/bullet/collision/PhysicsCollisionObject.java#addToIgnoreList` 的说明明确指出射线与扫掠不遵循该忽略表，因此物理接触过滤不能代替查询筛选。

### 3.2 与 Machine-Max 的边界

Machine-Max 将 `CHARACTER_CONTROLLER` 接触交给刚体求解器，角色与车体的物理碰撞只解算一次。普通实体的人工击退分支在绑定宿主上需要跳过，判据使用宿主绑定关系；不能因为角色代理体关闭接触响应，就假定载具的人工回调也不会运行。

接线调查点为 `../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#onPreCollision`、`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/collision/CollisionHandler.java#onContactProcessed` 与 `common/IArmsHost.java#getControlledArmsCore`。跨仓库实现应使用可选集成或公共判据，避免 Machine-Max 对其附属模组 ARMS-Core 建立强制反向依赖。

主线程快照的追踪范围由 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/CollisionGroups.kt#SNAPSHOT_TRACKED` 与 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/level/WorldSnapshot.kt#markAdd` 控制。本计划的支撑查询在物理空间执行，独立组无需因此进入主线程快照；控制器形状也不作为命中盒。

## 4. 支撑观测与字段纪律

### 4.1 观测结果分成三个概念

| 概念 | 来源与用途 |
| --- | --- |
| 支撑候选 | 向下扫掠命中，只说明脚下窗口内有可站立表面 |
| 有效承重接触 | 接触点满足底部位置、朝上法线与有效距离等条件，允许使用地面驱动和向支撑体回传主动反作用 |
| 触地状态宽限 | 短暂漏判时给状态机使用的有限保持；不凭宽限向已经失联的车体施力 |

本步无有效承重接触时，不对历史支撑体施加接触式驱动。起跳许可第一阶段也以有效承重接触为准；宽限不单独构成一次起跳许可。贴地保持不能制造吸附力或直接搬运角色位置。

### 4.2 只保存有消费者的数据

| 数据 | 生命周期与理由 |
| --- | --- |
| 上次选中的支撑体身份 | 物理线程跨步保存，用于支撑切换的稳定选择；每步校验仍在同一空间且可用 |
| 触地保持计数 | 物理线程跨步保存，供状态机宽限使用 |
| 支撑点、法线、材质与承重有效性 | 每步生成的一份观测，供本步力学与逻辑消费者共享；缓存容器可以复用，内容必须标记所属物理步 |
| 支撑点速度、相对切向速度与相对分离速度 | 从本步观测与刚体状态现算，作为本步计算量 |
| 间隙 `gap` | 当步候选筛选和距离上限判断的局部变量；不进入跨步支撑状态，不用于补算平台位移 |

`common/control/MechaCharacter.java#groundGap` 及其公开读取口 `common/control/MechaCharacter.java#getGroundGap` 当前存在，但本仓库没有该读取口的调用方。实施时核对兼容要求；本计划不为支撑记录增加间隙缓存。若有外部兼容需求，测距接口也须说明采样时效，不能把过期距离当成承重依据。

### 4.3 候选与承重筛选

1. 允许的组是 `TERRAIN` 与 `PHYSICS_BODY`；排除自身、同宿主代理体、同装配体部件、触发体、无接触响应物体和已失效对象。碰撞关系不允许的对象也不能成为查询支撑。
2. 接触法线统一为“由支撑体指向角色”的世界法线，必须朝上；首轮采用当前 `common/control/MechaCharacter.java#GROUND_NORMAL_THRESHOLD`，并在旋转甲板上验证。`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/ManifoldPoint.kt#getNormalWorld` 会按 A/B 归属翻转，调用方须显式核对方向。
3. 接触位于角色底部支撑区域；头顶、侧墙与车底面不构成承重。接触距离阈值、底部区域与边缘接触的合法范围由 §8 的边界用例标定。
4. 真实接触优先于仅扫掠可见的候选。多个有效接触先按接触距离与支撑位置筛选，在近似等价候选中优先保持同一支撑体，最后采用稳定排序；不能跨不同支撑体只取最竖直的一条法线。
5. 跳离、warp、支撑体离开空间、部件失效及世界卸载使相关观测失效。支撑切换本身不叠加速度。

扫掠接口 `../Spark-Core/src/main/java/com/jme3/bullet/collision/PhysicsSweepTestResult.java#PhysicsSweepTestResult` 提供对象、比例、法线与形状索引，没有接触点位置。精确支撑点从 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/ManifoldPoint.kt#getPositionWorld` / `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/ManifoldPoint.kt#getLocalPoint` 取得；扫掠候选不能虚构一份精确接触点。

## 5. 运动参考系与力学处理

### 5.1 支撑点速度与相对速度

所有速度单位为 m/s，角速度单位为 rad/s。设支撑体质心世界位置为 `c_s`，接触点为 `p`，支撑体线速度为 `v_s`、角速度为 `ω_s`，朝向角色的单位支撑法线为 `n`：

```text
v_support(p) = v_s + ω_s × (p − c_s)
v_character(p) = v_c + ω_c × (p − c_c)
v_relative = v_character(p) − v_support(p)
v_separate = dot(v_relative, n)
v_tangent = v_relative − v_separate · n
```

支撑点应取真实接触位置；存在两侧接触点时分别计算角色侧与支撑侧的点速度。公式中的共同 `p` 是接触距离可忽略时的表达。世界点速度已有实现可复用：`../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/util/MMMath.java#worldPointWorldVel`。

地面力速曲线与无输入制动使用 `v_tangent`，输入方向按视野转换到世界系后投影到支撑切平面。输入投影只做一次，并处理投影接近零的情形。上升拒绝使用 `v_separate`，因此人与升降台同速时相对分离速度为 0。

世界速度用于真实积分、同步与空中惯性；相对速度用于支撑相关的运动控制。`common/control/MechaCharacter.java#getHSpeed` 和 `common/control/MechaCharacter.java#getHorizontalVelocity` 的世界速度语义保留，逻辑层需要相对量时使用含义明确的独立读取口。

### 5.2 跟随、竖直修正与起跳

跟车由接触约束、摩擦和有限主动控制产生。控制器不按支撑体变换增量搬运角色，也不在每步世界速度上累加一份平台速度。平台旋转带来的切向速度由 `ω × r` 与接触摩擦体现，视野偏航权威继续来自 `common/control/MechaCharacter.java#setViewYaw`。

`common/control/MechaCharacter.java#updateWalk` 中的小正竖直速度修正需要按支撑参考系重新审查：不能把角色随平台产生的世界系上升速度清零；也不能在无接触或平台下坠时制造把角色拉向平台的法向速度。先用接触求解器验证稳定性，再决定是否需要有界的相对法向残差修正。

`common/control/MechaCharacter.java#updateJump` 的瞬时冲量以角色已有世界速度为起点，速度增量上限按支撑相对速度解释，避免载具速度占满角色的起跳预算。成功起跳当步使承重许可与保持状态失效，禁止该步再次制动起跳分量。失去支撑后沿世界速度演化，不逐步扣除或补入支撑速度。

持续助推是机体的外力；其松键、时长与上止点终止条件需要覆盖上升和下降平台的起跳，不能因更换参考系引入重复冲量。推进器式闪避沿 `common/control/MechaCharacter.java#requestDodgeImpulse` 的世界轴处理，不自动继承甲板方向；本计划不重定义其力源。

### 5.3 摩擦、法向载荷与反作用

本接触对的材质参数必须同时供给控制器预算与求解器，不能把“地形侧默认 0.5”当成所有支撑体的摩擦。对于各向同性表面可以共享一个有效系数；对于各向异性表面，控制力与前馈须按切向方向取预算。材质接线调查点为 `../Machine-Max/src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/collision/CollisionHandler.java#setupFriction`，接触点组合摩擦入口为 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/body/ManifoldPoint.kt#combinedFriction`。

地形侧的力律基线是 `docs/角色控制器-刚体动力学方案.md` §7.4 的驱动力与摩擦前馈。动态支撑上的前馈是否保留、如何与接触式主动驱动配对，必须先经过 §7 的 V0 对照测量。前馈、被动摩擦和主动反作用不能分别算出后无条件叠加。

目标力学语义：

- 求解器给出的承重、碰撞与摩擦冲量由引擎双向解算，控制器不重复施加。
- 以甲板为反力面的主动行走与接触式起跳，对动态支撑施加等大反向作用，并按实际接触点计算力臂。若采用接触电机式约束，两侧作用由同一约束产生。
- 持续助推及推进器式闪避属于机体外力，其反作用不归属脚下支撑体。
- 只有本步有效承重接触允许向支撑体施加接触式主动反作用；静态体与运动学体遵循各自的无限质量／外部驱动语义。

静态法向载荷估算 `N = m·g·cosθ` 的现有依据见 `docs/角色控制器-刚体动力学方案.md` §7.6。动态支撑加速、转动及落地瞬间的载荷可能偏离该值；这部分属于 V0 的必测项。必须确定适用范围或给出动态载荷取法后，才能宣称通过动态支撑验收。若使用接触冲量估算载荷，要处理首个接触步、步长换算和采样滞后，不能直接拿前一帧冲量当本步权威法向力。

## 6. 线程、时序与同步

支撑选择、接触点读取、刚体速度计算和力的施加全部在物理线程完成；主线程不保存或解引用接触点原生 id。需要跨步的接触数据复制成值，并在下步按对象有效性与当前几何复核。

当前 `common/control/MechaControl.java#onPhysicsStep` 先执行逻辑，再调用控制器的物理预步；`common/control/MechaControl.java#writeStateInputs` 读取触地和世界速度。实施时应使一次物理子步只生成一份支撑观测，逻辑输入与力学消费同一物理步编号的结果。可以拆出“位姿准备与支撑观测／逻辑推进／动作施加”三个阶段；朝向写入必须先于移动意图的世界方向解算，且支撑扫掠使用准备阶段的姿态。

接触流形反映最近完成的求解步；它不是未来一步的真实接触。准备阶段读取流形时需要用本步的刚体变换复核位置、距离与分离速度，向下扫掠提供当前几何候选。接触回调的产生与消费时序依据 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/level/PhysicsWorld.kt#onContactConceived`、`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/level/PhysicsWorld.kt#onContactProcessed` 与 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/level/PhysicsLevel.kt#prePhysicsTick` 实测确认；不能把当前步尚未发生的回调作为当前步逻辑输入。

逻辑层的地面运动状态需要使用相对切向速率；地面升降不构成自主跳跃或下落。空中状态使用世界系运动。`common/control/MechaControl.java#writeStateInputs` 是接线点，必须检查相关状态图对速度字段的含义，避免把相对法向分离速度冒充世界竖直速度。

下行位姿与速度保持世界系，本计划不增加支撑体引用或支撑点的网络字段。`common/control/presentation/MechaMolangContext.java#queryGroundSpeed` 当前读同步速度，动画查询口径的变更另行设计；本计划的验收范围是控制器与逻辑状态。字段表与网络协议的纪律见 `docs/ArmsCore双端权威与网络同步实现计划.md` §2.2。

## 8. 验收矩阵与命令

### 8.1 自动化物理与逻辑用例

物理车道使用正式控制器、真实 `PhysicsSpace`、0.01 s 步长；既覆盖静态盒，也覆盖有限质量动态平台和正确设置运动速度的运动学平台。平台的位姿积分、速度与接触回调须与生产路径具有同一时序；原始世界位置、世界速度、支撑点速度、相对速度、有效承重状态和主动施力分别记录。

| 场景 | 必须验证的行为 |
| --- | --- |
| 静止地形与静止甲板 | 两类支撑都能着地、起步和停止；车体组分类不能令角色永久处于空中 |
| 匀速平移，无输入 | 相对速度接近零时没有反向世界速度刹车；运动状态不因跟车而进入自主行走 |
| 甲板上相对行走、反向行走与松键 | 力速曲线按相对速度工作，松键制动目标是甲板相对静止 |
| 加速、刹车及有限质量轻平台 | 摩擦不足允许滑动；主动驱动具有反作用；无持续的额外动量来源或同一接触重复冲量 |
| 匀速旋转与倾斜甲板 | 支撑点速度包含 `ω × r`；不同半径速度不同；超过支撑几何／摩擦能力可滑落 |
| 上升与下降平台 | 相对静止时能够识别支撑；上升世界速度不被清零；平台快速下降／失联时不拉住角色 |
| 平移、旋转和升降平台上的起跳 | 已有世界动量保留，起跳增量预算正确；起跳当步无支撑制动；无重复叠加平台速度 |
| 走出边缘与一次扫掠漏判 | 状态宽限与承重许可分离；失联后没有对历史车体的主动反作用 |
| 两支撑交界、支撑失效、warp 与卸载 | 选择稳定，切换不注入速度；失效身份和失效接触几何不进入新场景 |
| 车底、侧壁、触发体、宿主代理体和自身部件 | 不误判承重；接触过滤与扫掠过滤一致 |
| 材质阶梯 | 至少覆盖平台摩擦 0.5、1.0 与低摩擦，以及一组各向异性表面；预算与求解器口径一致 |
| 普通实体与绑定宿主 | 普通实体的载具响应有回归；绑定宿主只接受控制器这一路物理运动 |
| 地形基线 | 平地、半砖、楼梯、坡、拼缝、跳跃和闪避不因载具接入产生非预期变化 |

误差阈值由 V0 给出具体数值并写进正式用例；均匀运动时的相对静止误差、起步加速度和动量变化应有可复现的断言。载具质量与摩擦阶梯至少包含与角色同量级及远大于角色两档，不能用一块无限质量盒代替全部动态支撑验收。

### 8.2 执行与实车检查

```powershell
# 定向验证：V0 建立正式测试类后可执行
.\gradlew --offline test --tests "*MechaCharacterSupportPhysicsTest"

# 完整 JUnit 回归与构建
.\gradlew --offline test
.\gradlew --offline build

# 真实载具、物理线程与宿主同步检查
.\gradlew --offline runClient
```

实车检查包括：停车车顶、匀速车顶、急刹、转弯、旋转载具部件、甲板上行走／起跳／走出边缘、载具销毁，以及玩家退出绑定。确认人物逻辑、控制器位置与宿主显示之间没有第二套载具运动叠加。

GameTest 用于生命周期和注册接线检查；本计划的精细位移与速度断言使用裸物理空间。GameTest 场地与车道边界的说明见 `docs/GameTest车道指南.md` §4、§5，实施时按实际加载的 native 精度与当前坐标链路核对，不能仅凭历史环境假定数值精度。

## 9. 实施前必须定型的事项

| 项目 | 必须回答的问题 | 定型阶段 |
| --- | --- | --- |
| 动态支撑的主动驱动 | 成对施力与接触电机的选择依据；摩擦前馈与被动摩擦的配对方式；有限质量平台的功与动量是否符合 §5.3 | V0，进入 V3 前完成 |
| 动态法向载荷 | 静态估算在哪些加速度与转动范围可用；范围外采用何种有界估算或退化行为 | V0，进入 V3 前完成 |
| 接触时序与有效性 | 流形采样对应哪个求解步；首个接触步与高速离开边缘如何处理；接触点距离／底部区域阈值是多少 | V0–V2，V2 完成前固定 |
| 绑定宿主的跨模组识别 | 使用哪个可选集成入口过滤普通实体人工响应，如何避免 Machine-Max 强制依赖 ARMS-Core | V1 完成前固定 |

这些是局部实现与测量问题，不需要以“先让角色刚性跟随车体”绕过。第一阶段的最终实现必须满足 §1 的接触式运动语义，并通过 §8 的适用场景。
